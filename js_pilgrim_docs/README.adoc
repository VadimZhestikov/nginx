= JS-Pilgrim Architecture
:toc: left
:toc-title: Contents
:toclevels: 2
:sectnums:
:revdate: 2026-03-27

JS-Pilgrim is the codename for the full-proxy programmable layer built on top of
the JS COM foundation.  The goal is to give JavaScript complete control over every
stage of connection and request processing — from raw TCP accept through to upstream
response body — with nginx's existing phase engine treated as one pluggable layer
rather than the fixed centre.

== Design Principles

=== Full proxy framing

Every incoming connection passes through a stack of independently programmable
layers:

....
Client TCP
  ↓
[L4 JS filters]          ← raw Buffer async-generator streams, both directions
  ↓
[Protocol detection]     ← nginx stream / http selection
  ↓
[L7 JS hooks]            ← req / res objects, async hooks before/after phases
  ↓
[nginx phase engine]     ← existing modules (proxy, FastCGI, static, …)
  ↓
[Upstream JS filters]    ← modify what goes to / comes from backend
  ↓
Backend TCP
....

A layer that does nothing passes through automatically.  A layer that calls
`req.respond()` (or equivalent) short-circuits everything below it.  This is the
BIG-IP iRules / HUD filter model: the full proxy gives independent client-side and
server-side streams with hook points at every protocol boundary.

=== Async generators as the layer primitive

Async generators compose naturally into transform pipelines:

[source,javascript]
----
async function* gzipExpand(upstream) {
    const dec = new DecompressStream();
    for await (const chunk of upstream) {
        yield* dec.write(chunk);
    }
    yield* dec.flush();
}

location.addBodyFilter(gzipExpand);
----

The three primitives:

[cols="1,3"]
|===
| `yield chunk`       | passthrough (observe and forward unchanged)
| `yield otherChunk`  | replace (emit different content)
| `return` / `throw`  | cancel / error
|===

=== Module packaging

Packages are directories with a `package.json` (`ngxjs` key) and an `index.js`
entry point.  Installed at runtime with `nginx.use(name, config)` — no reload
required.

=== Admin shell

A JS COM application that uses `nginx.repl` and WebSocket to expose a
browser-based admin UI.  Each installed package contributes a panel (analogous to
a browser DevTools tab).

== Implementation Steps

[cols="1,2,4", options="header"]
|===
| Step | Name | Description

| P1 ✓
| <<p1-location-hooks.adoc#,Location hooks>>
| `location.addHook(fn)` — async pre-content hooks on a location.  Sync and async
  (Promise-returning) hooks; cancel by calling `req.respond()`.

| P2 ✓
| <<p2-scope-hooks.adoc#,Server & global hooks>>
| `server.addHook(fn)`, `nginx.http.addHook(fn)` — hooks at higher scopes
  via the nginx access phase; fire for every matching request regardless of
  content handler.

| P3 ✓
| <<p3-response-hooks.adoc#,Response hooks>>
| `location.addResponseHook(fn)` — fires after upstream selects response
  headers, before they are sent to the client.  Modify status / headers.

| P4 ✓
| <<p4-accept-hook.adoc#,Accept hook>>
| `listener.on('accept', fn(conn))` — TCP connection level hook.
  `conn.remoteAddr`, `conn.remotePort`, `conn.reject()`.

| P5 ✓
| <<p5-gen-filter.adoc#,Generator body filter>>
| Upgrade `addBodyFilter` to accept async generator functions
  (`async function*(body, req)`).  Body is buffered; generator yields zero or
  more output chunks and may `await` between yields.

| P6 ✓
| <<p6-l4-filter.adoc#,L4 data filter>>
| `listener.addL4Filter(asyncGenFn)` — raw TCP byte-stream filter on
  JS-managed listeners.  Client→server direction: intercepts bytes before
  HTTP parsing.  Generator receives `Uint8Array`, yields transformed bytes.

| P7 ✓
| <<p7-module.adoc#,Module packaging>>
| `nginx.use(path, config?)` / `nginx.install(plugin, config?)` API.
  Directory-based packages with `package.json` (`ngxjs.main` entry),
  inline function/object plugins, `nginx.pluginConfig` config injection.

| P8 ✓
| <<p8-async-hooks.adoc#,Async P2/P3 hooks>>
| `nginx.http.addHook(async fn)` / `server.addHook(async fn)` — server-
  and global-scope hooks that may `await` inside the body.  Request is
  suspended (count++) while the Promise is pending; resumed when it
  settles.  Throwing rejects with 500; `req.respond()` short-circuits the
  content handler exactly as in the sync case.

| P9 ✓
| <<p9-next.adoc#,next() / middleware wrapping>>
| All hook callbacks now receive a second argument `next`.  Calling
  `next()` runs the remaining hooks and returns a Promise; code after
  `await next()` in a P1/P2 hook executes before the content handler.
  Hooks that do not call `next()` auto-advance (backward-compatible).
  Implemented as a Koa-style JS IIFE (`__ngx_hook_chain__`) evaluated once
  per context.  `req.responded` (read-only) bridges JS/C for short-circuit
  detection.  `ngx_js_run_chain` replaces the old per-hook C loop.

| P10 ✓
| <<p10-ctx.adoc#,req.ctx — persistent per-request context>>
| `req.ctx` — a plain JS object tied to the nginx request pool, not to
  the JS req wrapper.  Survives async suspend/resume (wrapper replaced),
  and spans the P2-access → P1-content phase boundary.  Lazily created
  on first access; freed via pool cleanup when the request ends.
  Implemented as a C-level `JSValue ctx_obj` slot in `ngx_js_req_ctx_t`
  with a `ngx_pool_cleanup_add` finalizer.

| P11 ✓
| <<p11-shared.adoc#,nginx.shared — cross-worker key/value store>>
| `nginx.shared.get/set/delete/keys/incr` — flat fixed-size shared-memory
  zone (256 entries, 163 kB) protected by `ngx_spinlock`.  Available in
  all request-phase handlers and timer callbacks.  Zone registered via
  `ngx_shared_memory_add` in HTTP postconfiguration; init callback zeroes
  on first start, preserves entries across hot-reload.

| P12 ✓
| <<p12-l4-stream.adoc#,L4 full-stream + async>>
| Upgrade `listener.addL4Filter` to a true streaming async generator:
  `async function*(source)` with `for await (const chunk of source)`.
  `await` is permitted inside the loop.  Multiple TCP segments feed the
  same live generator via a JS async-iterable source factory.  Per-connection
  `ngx_js_l4_pending_t` tracks the live generator; `ngx_js_l4_async_check`
  resumes parked connections from the event loop.

| P13 ✓
| <<p13-l4-send.adoc#,L4 server→client direction>>
| `listener.addL4SendFilter(asyncGenFn)` — intercepts raw outbound bytes
  after HTTP processing, before they reach the client socket.  Hooks into
  `c->send` / `c->send_chain` via pool-cleanup type-tagged state.  EOF
  delivered lazily inside collect loop after first yield.

| P14 ✓
| <<p14-upstream-filter.adoc#,Upstream JS filters>>
| `location.addUpstreamFilter(asyncGenFn)` (response) and
  `location.addUpstreamRequestFilter(asyncGenFn)` (request body) — JS
  generators hooked into `ngx_http_upstream_t` input/output filter chain.
  Completes the top-level architecture diagram layer that P5 covers only
  at HTTP level.  Request-body count balance: `r->main->count--` before
  resuming phases prevents "open socket" hangs.

| P15 ✓
| <<p15-multi-filter.adoc#,P5 multi-filter composition>>
| Allow multiple `addBodyFilter` calls on the same location; each
  filter's output becomes the next filter's input.  `body_filters`
  is a priority-ordered `ngx_array_t`; the runner threads `body_val`
  through all entries (GENERATOR, WB_SYNC, WB_ASYNC, STREAM_*).
  No code changes — structurally complete since P5.

| P16 ✓
| <<p16-hot-reload.adoc#,Post-fork plugin loading (nginx.use hot reload)>>
| `nginx.use(path, config)` callable from a worker request handler —
  loads the plugin locally then sends `NGX_CMD_JS_USE_PLUGIN` to master,
  which forwards `NGX_CMD_JS_LOAD_PLUGIN` to every other worker.
  `ngx_js_load_plugin` is the shared helper; `ngx_js_channel_send`
  promoted from static for reuse.

| P17 ✓
| <<p17-server-accept.adoc#,Standard listen socket support for P4/P6>>
| `server.on('accept', fn)`, `server.addL4Filter(fn)`, and
  `server.addL4SendFilter(fn)` on the existing `NginxServer` COM object,
  so accept hooks and L4 filters work on sockets declared with the `listen`
  directive — not only JS-created listeners.

| P18
| Online package registry for nginx.use
| `nginx.use('vendor/plugin@1.2.3', config)` — resolve from a central
  registry.  Implemented as a CLI tool (`ngxjs install`) that downloads
  to a local cache; the JS runtime stays network-free.

| P19
| Admin shell
| Browser-based admin UI using `nginx.repl` and WebSocket.  Each
  installed package contributes a panel (analogous to a DevTools tab).
  Provides runtime visibility into loaded plugins, hook chains, shared
  state, and live log streaming.
|===

== Hook Cancellation Model

At every layer the same three-outcome model applies:

[source,javascript]
----
location.addHook(async function(req) {
    // 1. Cancel — respond immediately, skip all remaining hooks + handler
    if (!req.headers['authorization']) {
        req.respond(401, {}, 'Unauthorized\n');
        return;
    }

    // 2. Continue — return without responding; next hook (or handler) runs
});
----

There is no explicit `next()` call required.  The chain advances automatically
unless `req.respond()` is called.  (A `next()` API for middleware-style wrapping
is planned as a later extension.)
