1. Overview

A checkpoint is a named, persistent copy of config state that survives across multiple requests and can be restored on demand.

This is distinct from the request-scoped snapshot() / restore() covered in the for single worker guide: a snapshot lives only for the duration of the request that created it; a checkpoint lives until nginx restarts (or longer, if externalised).

2. Worker-level checkpoint

2.1. How it works

A module-level variable in js_source persists for the lifetime of a worker process. Any request handler in that worker can read or write it.

// js_source: worker_checkpoint.js

// The module-level map is shared across all requests in this worker.
const checkpoints = new Map();   // name → NginxSnapshot

function saveCheckpoint(name, snap) {
    checkpoints.set(name, snap);
}

function loadCheckpoint(name) {
    return checkpoints.get(name) || null;
}

2.2. Example: manual checkpoint via admin endpoint

// POST /admin/checkpoint?name=stable  → save current config
// POST /admin/restore?name=stable     → restore that checkpoint

const adminLoc = nginx.http.servers[0].locations
    .find(l => l.path === '/admin/checkpoint');

adminLoc.handler = (req) => {
    const name = req.getVar('arg_name') || 'default';

    if (req.method === 'POST' && req.uri.startsWith('/admin/checkpoint')) {
        const snap = req.location.snapshot();
        saveCheckpoint(name, snap);
        req.json({ saved: name });

    } else if (req.method === 'POST' && req.uri.startsWith('/admin/restore')) {
        const snap = loadCheckpoint(name);
        if (!snap) {
            req.respond(404, {}, 'checkpoint not found: ' + name);
            return;
        }
        snap.restore();
        req.json({ restored: name });
    }
};
A checkpoint stored this way is per-worker. The other workers still have the old config. To propagate the restore to all workers, combine this with the SharedWorker broadcast strategy from the for all workers guide.

2.3. Auto-checkpoint on successful apply

Automatically save a "last-known-good" checkpoint every time a config change is validated and applied:

loc.handler = async (req) => {
    const snap = req.location.snapshot();      // save candidate rollback point

    try {
        const cfg = JSON.parse(await req.readBody());
        req.location.root = cfg.root;

        const ok = await probeBackend(req);
        if (!ok) { throw new Error('probe failed'); }

        // Success — promote snapshot to "last-known-good" checkpoint
        const lkg = req.location.snapshot();   // re-snapshot after apply
        saveCheckpoint('last-known-good', lkg);

        req.json({ applied: true });

    } catch (e) {
        snap.restore();
        req.respond(500, {}, 'apply failed: ' + e.message);
    }
};

2.4. Multi-step migration with intermediate checkpoints

Some config changes involve multiple fields that must be updated atomically or rolled back step by step.

loc.handler = async (req) => {
    const steps = JSON.parse(await req.readBody());

    // Checkpoint before every step so we can roll back to any intermediate state
    const checkpointStack = [];

    try {
        for (const step of steps) {
            checkpointStack.push(req.location.snapshot());  // save this step's start

            applyStep(step, req);

            const ok = await probeStep(step, req);
            if (!ok) { throw new Error('step failed: ' + step.name); }
        }

        req.json({ applied: steps.length });

    } catch (e) {
        // Roll back to the checkpoint taken before the failing step
        const rollback = checkpointStack[checkpointStack.length - 1];
        if (rollback) { rollback.restore(); }

        req.respond(500, {}, e.message);
    }
};

function applyStep(step, req) {
    if (step.type === 'set-root')    { req.location.root = step.value; }
    if (step.type === 'set-timeout') { req.location.proxy.readTimeout = step.value; }
    // …
}

3. Cross-worker checkpoint (SharedWorker)

3.1. Architecture

The SharedWorker holds the checkpoint store. Any worker can save or load a checkpoint by posting a message and awaiting the reply.

  Worker 0                SharedWorker pthread              Worker 1
  ────────                ────────────────────              ────────
  req → saveCheckpoint()  checkpoints Map                  req → loadCheckpoint()
     postMessage('save')  ─────────────                       postMessage('load')
                          │ name → snap │  ←── snapshots       ← postMessage(snap)
                          │   (JS obj) │      are JS objs
                          │            │      serialised
                          └────────────┘      via structured clone
NginxSnapshot is an opaque C-backed object — it cannot be serialised via structured clone. The SharedWorker checkpoint stores the raw property values (plain JS objects), not the NginxSnapshot handle itself.

3.2. SharedWorker checkpoint store

// cpstore.js  (SharedWorker)

const store = new Map();   // name → plain JS object with property values

onmessage = (msg) => {
    const { type, name, data } = msg.data;

    if (type === 'save') {
        store.set(name, data);
        postMessage({ type: 'saved', name });

    } else if (type === 'load') {
        const data = store.get(name);
        postMessage({ type: 'loaded', name, data: data || null });

    } else if (type === 'list') {
        postMessage({ type: 'list', names: [...store.keys()] });
    }
};

3.3. Worker helpers: serialise and apply a checkpoint

Because NginxSnapshot is opaque, checkpoints are stored as plain objects:

// js_source: cross_worker_checkpoint.js

const cpStore = new SharedWorker('cpstore.js');

// Serialise the current location config to a plain object
function captureToPlainObject(req) {
    const loc = req.location;
    return {
        root:             loc.root,
        sendfile:         loc.sendfile,
        keepaliveTimeout: loc.keepaliveTimeout,
        defaultType:      loc.defaultType,
        proxy: loc.proxy ? {
            readTimeout:    loc.proxy.readTimeout,
            connectTimeout: loc.proxy.connectTimeout,
            buffering:      loc.proxy.buffering,
        } : undefined,
    };
}

// Apply a plain-object checkpoint back to the location
function applyFromPlainObject(req, data) {
    if (!data) { return; }
    if (data.root             !== undefined) { req.location.root             = data.root; }
    if (data.sendfile         !== undefined) { req.location.sendfile         = data.sendfile; }
    if (data.keepaliveTimeout !== undefined) { req.location.keepaliveTimeout = data.keepaliveTimeout; }
    if (data.defaultType      !== undefined) { req.location.defaultType      = data.defaultType; }
    if (data.proxy?.readTimeout    !== undefined) { req.location.proxy.readTimeout    = data.proxy.readTimeout; }
    if (data.proxy?.connectTimeout !== undefined) { req.location.proxy.connectTimeout = data.proxy.connectTimeout; }
    if (data.proxy?.buffering      !== undefined) { req.location.proxy.buffering      = data.proxy.buffering; }
}

// Save current location config as a named checkpoint in the SharedWorker
async function saveCheckpoint(req, name) {
    const data = captureToPlainObject(req);
    return new Promise(resolve => {
        cpStore.onmessage = (msg) => {
            if (msg.data.type === 'saved' && msg.data.name === name) { resolve(); }
        };
        cpStore.postMessage({ type: 'save', name, data });
    });
}

// Load a named checkpoint from the SharedWorker and apply it to this worker
async function loadCheckpoint(req, name) {
    return new Promise((resolve, reject) => {
        cpStore.onmessage = (msg) => {
            if (msg.data.type === 'loaded' && msg.data.name === name) {
                if (!msg.data.data) { reject(new Error('checkpoint not found: ' + name)); return; }
                applyFromPlainObject(req, msg.data.data);
                resolve();
            }
        };
        cpStore.postMessage({ type: 'load', name });
    });
}

3.4. Example: save and restore via HTTP endpoints

loc.handler = async (req) => {
    const name = req.getVar('arg_name') || 'default';

    if (req.uri === '/admin/checkpoint/save') {
        await saveCheckpoint(req, name);
        req.json({ saved: name });

    } else if (req.uri === '/admin/checkpoint/restore') {
        try {
            await loadCheckpoint(req, name);
            req.json({ restored: name });
        } catch (e) {
            req.respond(404, {}, e.message);
        }

    } else if (req.uri === '/admin/checkpoint/list') {
        const names = await new Promise(resolve => {
            cpStore.onmessage = (msg) => {
                if (msg.data.type === 'list') { resolve(msg.data.names); }
            };
            cpStore.postMessage({ type: 'list' });
        });
        req.json({ checkpoints: names });
    }
};

4. Atomic checkpoint restore with worker suspension

4.1. Why suspension matters for checkpoints

snap.restore() and applyFromPlainObject() write fields one at a time through the normal setter path. Between any two writes the event loop can dispatch a concurrent request on the same worker that reads a partially-restored state.

Wrapping the restore in a suspension window makes the entire restore appear instantaneous to other requests.

4.2. Single-worker atomic restore

loc.handler = (req) => {
    const name = req.getVar('arg_name') || 'default';
    const snap = loadCheckpoint(name);     // module-level checkpoint Map

    if (!snap) {
        req.respond(404, {}, 'checkpoint not found: ' + name);
        return;
    }

    nginx.suspendAcceptance();             // no new requests on this worker
    snap.restore();                        // all fields written before resume
    nginx.resumeAcceptance();

    req.json({ restored: name });
};

4.3. Cross-worker atomic restore

Combine suspendAllWorkers() with the SharedWorker broadcast so that all workers restore consistently before any new request is accepted anywhere.

loc.handler = async (req) => {
    const name = req.getVar('arg_name') || 'default';

    // Load checkpoint data from SharedWorker store
    let data;
    try {
        data = await loadSharedCheckpoint(name);   // defined in cross-worker section
    } catch (e) {
        req.respond(404, {}, e.message);
        return;
    }

    await nginx.suspendAllWorkers();

    try {
        // Apply on this worker
        applyFromPlainObject(req, data);

        // Broadcast restore to all other workers
        cfgWorker.postMessage({ type: 'restore', name, data });

        req.json({ restored: name });

    } catch (e) {
        req.respond(500, {}, 'restore failed: ' + e.message);
    } finally {
        await nginx.resumeAllWorkers();
    }
};

Add a handler in cfgworker.js for the restore message type:

// inside cfgworker.js onmessage:
} else if (type === 'restore') {
    // Fan out the checkpoint data to all workers
    postMessage({ type: 'apply-checkpoint', data });
}

And in the main worker script:

cfgWorker.onmessage = (msg) => {
    if (msg.data.type === 'apply-checkpoint') {
        // This worker receives the fan-out; no suspension needed here —
        // the initiating worker holds suspendAllWorkers() until after the
        // broadcast, so all workers are still suspended when this runs.
        applyFromPlainObject(null, msg.data.data);   // null req = global write
    }
};

4.4. Auto-checkpoint with atomic apply

Validate before suspending, then atomically apply + checkpoint inside the suspension window so that the "new config" and the "last-known-good checkpoint" are always consistent:

loc.handler = async (req) => {
    const cfg = JSON.parse(await req.readBody());

    // Validate BEFORE suspending — keep the suspension window short
    const valid = await validateConfig(cfg);
    if (!valid) {
        req.respond(400, {}, 'invalid config');
        return;
    }

    await nginx.suspendAllWorkers();

    try {
        const rollback = req.location.snapshot();   // rollback point

        // Apply
        req.location.root = cfg.root;
        // … more fields …

        // Promote to last-known-good checkpoint
        const lkg = req.location.snapshot();
        saveCheckpoint('last-known-good', lkg);

        // Broadcast
        cfgWorker.postMessage({ type: 'set', payload: cfg });

        req.json({ applied: true });

    } catch (e) {
        // rollback is defined only if suspension succeeded
        req.respond(500, {}, e.message);

    } finally {
        await nginx.resumeAllWorkers();
    }
};

4.5. Flow diagram: checkpoint restore lifecycle

  Worker 0 (handler):              All workers:

  await suspendAllWorkers()
  ─────────────────────────────►   all suspended (no new requests anywhere)

  applyFromPlainObject(req, data)  ← writes to this worker's structs

  cfgWorker.postMessage(restore) ──► SharedWorker fan-out
                                       │
                                       ├──► Worker 1: applyFromPlainObject
                                       └──► Worker 2: applyFromPlainObject

  await resumeAllWorkers()
  ─────────────────────────────►   all resume (queued connections accepted)

  All workers now have identical config matching the checkpoint.

5. Persistent checkpoint (survives nginx reload)

5.1. The problem

When nginx reloads (nginx -s reload) or restarts, all workers and the SharedWorker are replaced. In-memory checkpoints are lost.

To survive a reload, checkpoints must be externalised — written to a file or database before nginx shuts down, and re-read at the next startup.

5.2. Pattern: write checkpoint to file, read back via js_preprocess

js_preprocess runs during config parse and can read files. A checkpoint can be written to a JSON file by a request handler and read back at next startup.

// js_source: persistent_checkpoint.js
// (uses Worker for async file I/O — not shown in detail here)

async function persistCheckpoint(name, data) {
    const path = '/var/run/nginx/checkpoints/' + name + '.json';
    // Write via a Worker that can do synchronous file I/O
    const w = new Worker('filewriter.js');
    w.postMessage({ path, data: JSON.stringify(data) });
    await new Promise(resolve => { w.onmessage = resolve; });
}
// js_preprocess: read_checkpoint.js
// Runs during config parse; injects config text based on saved checkpoint.

const fs   = require('std');
const path = '/var/run/nginx/checkpoints/startup.json';

try {
    const raw  = fs.open(path, 'r').readAsString();
    const data = JSON.parse(raw);

    // Generate nginx config fragment from checkpoint data
    config.write('location /from-checkpoint {\n');
    config.write('    root ' + data.root + ';\n');
    config.write('}\n');
} catch (e) {
    // No checkpoint file — use defaults from nginx.conf
}

5.3. Flow diagram: full persistent checkpoint lifecycle

  Nginx starts / reloads
       │
       ▼
  js_preprocess runs
       │  reads /var/run/nginx/checkpoints/startup.json
       │  injects config text (if file exists)
       ▼
  nginx.conf parsed → workers fork
       │
       │   (nginx is running)
       ▼
  Request: POST /admin/checkpoint?name=stable
       │  captures current config → plain JS object
       │  writes to /var/run/nginx/checkpoints/stable.json (via Worker)
       │
  Request: POST /admin/restore?name=stable
       │  reads from SharedWorker store OR file
       │  applies to this worker (write_mode='global')
       │  broadcasts to other workers via SharedWorker fan-out
       │
  nginx -s reload
       │
       ▼
  js_preprocess reads stable.json → injects into new config
  Workers fork with checkpoint baked in

6. Checkpoint-based A/B testing with controlled rollout

Checkpoints can represent named config states (e.g. "control", "experiment-v1", "experiment-v2"). Traffic routing between states is controlled per-request.

// js_source: ab_checkpoint.js

const cpStore = new SharedWorker('cpstore.js');

// Pre-load both configs at init time
// (assumes they were previously saved as named checkpoints)

loc.handler = async (req) => {
    // Route by cookie or percentage
    const bucket = req.getVar('cookie_ab_bucket');
    const target = (bucket === 'experiment') ? 'experiment-v1' : 'control';

    // Apply per-request (local write_mode — does not affect other requests)
    req.location.setWriteMode('local');
    req.location.setReadMode('local');

    try {
        await loadCheckpoint(req, target);    // applies to local snapshot
    } catch (e) {
        // Fall back to global (control) config — no local mutation applied
    }

    req.sendfile('/index.html');
    // local snapshot is automatically discarded at request end
};

7. Caveats

7.1. NginxSnapshot is not serialisable

NginxSnapshot handles are C-backed opaque objects. They cannot be passed to postMessage or serialised via JSON.stringify. Cross-worker and persistent checkpoints must store plain JS objects (see captureToPlainObject above) and apply them field-by-field using setters.

7.2. Checkpoint staleness

A checkpoint captures a point-in-time view. If nginx’s upstream peer list changes (peers added or removed), a stale checkpoint may attempt to set weights on non-existent peers. restore() (and applyFromPlainObject) are best-effort and silently ignore such errors.

7.3. Concurrent checkpoint writers

Module-level variables and SharedWorker state are not automatically mutex- protected. If two requests write checkpoints concurrently, the last writer wins. For critical checkpoint writes, use a flag guard similar to mutationInProgress from the for single worker guide.

7.4. Checkpoint and nginx reload

Files written by persistCheckpoint during a request are not guaranteed to be flushed before nginx -s reload starts the new worker processes. If the reload is triggered immediately after a checkpoint write, the new js_preprocess run may read a partial or previous file. Use atomic rename-from-temp to mitigate:

// In filewriter.js Worker:
// 1. Write to /var/run/nginx/checkpoints/.stable.json.tmp
// 2. Atomically rename to /var/run/nginx/checkpoints/stable.json
