 just a question: suppose javascript in nginx worker misbehaved (in sence of memory comsumption or cpu consumption). The question is: how we can safely re-run nginx worker then?

● This is a good question that touches both nginx architecture and our specific design.

  Good news: our COW fork design already handles this cleanly.

  When a worker is killed, the OS reclaims all its private COW pages — including all JS heap allocations made during request handling. The master's original JSRuntime is completely unaffected.
  Forking a new worker from the master gives a fresh, clean JS state. So the "kill and refork" path nginx already uses is safe.

  Two remaining problems to address proactively:

  1. Memory runaway — a JS request handler leaks or allocates excessively.

  Solution: call JS_SetMemoryLimit(w->rt, limit) in init_process (per-worker, after fork). When the limit is exceeded, QuickJS throws an OOM exception rather than crashing. The handler catches it and
   returns a 500. Worker stays alive and continues serving other requests.

  2. CPU runaway — infinite loop or pathologically slow JS.

  Solution: JS_SetInterruptHandler(rt, handler, opaque). QuickJS polls this callback periodically during bytecode execution. The handler checks a flag set by an ngx_event_t timer; if the flag is set,
   it returns 1 to abort execution with an exception. Again, handler catches it, returns 503, worker survives.

  If the worker is truly unrecoverable (handler doesn't catch, worker crashes or hangs):
  - nginx master already monitors workers via waitpid and a heartbeat check
  - worker_shutdown_timeout forces SIGKILL if a worker ignores SIGQUIT
  - Master reforits a clean worker automatically

  Summary of what we should add:

  ┌─────────────────────────┬────────────────────────────────┬──────────────────────────────────┐
  │         Problem         │           Mechanism            │              Where               │
  ├─────────────────────────┼────────────────────────────────┼──────────────────────────────────┤
  │ Memory leak/overuse     │ JS_SetMemoryLimit              │ init_process                     │
  ├─────────────────────────┼────────────────────────────────┼──────────────────────────────────┤
  │ Infinite loop / slow JS │ JS_SetInterruptHandler + timer │ init_process + per-request timer │
  ├─────────────────────────┼────────────────────────────────┼──────────────────────────────────┤
  │ Worker crash/hang       │ nginx built-in (already works) │ master process                   │
  └─────────────────────────┴────────────────────────────────┴──────────────────────────────────┘

  The memory limit is the most important one to add — it's a one-liner and prevents a single bad request from exhausting system memory before nginx's process-level monitoring kicks in.

● Done. Committed as d8489ad93.

  Summary of what was implemented:

  - nginx.workerMemoryLimit — a plain writable JS property (number, default 0)
  - Set it from js_source before workers start:
  nginx.workerMemoryLimit = 64 * 1024 * 1024;  // 64 MB headroom
  - After all scripts run in init_conf, the value is read and cached in jcf->worker_memory_limit
  - In init_process after fork, JS_ComputeMemoryUsage measures the inherited baseline, then JS_SetMemoryLimit(baseline + cap) is applied — so the cap only limits new allocations by request handlers,
  not the shared COM objects
  - On OOM, QuickJS throws an exception; handlers can catch it and return a clean 503; the worker stays alive

  2. clock_gettime(CLOCK_MONOTONIC) is called inside the interrupt handler — it reads wall time directly without needing the nginx event loop to be running, so it fires even inside a tight for(;;)
