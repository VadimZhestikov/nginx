❯ just a question: at what point of master worker script loaded by js_include is executed?

● Searched for 1 pattern, read 1 file (ctrl+o to expand)

● js_include scripts are executed in init_conf — the NGINX lifecycle hook that runs after ngx_conf_parse() completes but before any worker processes are forked.

  The exact sequence:

  1. ngx_conf_parse() runs — all server {}, location {}, upstream {} blocks are parsed, C config structs fully populated. js_include directives just record file paths into jcf->includes[], nothing is
   executed yet.
  2. init_conf fires (NGINX core module hook, called once in the master):
    - Creates JSRuntime + JSContext
    - Installs the COM namespace (nginx.*)
    - Evaluates each js_include file in declaration order via JS_Eval
  3. Workers are forked — they inherit the already-evaluated runtime/context via COW. No re-evaluation at worker start.

  So the scripts run once, in the master, after the full config is parsed and before any request is served.

❯ please suggest better name for js_include directive

● A few candidates, each with a different emphasis:

  ┌──────────────┬─────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │     Name     │                                                  Rationale                                                  │
  ├──────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ js_load      │ Short, verb-only, implies "load this file at startup". No confusion with nginx's include directive.         │
  ├──────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ js_script    │ Noun form — "this is the JS script for this server". Matches how people think of a single entry-point file. │
  ├──────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ js_bootstrap │ Emphasises that it runs once before workers start, setting up the environment. A bit long.                  │
  ├──────────────┼─────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ js_run       │ Extremely terse. Fine, but could imply it runs on every request.                                            │
  └──────────────┴─────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  Recommendation: js_load

  - Nginx's own include directive means "splice another config file here", so js_include creates a false analogy.
  - js_load matches the mental model: load a JS file into the master runtime at startup. It's how browser <script src> loading is commonly described in C API docs too (JS_LoadFile, etc.).
  - It pairs cleanly with the existing directives: js_preprocess (parse-time), js_init_http (post-parse http-block), js_load (post-parse master runtime).

❯  just a question: at what point of master worker script loaded by js_inint_http is executed?

● Searched for 1 pattern, read 1 file (ctrl+o to expand)

● js_init_http fires immediately when the directive line is encountered during ngx_conf_parse() — i.e. mid-parse, while the http {} block is still being read.

  The exact sequence:

  1. ngx_conf_parse() starts processing nginx.conf
  2. It enters the http {} block, parses server {} blocks one by one
  3. When it hits the js_init_http /path.js; line, the handler is called right there and then:
    - Creates a short-lived JSRuntime + JSContext (independent of the js_include runtime)
    - Runs the script synchronously
    - Script can call config.write(text) → feeds text back into ngx_conf_parse() recursively (same as js_preprocess)
    - Script can read nginx.http.servers[] — but only servers parsed before this line
  4. Runtime is freed, ngx_conf_parse() resumes with the next line
  5. Servers added via config.write() are parsed in-place and go through the full merge / init_locations / optimize_servers treatment

  So compared to js_include:

  ┌───────────────────────┬────────────────────────────────┬───────────────────────────────────────┐
  │                       │          js_init_http          │              js_include               │
  ├───────────────────────┼────────────────────────────────┼───────────────────────────────────────┤
  │ When                  │ Mid-parse, inline in http {}   │ After full ngx_conf_parse() completes │
  ├───────────────────────┼────────────────────────────────┼───────────────────────────────────────┤
  │ Runtime lifetime      │ Short-lived, freed immediately │ Lives until master exits              │
  ├───────────────────────┼────────────────────────────────┼───────────────────────────────────────┤
  │ Workers see it        │ No (runtime gone)              │ Yes (forked from it)                  │
  ├───────────────────────┼────────────────────────────────┼───────────────────────────────────────┤
  │ Can inject config     │ Yes (config.write)             │ No                                    │
  ├───────────────────────┼────────────────────────────────┼───────────────────────────────────────┤
  │ Sees full nginx.* COM │ No                             │ Yes                                   │
  └───────────────────────┴────────────────────────────────┴───────────────────────────────────────┘
