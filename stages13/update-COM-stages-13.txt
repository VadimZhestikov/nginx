 just a question: can we update COM, so it will contain all directives and all merging results?

● Theoretically yes, practically it's a large amount of manual glue code. Here's why:

  What's available after merge

  By the time our COM runs (init_conf, after ngx_http_merge_servers), every location's loc_conf[module_index] array holds the fully-merged config for every module. The data is all there.

  Why there's no generic path

  nginx has no runtime reflection. The directive table (ngx_command_t[]) has setter function pointers (ngx_conf_set_str_slot, ngx_conf_set_num_slot, etc.) and struct offsets, but no getter
  counterpart and no type tag you can read back safely. To expose a directive value you have to:

  1. Know which module owns it (module->ctx_index)
  2. Cast loc_conf[idx] to the right C struct
  3. Know the field name and type
  4. Write a JS property getter for it

  That's manual binding — one per directive, times ~70 modules.

  What's feasible in practice

  ┌───────────────────────────────┬─────────────────────────────────┬─────────────────────────────────────────────────────────────────────────────────────┐
  │             Scope             │             Effort              │                                        Value                                        │
  ├───────────────────────────────┼─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────┤
  │ Full ngx_http_core_loc_conf_t │ Medium — one struct, ~40 fields │ High — root, alias, index, try_files, limit_rate, keepalive_timeout, sendfile, etc. │
  ├───────────────────────────────┼─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────┤
  │ ngx_http_proxy_loc_conf_t     │ Medium                          │ High — proxy_pass, timeouts, buffering                                              │
  ├───────────────────────────────┼─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────┤
  │ ngx_http_gzip_conf_t          │ Low                             │ Medium                                                                              │
  ├───────────────────────────────┼─────────────────────────────────┼─────────────────────────────────────────────────────────────────────────────────────┤
  │ SSL, cache, auth, …           │ High (per module)               │ Diminishing                                                                         │
  └───────────────────────────────┴─────────────────────────────────┴─────────────────────────────────────────────────────────────────────────────────────┘

  The core loc conf alone covers the 80% case and is a single well-known struct.

  One real obstacle: post-merge mutation

  If you expose merged values as writable (like current root, weight etc.) you also need to re-trigger whatever nginx normally does after a setter — e.g. rebuilding regex location trees, re-sorting
  try_files. Some directives are safe to mutate live, others are not. Read-only exposure is much safer and still very useful.

  Bottom line: expanding COM to cover all of ngx_http_core_loc_conf_t and a few high-value module structs is realistic. Covering every directive from every module is technically possible but would be
   a large ongoing maintenance surface — essentially reimplementing nginx's config layer in JS bindings.

● Here is the full staged plan, highest value first:

  ---
  Stage 1 — ngx_http_core_loc_conf_t read-only (highest value)

  The single most useful expansion. One well-known struct, covers the most commonly inspected/generated directives.

  Fields to expose on each location object:

  alias            root / alias distinction
  index            array of index files
  try_files        array of paths + fallback
  error_page       array of {codes[], uri}
  limit_rate       bytes/s (0 = unlimited)
  limit_rate_after bytes before throttle kicks in
  sendfile         bool
  tcp_nopush       bool
  tcp_nodelay      bool
  keepalive_timeout  ms
  keepalive_requests number
  client_max_body_size  bytes
  client_body_timeout   ms
  send_timeout          ms
  autoindex        bool
  internal         bool (internal-only location)
  default_type     string
  charset          string

  Writability: root, alias, default_type, limit_rate are safe to mutate live. try_files, index, error_page are array-backed and need care (rebuild after write). internal is safe.
  sendfile/tcp_nopush/tcp_nodelay are safe.

  ---
  Cross-cutting concerns for all stages

  Type representation
  - nginx ngx_msec_t → JS number (milliseconds)
  - nginx size_t/off_t → JS number (bytes)
  - nginx ngx_flag_t → JS boolean
  - nginx ngx_str_t → JS string (or null if unset)
  - nginx arrays → JS arrays

  Writability rules
  - Scalar fields (string, number, bool): safe to write directly
  - Array fields (index, try_files, add_header): need a setter that reallocates the nginx array
  - Compiled structures (rewrite bytecode, regex): read-only until we add a recompile step
  - SSL cert/key: writable but requires SSL_CTX_use_certificate_file re-call after write

  Naming convention
  All new fields use camelCase matching the JS convention already established (maxFails, remoteAddr), mapping from nginx's snake_case (max_fails, remote_addr).
