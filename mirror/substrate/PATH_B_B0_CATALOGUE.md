# Path B — sub-phase B.0: catalogue of F-Stack's nginx patch (vs stock 1.28.0)

Generated by diffing F-Stack's `app/nginx-1.28.0` against pristine nginx 1.28.0
(throwaway git repo, in the KVM guest). The raw patch lives at
`~/fstack_vs_stock_1.28.patch` on the guest (3243 lines) — **not** committed here
(it's F-Stack's own code). This file is our *analysis*: what changed, why, and how
it maps onto pilgrim's `ngx_substrate` seam and the B.1+ plan.

## Totals

**53 files, +1895 / −60.** Two new files carry the core; the rest are small hooks.

## Buckets (grouped by purpose)

### A. New integration core — 2 files, ~1016 lines (the heart)
| file | +L | what |
|---|---|---|
| `src/event/modules/ngx_ff_module.c` | 561 | the **syscall shim**: `is_fstack_fd()` + wrappers for socket/accept/bind/listen/recv/send/close/setsockopt/ioctl/epoll_* that dispatch to `ff_*` for F-Stack fds else the real syscall; `ff_mod_init()` |
| `src/event/modules/ngx_ff_host_event_module.c` | 455 | a **second event module** for **kernel** fds (channel/timers/control), running beside F-Stack's epoll for data-plane fds |

Note: stock `ngx_epoll_module.c` is **not** patched — the shim intercepts
`epoll_create/ctl/wait`, so the stock epoll module transparently drives F-Stack.

### B. Loop inversion + per-worker init — `ngx_process_cycle.c` (+266), `.h` (+6)
`ff_mod_init(fstack_conf, worker_idx, proc_type)` per worker, then
`ff_run(ngx_worker_process_cycle_loop, cycle)` — **F-Stack owns the worker loop**;
nginx's cycle body is its per-tick callback. This is the single most invasive core
change and the one the seam can't hide.

### C. Build-system integration — `auto/{options,os/linux,sources,unix}` (+68)
`--with-ff_module`, link `libfstack` + DPDK, register the two new event modules.

### D. `fstack_conf` config directive — ~8 files (+~70)
`ngx_cycle.h`, `ngx_config.h`, `ngx_module.h`, and the `*_core_module.c` for
http/stream/mail each register the `fstack_conf` directive (path to `config.ini`).

### E. I/O routing — os/unix thin edits (~34 lines across 7 files)
`ngx_recv.c`(6) `ngx_send.c`(2) `ngx_udp_recv.c`(2) `ngx_readv_chain.c`(6)
`ngx_writev_chain.c`(2) `ngx_udp_sendmsg_chain.c`(14) `ngx_channel.c`(8).
**→ This bucket is exactly what pilgrim's `ngx_substrate` seam already abstracts**
(2.1a bound `c->recv/send/*_chain`; 2.1b `close/shutdown`). F-Stack edits these
files inline; we route them through the vtable. The seam **subsumes bucket E** — a
concrete win for the "clean seam" thesis.

### F. Connection / accept / connect — `ngx_connection.c`(+81), `ngx_event_accept.c`(+10), `ngx_event_connect.c`(+30/.h+4)
Listener creation on the F-Stack stack, accept returning F-Stack fds, upstream
connect choosing a stack. **→ These are the deferred-2.1b pieces** (accept,
listener, per-connection substrate) — the seam's planned growth, not yet built.

### G. Event glue — `ngx_event.c`(+64), `ngx_event.h`(+56), select/kqueue(+36)
Wiring the two event modules + flags.

### H. Upstream / proxy / resolver over F-Stack — `http_proxy`(+29), `stream_proxy`(+29), `upstream`(+4), `resolver`(+8), `mail_proxy`(+4)
Making outbound/proxy connections and DNS use the F-Stack stack. **→ Pilgrim's
`r.fetch` (mirror.kv) lands here** — outbound over which stack is a real choice.

### I. Protocol misc — `http_request`(4), `http/v2`(2), `quic_output`(8), `ngx_http.c`(4), stream/mail `.c/.h`(+~16)
Small touch-ups.

## What this tells us for Path B

1. **The seam already covers bucket E** (per-connection I/O) — proof the
   `ngx_substrate` abstraction is on the right axis. F-Stack needed inline edits
   to 7 os/unix files; pilgrim needs none there.
2. **Buckets A + B + C + D are the unavoidable "port" work** (shim, loop
   inversion, build, `fstack_conf`) — these do NOT fit the vtable and must be
   ported largely as-is in **B.1**. ~1350 lines, 2 new files + `ngx_process_cycle.c`
   + build + directive.
3. **Buckets F + G** are the deferred-2.1b growth (accept/listener/event module +
   per-connection substrate tag) — the **B.4 refactor** turns F-Stack's inline
   edits here into `ngx_substrate` backend ops.
4. **Bucket H** is future (fetch/upstream-over-DPDK), out of the functional-proof
   scope.
5. **1.28 → 1.29 drift risk (B.1):** the patch targets nginx 1.28; pilgrim is
   1.29. The high-churn files to re-base carefully: `ngx_process_cycle.c`,
   `ngx_event.c/.h`, `ngx_connection.c`, `auto/*`. The 2 new files are
   version-independent (they call `ff_*` + libc, not nginx internals heavily),
   so they port cleanly; the *hooks* into core need re-basing.

## B.1 entry criteria (what to do first, when Path B is opened)

- Re-base buckets A–D onto pilgrim 1.29 (start with the JS module **disabled** to
  isolate F-Stack breakage from pilgrim breakage).
- Keep bucket E as-is on pilgrim (already via `ngx_substrate`) — do **not** re-add
  F-Stack's inline os/unix edits; instead point `ngx_substrate->io` at `ff_*` for
  F-Stack fds (needs the per-connection substrate tag from B.4, or a temporary
  `is_fstack_fd` check in the POSIX backend).
- Defer buckets F/G/H beyond a first "serves one static response over DPDK".
