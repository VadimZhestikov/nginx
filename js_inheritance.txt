● Now I have a complete picture. Here's the situation:

  - Master (init_conf): creates JSRuntime, installs COM, evals scripts (config
  mutations), then discards JS state
  - Workers (init_process): each creates a new independent JSRuntime and
  re-reads + re-parses all source files from disk

  The goal is to have workers inherit pre-compiled bytecode from the master
  instead of re-parsing source files. The mechanism: use QuickJS's
  JS_Eval(COMPILE_ONLY) + JS_WriteObject in master to serialize bytecode into
  cycle->pool, then workers use JS_ReadObject + JS_EvalFunction on the
  pool-inherited buffers.

  This is safe because cycle->pool memory is inherited via fork()
  (copy-on-write), and the bytecode buffers are valid read-only data from the
  worker's perspective.

  ---
  What changed

  nginx/src/js/ngx_js.h

  Added ngx_js_bytecode_t struct and a bytecodes array field to ngx_js_conf_t:
  typedef struct {
      uint8_t  *data;
      size_t    size;
  } ngx_js_bytecode_t;

  nginx/src/js/ngx_js_module.c

  create_conf — initialises the new bytecodes array alongside includes.

  init_conf (master) — after executing each script for config mutations, runs a
  second pass with JS_EVAL_FLAG_COMPILE_ONLY to produce a compiled function
  object, serialises it to a byte buffer via JS_WriteObject, copies the buffer
  into cycle->pool, and frees the QuickJS-owned copy. One ngx_js_bytecode_t
  entry is pushed per include file.

  init_process (workers) — no longer reads source files or parses JS. Instead it
   iterates over jcf->bytecodes, deserialises each with
  JS_ReadObject(JS_READ_OBJ_BYTECODE), and executes it with JS_EvalFunction. The
   bytecode buffers live in cycle->pool which is inherited by workers via fork()
   (copy-on-write) — no I/O, no parsing.

  Why this is the right approach

  Workers cannot simply reuse the master's JSRuntime pointer after fork() —
  QuickJS runtimes own heap state (GC roots, class registries, atom tables) that
   must be private per-process. The bytecode path is the canonical way QuickJS
  itself handles pre-compilation (qjsc): parse once, execute N times. Each
  worker gets a fresh runtime with its own GC, but skips the parse step
  entirely.

● Clean and done. Here's what changed and why it works:

  ---
  What changed

  ngx_js.h

  Removed ngx_js_bytecode_t and the bytecodes array field — no longer needed.

  ngx_js_module.c

  init_conf — unchanged in substance; the master still creates the runtime,
  installs COM (which registers all classes including NginxRequest via
  ngx_js_http_register_classes), and evaluates all scripts. The full JS
  environment lives in jcf->rt / jcf->ctx.

  init_process — reduced to 4 lines of actual logic:
  w->rt  = jcf->rt;
  w->ctx = jcf->ctx;
  No JS_NewRuntime, no JS_NewContext, no ngx_js_com_init, no script evaluation,
  no file I/O.

  exit_process — unchanged; frees the worker's private copy of the
  runtime/context.

  exit_master — unchanged; frees the master's original. No conflict because
  these are separate processes after fork().

  ---
  Why this is safe

  After fork(), each worker has its own private copy-on-write image of the
  master's address space. jcf->rt and jcf->ctx are usable QuickJS objects in
  each worker process because:

  1. QuickJS is single-threaded — no internal mutexes that could be held at fork
   time
  2. All classes already registered — ngx_js_http_register_classes ran during
  init_conf, including NginxRequest
  3. All handler functions already in global scope — JS_Eval ran before fork
  4. COM pointers are valid — cycle and its pool data are in the inherited
  address space
  5. No shared mutable state — each process modifies only its own copy (COW),
  and exit_process/exit_master each free their own copy independently

  ngx_js.h — ngx_js_loc_conf_t now holds handler_idx ngx_int_t instead of
  handler ngx_str_t.

  ngx_js_com_http.c — The setter type-checks that the value is actually a
  function (JS_ThrowTypeError otherwise), then appends it to a __ngx_handlers__
  array on the global object and stores its index. The array keeps the function
  GC-reachable — this is critical for anonymous/arrow functions that have no
  other JS-side reference. A getter was also added so location.handler returns
  the stored function.

  ngx_js_http_module.c — ngx_js_content_handler retrieves

  create_loc_conf initialises handler_idx = -1; merge_loc_conf uses -1 as the
  unset sentinel.

  helloHandler)) or inline arrow functions (set('/missing/', req => { throw ...
