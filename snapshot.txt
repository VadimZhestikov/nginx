● This is a fundamental architectural question. Let me work through exactly what
   nginx does and where the current implementation stands.

  How modules access config today

  After NGX_HTTP_FIND_CONFIG_PHASE, nginx sets:
  r->loc_conf = clcf->loc_conf;   /* direct pointer to the shared array */

  Every subsequent module access — phase handlers AND filters — does:
  clcf = ngx_http_get_module_loc_conf(r, ngx_http_core_module);
  // expands to: r->loc_conf[ngx_http_core_module.ctx_index]
  // which is: the original shared ngx_http_core_loc_conf_t *

  When our JS setter writes clcf->keepalive_timeout = newVal, it writes to that
  shared struct. There is no per-request copy. r->loc_conf gives the in-progress
   request the same pointer it would give a brand-new request.

  Concrete danger points

  1. Cross-phase, same request:
  client_max_body_size is checked during body reading (preaccess phase). If a JS
   content handler raises it, the check already passed and it's harmless. But
  keepalive_timeout is read at ngx_http_finalize_request — after the content
  phase — so a change in the content handler does affect the current request's
  keepalive decision.

  2. Filters during chunked/streaming responses:
  Filters re-read r->loc_conf[m.ctx_index] on every invocation. For a streaming
  response, the filter chain fires multiple times across multiple event-loop
  ticks. A JS-driven config change between two chunks (e.g. changing gzip
  settings) would be seen mid-stream by the gzip filter — which has already
  written a gzip stream header. That would corrupt the response.

  3. Async handlers (nginx.setTimeout):
  The request is suspended, other JS code runs, changes config, request resumes.
   The resumed request's filters see the new config. This is the highest-risk
  scenario.

  What would actually guarantee isolation

  The only proper fix is a per-request snapshot of the loc_conf structs copied
  into r->pool at the end of FIND_CONFIG_PHASE. In
  ngx_http_core_find_config_phase, after the location is matched:

  /* snapshot ngx_http_core_loc_conf_t for this request */
  ngx_http_core_loc_conf_t *snap = ngx_palloc(r->pool, sizeof(*snap));
  *snap = *clcf;                           /* shallow copy of the struct */

  void **lc = ngx_palloc(r->pool, nmodules * sizeof(void *));
  ngx_memcpy(lc, clcf->loc_conf, nmodules * sizeof(void *));
  lc[ngx_http_core_module.ctx_index] = snap;
  snap->loc_conf = lc;
  r->loc_conf = lc;

  This gives each request its own immutable snapshot of the core config. JS
  changes only affect the original clcf; new requests get a fresh snapshot of
  the updated struct.

  Limitation: this only snapshots ngx_http_core_loc_conf_t. Other modules'
  loc_conf structs (gzip, proxy, sub_filter, etc.) remain shared. A full
  per-module snapshot would require knowing each module's struct size, which
  isn't available through the module API.

  Practical scope: most of the values we expose as writable live in
  ngx_http_core_loc_conf_t. The sub-module wrappers (NginxGzip, NginxProxy,
  etc.) expose writable fields in their own structs, which the snapshot above
  would not protect.

  Bottom line

  ┌───────────────────────────────┬─────────────────────────────────────────┐
  │           Scenario            │             Current status              │
  ├───────────────────────────────┼─────────────────────────────────────────┤

● The row 4 problem in detail

  Streaming body filters run once per chunk, across multiple event-loop ticks.
  Between chunks, the event loop returns to accept other work (including JS
  callbacks). The sub_filter body filter, for example, re-reads its config on
  every chunk to know what pattern to match:

  chunk 1 arrives → sub_filter reads slcf->match = "foo"   → replaces "foo"
    [event loop tick — JS setTimeout fires, sets slcf->match = "bar"]
  chunk 2 arrives → sub_filter reads slcf->match = "bar"   → mid-stream
  inconsistency

  For gzip specifically it's even worse: the gzip body filter maintains a
  deflate stream in per-request ctx, but some gzip options (buffer size, level)
  are re-read per chunk. Changing them mid-deflate-stream is undefined behavior.

  ---
  The unified approach that covers all four rows

  The key insight: JS only runs inside our content handler (or timer callbacks).
   No other phase calls JS. So config can only be mutated at one well-defined
  point in the request lifecycle.

  Take a per-request snapshot of all writable loc_conf structs at the start of 
  ngx_js_content_handler, before calling the JS function:

  ngx_int_t
  ngx_js_content_handler(ngx_http_request_t *r)
  {
      ngx_js_snapshot_loc_conf(r);   /* freeze config for this request */
      /* ... call JS ... */
  }

  After ngx_js_snapshot_loc_conf:
  - r->loc_conf → per-request copy of the pointer array (in r->pool)
  - r->loc_conf[core_module.ctx_index] → per-request copy of
  ngx_http_core_loc_conf_t
  - r->loc_conf[gzip_module.ctx_index] → per-request copy of
  ngx_http_gzip_conf_t
  - r->loc_conf[sub_filter_module.ctx_index] → per-request copy of
  ngx_http_sub_loc_conf_t
  - … (each module we expose as writable in the COM)

  JS then runs and mutates the originals (shared structs). The in-progress
  request's r->loc_conf[m.ctx_index] already points to the snapshots, so:

  ┌───────────────────────────────────────┬─────────────────────────────────┐
  │           Who reads config            │          What they get          │
  ├───────────────────────────────────────┼─────────────────────────────────┤
  │ Current request's filters             │ Snapshot — frozen at moment JS  │
  │ (post-snapshot)                       │ was called                      │
  ├───────────────────────────────────────┼─────────────────────────────────┤
  │ Current request's finalization        │ Snapshot                        │
  │ (keepalive etc.)                      │                                 │
  ├───────────────────────────────────────┼─────────────────────────────────┤
  │ New requests (any phase)              │ Shared original — sees JS       │
  │                                       │ mutations ✓                     │
  └───────────────────────────────────────┴─────────────────────────────────┘

  This also handles the nginx.setTimeout case: the snapshot is taken before JS
  suspends. When JS resumes and makes further mutations, the suspended request's
   snapshot is already in r->pool and unaffected.

  ---
  ngx_js_snapshot_loc_conf design

  static ngx_int_t
  ngx_js_snapshot_loc_conf(ngx_http_request_t *r)
  {
      void  **lc;

      /* idempotent — skip if already snapshotted for this request */
      if (ngx_js_get_ctx(r)->loc_conf_snapshotted) {
          return NGX_OK;
      }

      /* 1. copy pointer array */
      lc = ngx_palloc(r->pool, ngx_js_http_nmodules * sizeof(void *));
      ngx_memcpy(lc, r->loc_conf, ngx_js_http_nmodules * sizeof(void *));
      r->loc_conf = lc;

      /* 2. deep-copy each writable struct (only modules we expose via JS COM) 
  */
      #define SNAP(module_sym, type)  do {                    \
          type *_s = ngx_palloc(r->pool, sizeof(*_s));        \
          *_s = *(type *) lc[(module_sym).ctx_index];         \
          lc[(module_sym).ctx_index] = _s;                    \
      } while (0)

      SNAP(ngx_http_core_module,          ngx_http_core_loc_conf_t);
      /* fix self-reference: clcf->loc_conf must point to our new lc */
      ((ngx_http_core_loc_conf_t *)
  lc[ngx_http_core_module.ctx_index])->loc_conf = lc;

  #if (NGX_HTTP_GZIP)
      SNAP(ngx_http_gzip_filter_module,   ngx_http_gzip_conf_t);
  #endif
      SNAP(ngx_http_sub_filter_module,    ngx_http_sub_loc_conf_t);
      SNAP(ngx_http_headers_filter_module,ngx_http_headers_conf_t);
      SNAP(ngx_http_rewrite_module,       ngx_http_rewrite_loc_conf_t);
      /* … add one SNAP per module we expose as writable … */

      #undef SNAP

      ngx_js_get_ctx(r)->loc_conf_snapshotted = 1;
      return NGX_OK;
  }

  Memory cost: ~10 modules × ~200 bytes average ≈ 2 KB per request, allocated
  from r->pool (freed when request ends). Negligible.

  Maintenance rule: every time we add a new writable property to any module's
  COM wrapper, we add the corresponding SNAP(...) line. The list lives in one
  place and is obviously auditable.

  ---
  One subtlety: clcf->loc_conf self-reference

  ngx_http_core_loc_conf_t contains void **loc_conf which points back to the
  pointer array it lives in. After snapshot, this must be updated to point to lc
   (the per-request copy), not the original array — otherwise modules that do
  clcf->loc_conf[other_module.ctx_index] will bypass the snapshot for other
  modules. This is the one non-mechanical line in the function above.

● Good question. The answer turns out to be no for most cases, because of when
  those configs are actually read relative to when JS runs.

  ---
  The timing argument

  JS only runs in NGX_HTTP_CONTENT_PHASE. Everything before that phase is frozen
   from JS's perspective. The question for each config level is: are its 
  writable fields read before or after CONTENT_PHASE?

  srv_conf (ngx_http_core_srv_conf_t)

  The writable fields we expose — clientHeaderBufferSize, clientHeaderTimeout,
  largeClientHeaderBuffers, ignoreInvalidHeaders, underscoresInHeaders,
  mergeSlashes — are all consumed during header parsing, which happens at
  connection setup / POST_READ_PHASE, long before CONTENT_PHASE. By the time JS
  runs, those reads are already done and the parsed result (e.g. the header
  buffers, the normalized URI) is sitting in r-> fields. Mutating the srv_conf
  originals after the fact has no effect on the current request.

  The one exception is serverTokens — it's read when building the Server:
  response header. But that's cosmetic and arguably the desired behavior ("I
  changed the server token, I want this response to reflect it").

  main_conf (ngx_http_core_main_conf_t)

  The writable fields exposed at nginx.http level — if any — are
  structural/global: variable hashes, type maps, server count. These are
  consumed at startup or during phase engine construction, not during
  per-request filter chains. Nothing in main_conf is read in a body filter or
  finalization path that JS could affect.

  Filters read loc_conf, not srv_conf or main_conf

  The row 4 problem (streaming filter inconsistency) exists specifically because
   body filters call ngx_http_get_module_loc_conf(r, m). They don't call
  ngx_http_get_module_srv_conf or ngx_http_get_module_main_conf. So the snapshot
   requirement is loc_conf-scoped.

  ---
  Summary

  ┌────────────┬────────────────────────────────────────────┬──────────────┐

  ├────────────┼────────────────────────────────────────────┼──────────────┤
  │ loc_conf   │ Yes — filters, finalization, keepalive     │ Yes          │

  Default getter change

  Currently loc.x reads from op->clcf (always global). After this plan the
  getter becomes effective: if a snapshot exists for the current request, it
  reads from the snapshot; otherwise from the original. This keeps loc.x
  coherent with what the request will actually use:

  loc.setProperty('x', 99, 'local');
  loc.x  →  99   ✓  (not the old global value)

  For the rare case where you need the global value while a snapshot exists:
  loc.getProperty('x', 'global');   // explicitly bypass snapshot
