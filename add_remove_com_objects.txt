● All 69/69 tests pass. Here's a summary of the three bugs that were fixed:

  1. Worker crash on server.names / server.name (Phase 1)

  cscf->server_names.elts is allocated from cf->temp_pool, which nginx destroys
  after init_conf() returns but before workers fork. Workers inherited dangling
  pointers. Fix: ngx_js_wrap_server() now copies the ngx_str_t array into
  cycle->pool only when ngx_process != NGX_PROCESS_WORKER. The guard uses != 
  NGX_PROCESS_WORKER (not == NGX_PROCESS_MASTER) because during init_conf() the
  process is NGX_PROCESS_SINGLE (0), not NGX_PROCESS_MASTER (1).

  2. server.root mutation not serving new root (Phase 2)

  ngx_conf_merge_str_value copies the parent's root.data pointer by value —
  child locations that lack an explicit root {} directive share the same address
   as the parent. The setter was only updating the server-level clcf. Fix: a new
   ngx_js_propagate_root() recursively walks static_locations (and
  regex_locations) and updates every child whose root.data matches the old
  pointer.

  3. Double ngx_http_finalize_request() for all Phase 4 requests

  req.respond() was calling ngx_http_finalize_request() internally, then
  ngx_js_content_handler returned NGX_DONE, causing ngx_http_core_content_phase
  to call ngx_http_finalize_request(r, NGX_DONE) a second time — triggering
  [alert] http request count is zero for every request. Fix: req.respond() now
  stores the output-filter rc in the NginxRequest opaque; ngx_js_content_handler
   reads it and returns it to nginx, letting ngx_http_core_content_phase call
  ngx_http_finalize_request() exactly once. The empty-body case uses
  ngx_calloc_buf + last_buf=1 through ngx_http_output_filter (the standard nginx
   idiom).

● This is a rich design question with several distinct sub-problems. Let me lay
  out the constraints and the options clearly.

  ---
  The Two Execution Windows

  nginx has two points where "JS that builds config" can run:

  Window: During parse
  When: Inside ngx_conf_parse() when js_include is encountered
  Can modify: Anything — location trees not yet built
  ────────────────────────────────────────
  Window: After parse (init_conf)
  When: After ngx_http_block() finishes
  Can modify: Scalars (root, workers) + shmem (upstreams). Location trees are
    frozen.

  The current implementation uses the after-parse window. That's fine for scalar
   mutations and upstream manipulation (Phases 2–3), but structural additions
  (addServer, addLocation) must happen during parse — before
  ngx_http_optimize_servers() builds the radix/hash structures.

  ---
  Approach A: config.write("http { ... }")

  JS runs as a config preprocessor — executed when js_include is encountered
  mid-parse, and it emits more config text that is fed back into
  ngx_conf_parse() recursively:

  // nginx.conf contains only:  js_include bootstrap.js
  config.write(`
    http {
      server {
        listen 80;
        server_name localhost;
        location / { root /var/www/html; }
      }
    }
  `);

  nginx already supports recursive parsing (include files do it). Implementation
   is straightforward: config.write(text) allocates a ngx_buf_t, sets
  cf->conf_file to point at it, calls ngx_conf_parse() recursively.

  Pros: No structural COM needed. Every directive nginx already knows works.
  Clean separation — JS is a preprocessor, not an internal manipulator.

  Cons: JS runs during parse, so the COM objects (nginx.http.servers[]) don't
  exist yet — you can introspect the environment (files, env vars, external
  services) but not already-parsed nginx config.

  ---
  Approach B: Structural COM API

  JS runs after parse (current init_conf window), but structural additions are
  deferred to ngx_js_http_module's postconfiguration hook, which fires inside
  ngx_http_block() before the location trees are frozen:

  ngx_http_block()
    → create_loc_conf × all HTTP modules
    → merge_loc_conf × all HTTP modules
    → postconfiguration × all HTTP modules    ← structural mutations applied
  HERE
    → ngx_http_optimize_servers()             ← trees frozen after this
    → ngx_http_init_static_location_trees()

  // Runs in init_conf() — structural additions queued, applied in 
  postconfiguration
  const srv = nginx.http.addServer({ listen: [8080], serverNames:
  ['api.example.com'] });
  srv.addLocation('/api/', { root: '/srv/api', handler: 'apiHandler' });

  Pros: Full COM access — JS can read existing servers, conditionally add more,
  combine with scalar mutations.

  Cons: More complex to implement. addServer must allocate a complete
  ngx_http_core_srv_conf_t and all loc_conf[] slots for every HTTP module (to
  satisfy merge expectations). This is the same work nginx does internally in
  ngx_http_core_server().

  ---
  Multi-Worker Coordination: The Hard Constraint

  This is the real architectural boundary:

  master: init_conf() runs → JS mutates config → fork workers
            ↓
  worker 0:  inherits master's memory snapshot (read-only copy-on-write)
  worker 1:  inherits master's memory snapshot
  worker N:  inherits master's memory snapshot

  Changes made before fork() are free — all workers see them automatically. This
   covers Phases 1–4 as implemented today.

  Changes made after fork() are per-worker. Three mechanisms exist for
  cross-worker coordination:

  1. Shared memory (the only truly atomic mechanism)

  Phase 3 already uses this for upstream peers. It can be extended to a
  general-purpose slab:

  nginx.shm.set('routing_table', JSON.stringify(routes));  // any worker writes
  // Every worker reads it on each request (or caches with TTL)
  const routes = JSON.parse(nginx.shm.get('routing_table'));

  This is the right tool for data that changes at runtime (routing tables,
  feature flags, rate limit state). It does not work for nginx C struct
  mutations (location trees etc.) because those structs are not shmem-backed.

  2. nginx reload (SIGHUP) — workers restart with new config

  The standard nginx mechanism. JS re-runs from scratch in init_conf() of the
  new cycle. New workers fork with the updated config; old workers drain
  gracefully. Zero-downtime since nginx already handles this.

  This is the right tool for structural config changes at runtime. The workflow:
  update /etc/nginx/routes.json
  nginx -s reload   # or POST to management API that sends SIGHUP

  JS reads routes.json in init_conf() and builds the COM tree accordingly.

  3. Worker-internal JS state (no inter-worker sync)

  Since each worker has its own JSRuntime, a nginx.onReload(fn) callback
  (triggered by the existing ngx_process_get_status() SIGUSR1 path) can update
  worker-private JS objects. Useful for in-process caches that tolerate
  per-worker staleness.

  ---
  Recommendation: Implement Both A and B, Use Shmem for Runtime

  The two approaches are complementary, not competing:

  Use case: Build entire config from scratch (js_include only)
  Mechanism: Approach A: config.write(text) as preprocessor
  ────────────────────────────────────────
  Use case: Read existing config, conditionally add/modify
  Mechanism: Approach B: structural COM (addServer, addLocation) deferred to
    postconfiguration
  ────────────────────────────────────────
  Use case: Runtime routing table / feature flags
  Mechanism: nginx.shm key-value store (slab-backed)
  ────────────────────────────────────────
  Use case: Structural config changes at runtime
  Mechanism: Existing nginx reload (SIGHUP) + JS re-runs init_conf

  Workers are intentionally not general-purpose reconfiguration targets. nginx's
   architecture treats them as identical, stateless request handlers. The
  master-restart-with-new-config model (reload) is the right lever for
  structural changes; shared memory is the right lever for data changes.

  The next concrete implementation step would be Approach A first — it's
  architecturally simpler (no deferred mutation queue, no postconfiguration
  hooks for structure) and immediately enables the "minimal nginx.conf + JS
  builds everything" scenario. The config.write() implementation is roughly:

  // During js_include execution — cf is available on JS context
  // config.write(text) pushes a buffer and calls ngx_conf_parse recursively
  static JSValue
  ngx_js_config_write(JSContext *ctx, JSValueConst this_val,
      int argc, JSValueConst *argv)
  {
      ngx_conf_t      *cf = JS_GetContextOpaque2(ctx, ...);
      const char      *text = JS_ToCString(ctx, argv[0]);
      // ... set up cf->conf_file pointing at text buffer ...
      ngx_conf_parse(cf, NULL);
      JS_FreeCString(ctx, text);
      return JS_UNDEFINED;
  }

  This requires shifting the JS execution window from init_conf() to inside the 
  js_include directive handler — which also unlocks postconfiguration-timed
  structural mutations as a natural consequence.
