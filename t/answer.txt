● The answer is in the C code at line 394-395. The architecture requires it:

  loc.handler stores a string name, not a function reference, because of the 
  NGINX master/worker process split.

  Here's what happens:

  1. Config phase runs in the master process. At that point, a JS JSValue
  function object exists only inside the master's JSRuntime/JSContext. That
  runtime is private to that OS process.
  2. After fork(), each worker gets its own separate process with its own memory
   space. The master's JSRuntime is not inherited in a usable state — QuickJS
  runtimes are not safe to use after fork.
  3. Each worker re-runs init.js (as the comment in the test says: "This code 
  also re-runs in each worker"), creating its own fresh JSContext with
  helloHandler etc. in its global scope.
  4. At request time, ngx_js_content_handler does this (lines 394-395):
  fn = JS_GetPropertyStr(ctx, global,
                         (const char *) jlcf->handler.data);
  4. It looks up the function by name in the worker's global JS object.

  A plain C string ("helloHandler") can be safely stored in nginx's config
  structures and survives fork() — it's just bytes. A JS function reference
  (JSValue) is a pointer into a specific runtime's heap; it becomes dangling
  garbage the moment that runtime no longer exists or is accessed from a
  different process.

  In short: strings cross process boundaries, JS values don't.
