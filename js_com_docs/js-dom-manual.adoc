== Introduction

=== What NGINX JS DOM Is

NGINX is deliberately static: its configuration is read once at startup (or
reload) and compiled into kernel-level data structures.  This rigidity is a
feature — it makes nginx predictable, fast, and easy to reason about — but it
creates friction whenever runtime adaptability is required: upstream weights
that need to track backend health scores, virtual hosts generated from a
tenant database, SSL certificates that rotate on a schedule, or request
routing rules that depend on live feature-flag state.

*NGINX JS DOM* embeds link:{quickjs-home}[QuickJS] (a lightweight
link:{es2020-spec}[ES2020+] JavaScript engine) directly into nginx and exposes
the entire nginx configuration as a structured JavaScript object tree called
the *Configuration Object Model (COM)*.  Through the COM, JavaScript can:

* *Read* the full live configuration of every module in every server and
  location.
* *Write* configuration properties — upstream peer weights, SSL certificates,
  location directives, gzip settings, and much more — with immediate effect,
  either for the current worker or atomically for all workers at once.
* *Generate* server and location blocks at parse time, before nginx has even
  finished reading its configuration file, and at run-time, when traffic events
  are processed by nginx workers in their nginx event loops.
* *Handle requests* in JavaScript, using the same event-driven async model as
  nginx itself.
* *Offload* CPU-intensive work to background threads (Workers) without
  blocking the nginx event loop.
* *Maintain shared mutable state* across all nginx worker processes using
  SharedWorkers and SharedArrayBuffers.

The result is an nginx that can be programmed rather than merely configured —
without restarting, without patching C code, and without sacrificing the
performance or stability of the core server.

=== Intended Audience

This manual assumes:

* Familiarity with nginx configuration syntax and core concepts (workers,
  upstreams, locations, modules).  See the
  link:{nginx-conf-guide}[NGINX Beginner's Guide] and the
  link:{nginx-docs}[full module reference] if you need a refresher.
* Working knowledge of modern JavaScript (ES2020): `async`/`await`, Promises,
  `import`/`export`, `SharedArrayBuffer`, `Atomics`.  See the
  link:{es2020-spec}[ECMAScript 2020 specification] or any ES2020 reference.

You do *not* need to know C or QuickJS internals to use the JS DOM API.

=== A Map of the Moving Parts

The sections that follow cover these components from a user's perspective.
For the internal C implementation — data structures, wire formats, and
architectural rationale — see the
link:../js_dom_doc_tech/README.md[`js_dom_doc_tech/` technical reference].

[cols="1,3", options="header"]
|===
| Component | What it gives you

| `js_preprocess`
| Runs JavaScript *during* config parsing; the script writes config text back
  into the parser.  Use it to generate server/location blocks from files,
  environment variables, or external sources.

| `js_init_http`
| Runs JavaScript *after* the `http {}` block is parsed but before directives
  are merged.  Can read already-parsed servers and inject new ones.

| `js_source`
| Evaluates JavaScript in the master process after all config has been parsed.
  This is where you install request handlers, set up Workers and
  SharedWorkers, and perform any pre-fork initialisation.

| Request handlers
| JavaScript `async` functions assigned to `location.handler`.  Each request
  runs through the nginx event loop; `await` suspends the handler without
  blocking any other request.

| COM
| The `nginx` global object tree.  Read live config values; write mutations
  that take effect immediately.

| Workers
| Standard link:{mdn-worker}[Web Worker] API.  A per-nginx-worker background
  thread for CPU-bound work.  Does not block the event loop.

| SharedWorkers
| A single long-lived thread in the master process, connected to every nginx
  worker via UNIX sockets.  The canonical place for mutable state that must
  be consistent across all workers.

| SharedArrayBuffers + Atomics
| Binary shared-memory regions (link:{mdn-sab}[MDN reference]) accessible
  from any thread with zero copy.  Combined with
  link:{mdn-atomics}[`Atomics`], they enable lock-free counters, mutexes,
  and condition variables.

| Bootstrap functions
| `nginx.createHttp()` / `nginx.createStream()` — instantiate the HTTP or
  stream module entirely from JavaScript, without an `http {}` or `stream {}`
  block in `nginx.conf`.  Combine with `nginx.http.addServer()` and
  `nginx.createSocket()` for a fully JS-defined server topology.

| Master/worker scripting
| `nginx.on(event, fn)` hooks into master lifecycle events (worker spawn,
  reload, SIGUSR1, …).  `nginx.sendToWorker()` / `nginx.broadcastToWorkers()`
  push messages from master to workers; `nginx.sendToMaster()` sends from
  a worker back to the master.

| `nginx.repl`
| An interactive JavaScript REPL that evaluates expressions inside a running
  nginx worker over a plain HTTP upgrade connection.  Useful for live
  introspection, ad-hoc mutations, and debugging.

| `location.clearHandler()`
| Removes a previously installed JS content handler and restores the
  original nginx C handler for that location.  Used by snapshot/rollback
  to undo handler changes atomically.

| Accept control
| `nginx.suspendAcceptance()` / `nginx.suspendAllWorkers()` — pause
  connection acceptance during a mutation window, then resume.

| Resource limits
| `nginx.workerMemoryLimit` and `nginx.workerRequestTimeout` cap heap usage
  and CPU time per request; JS exceptions are caught; the worker survives.
|===


== Architecture

=== Lifecycle Overview

....
nginx start
│
├─ Config file parsing begins (ngx_conf_parse)
│   │
│   ├── js_preprocess /gen.js ◄── STAGE 1: runs immediately, mid-parse
│   │      • Ephemeral JS runtime (freed after script returns)
│   │      • config.write(text) injects text back into the parser
│   │      • nginx.http, nginx.stream, etc. do NOT exist yet
│   │
│   ├── ... rest of nginx.conf parsed (servers, locations, upstreams) ...
│   │
│   └── js_init_http /init.js ◄── STAGE 2: runs after http{} block parses
│          • Ephemeral runtime, scoped to this directive
│          • config.write(text) still works; new servers get full merge treatment
│          • nginx.http.servers[] is readable (servers parsed before this line)
│
├─ init_conf (master process)  ◄── STAGE 3: js_source scripts evaluated here
│   │
│   ├── JS runtime + context created (persists, will be inherited by workers)
│   ├── All js_source files evaluated in order
│   │      • Install location.handler = fn assignments
│   │      • Create SharedWorkers (they start running immediately)
│   │      • Set nginx.workerMemoryLimit / nginx.workerRequestTimeout
│   │      • Any other pre-fork setup
│   └── SharedWorker threads spawned; channels to each future worker prepared
│
├─ fork() × worker_processes  ◄── STAGE 4: worker processes created
│   │
│   └── init_process (per worker)
│          • JS runtime inherited via copy-on-write
│          • No re-evaluation of scripts; all handlers already installed
│          • Worker attaches its UNIX socket channels to each SharedWorker
│
└─ Event loop (per worker)     ◄── STAGE 5: runtime
        │
        └── HTTP/stream request arrives
               • location.handler(req) called
               • await suspends handler; event loop serves other requests
               • COM reads/writes apply to THIS worker's copy (or all, with
                 suspendAllWorkers)
               • req.json() / req.respond() sends the response
....

=== Process and Thread Topology

:tabsize: 4

[source,text]
----
  ┌─────────────────────────────────────────────────────────────────┐
  │  Master process                                                 │
  │                                                                 │
  │  ┌──────────────────────┐  ┌──────────────────────┐             │
  │  │  SharedWorker A      │  │  SharedWorker B      │             │
  │  │  (pthread)           │  │  (pthread)           │             │
  │  │  long-lived JS state │  │  e.g. rate-limiter   │             │
  │  └──────────────────────┘  └──────────────────────┘             │
  └────────────────────────┬────────────────────────────────────────┘
                           │  AF_UNIX SEQPACKET
                           │  each worker gets one channel per SharedWorker
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  Worker 0    │  │  Worker 1    │  │  Worker N    │
  │  JS Runtime  │  │  JS Runtime  │  │  JS Runtime  │
  │  (CoW copy)  │  │  (CoW copy)  │  │  (CoW copy)  │
  │  Event loop  │  │  Event loop  │  │  Event loop  │
  │  JS Workers  │  │  JS Workers  │  │  JS Workers  │
  └──────────────┘  └──────────────┘  └──────────────┘
----

Key properties of this topology:

* Each nginx *worker process* has its own independent JS runtime.  QuickJS is
  not thread-safe; no runtime is ever shared between processes.
* Workers inherit the master's runtime via copy-on-write after `fork()`.
  Scripts do not need to be re-evaluated; all handler functions, SharedWorker
  references, and global variables are ready immediately.
* *SharedWorkers* run in the master process as pthreads, outside any worker.
  Each worker communicates with a SharedWorker over a dedicated UNIX socket
  channel.  This is the only channel through which workers can share mutable
  JS state.
* *JS Workers* (lowercase) are pthreads spawned *inside* a worker process.
  They exist to offload work from the event loop and are private to their
  nginx worker.

=== COM Ownership and Mutation Scope

All COM mutations go through one of three scopes:

[cols="1,2,2", options="header"]
|===
| Scope | Mechanism | Visible to

| Per-request snapshot
| `r.location.setWriteMode("local")` — writes a per-request copy of the
  location config
| This request only; reversed when the request pool is freed

| This worker only
| Direct COM write (default)
| All subsequent requests on this worker process

| All workers atomically
| `await nginx.suspendAllWorkers()` → mutate → `await nginx.resumeAllWorkers()`
| All workers, once they resume
|===

==== Inspecting mutation safety — `nginx.describe()`

Every settable COM property/method is classified along three axes so tooling
(and operators) can tell, at runtime, what a change will do:

* **class** — `safe` (reversible value change) · `guarded` (changes dispatch or
  live state; needs care + fan-out) · `irreversible` (cannot be undone for the
  process lifetime).
* **propagation** — `worker-local` (COW write; needs fan-out — the default) ·
  `zoned-shared` (cross-worker only when the upstream has a `zone`) ·
  `auto-shared` (`nginx.shared.*`, visible to all workers immediately).
* **requestScoped** — whether the member honours `setWriteMode('local')`.

[source,javascript]
----
nginx.describe("http.upstreams[0].peers[0]");          // Descriptor[] for every member
nginx.describe("http.servers[0].locations[0]", "handler");
// → {name:"handler", type:"function", access:"read-write",
//    class:"guarded", reversible:true, propagation:"worker-local",
//    requestScoped:false, note:"Rewires nginx dispatch; always global; …"}
----

`nginx.settable(path)` is unchanged (still returns `string[]`); `describe()` is
the superset that adds the safety metadata.  Unregistered classes / primitives
yield an empty array (or `null` for the single-member form).  The full
classification spec lives in `js_com_docs/js-com-safety-classes.adoc`; the
`A0.2_Safety_class_inspector` demo renders it as a traffic-light report.


== Quick Start

This section goes from "hello world" to "live upstream rebalancing" in four
steps, each building on the previous one.

=== Configure nginx with JS COM

Before any JS example can run, nginx must be built with the JS COM module and
told where to find your scripts.

==== Prerequisites

* GCC (or Clang), GNU make, PCRE, zlib, OpenSSL development headers
* https://github.com/bellard/quickjs[QuickJS] source tree checked out alongside the nginx tree

[source,bash]
----
# Debian / Ubuntu
sudo apt install gcc make libpcre3-dev zlib1g-dev libssl-dev
----

==== 1. Build the QuickJS static library

The JS COM module links against QuickJS as a static archive.
Build it once from the QuickJS source directory:

[source,bash]
----
# Run from the repository root (where both nginx/ and quickjs/ live)
make -C quickjs libquickjs.a
----

==== 2. Configure nginx with the JS module

Run `auto/configure` from inside the `nginx/` directory.
The two critical flags are `--add-module` (points at the JS COM source) and
`--with-cc-opt` / `--with-ld-opt` (link against the QuickJS library just built):

[source,bash]
----
cd nginx

auto/configure \
  --add-module=../nginx/src/js \
  --with-cc-opt="-I../quickjs -Wno-cast-function-type" \
  --with-ld-opt="-L../quickjs -lquickjs -lm" \
  --with-http_ssl_module
----

TIP: `-Wno-cast-function-type` suppresses a GCC warning triggered by QuickJS's
`JS_CFUNC_DEF` macro. nginx builds with `-Werror`, so this flag is required.

For a production build you will typically add more `--with-*` module flags
(stream, gzip, sub-filter, etc.).  The flags above are the minimal set needed
for all examples in this guide.

==== 3. Build the binary

[source,bash]
----
make -j$(nproc)
# Produced at: nginx/objs/nginx
----

==== 4. Write a minimal nginx.conf

Every JS COM setup needs exactly one thing in `nginx.conf`: a `js_source`
directive that points at your JavaScript file.  nginx evaluates all `js_source`
scripts in the master process after config parsing, before any worker is forked.
The global `nginx` object is available inside every script.

[source,nginx]
----
# /etc/nginx/nginx.conf — absolute minimum for JS COM
js_source /etc/nginx/js/init.js;   # <1>

events { }
----
<1> Path may be absolute or relative to the `--prefix` directory
    (default `/usr/local/nginx`).

Everything else — HTTP module, virtual servers, location handlers, upstreams —
can be created from `init.js` using `nginx.*` APIs, or left in `nginx.conf` and
then customised from JS.  The following subsections show both styles.

=== Hello World — Minimal (No http{} block)

The most compact nginx JS DOM server needs only a `js_source` directive and an
`events {}` block.  Everything else — the HTTP module, socket, virtual server,
and location handler — is created from JavaScript at init time:

[source,nginx]
----
# nginx.conf
js_source /etc/nginx/js/hello_world.js;

events { }
----

[source,javascript]
----
// hello_world.js — evaluated once in the master process after config parsing.
// Creates the entire server topology from JS; no http{}/server{}/location{}
// blocks are needed in nginx.conf.

(function () {

    // 1. Bootstrap the HTTP module (equivalent to an empty http{} block).
    //    Pass any http-level directives as a string argument.
    nginx.createHttp('access_log /var/log/nginx/access.log;');

    // 2. Create a new virtual server.
    var srv = nginx.http.addServer('hello-world.local');

    // 3. Add a location and install the JS content handler inline.
    srv.addLocation('/hello').handler = function (req) {
        req.respond(200, { 'content-type': 'text/plain' },
                    'JS COM: Hello World!\n');
    };

    // 4. Bind a TCP socket, attach it to the HTTP module,
    //    and register the server on that listener.
    var sock = nginx.createSocket('0.0.0.0:8080');
    nginx.http.attach(sock).addServer(srv);

})();
----

=== Hello World — Classic (with http{} block)

When `http {}` is already present in `nginx.conf`, just find the location
placeholder and assign a handler function:

[source,nginx]
----
# nginx.conf
js_source /etc/nginx/js/init.js;

events { }

http {
    server {
        listen 80;
        location /hello { }   # placeholder — handler installed from JS
    }
}
----

[source,javascript]
----
// /etc/nginx/js/init.js
// This file is evaluated once in the master process after config parsing.
// All location.handler assignments made here are inherited by every worker.

const loc = nginx.http.servers[0].locations.find(l => l.path === '/hello');

loc.handler = (req) => {
    // req is a NginxRequest object.  text() is a convenience shorthand
    // for respond(200, {'Content-Type': 'text/plain'}, body).
    req.text('Hello from JS DOM!\n');
};
----

=== Reading Request Data

[source,javascript]
----
// Read everything you might want from an incoming request.

loc.handler = async (req) => {
    // Basic identity
    const method  = req.method;          // "GET", "POST", …
    const uri     = req.uri;             // "/hello"
    const args    = req.args;            // raw query string: "a=1&b=2"
    const params  = req.queryParams;     // {a: "1", b: "2"}
    const scheme  = req.scheme;          // "http" or "https"
    const host    = req.host;            // "example.com"

    // Network info
    const client  = req.remoteAddr;      // "203.0.113.42"
    const port    = req.remotePort;      // 54321
    const server  = req.serverAddr;      // "192.0.2.1"

    // Headers (read-only object; keys are lowercased)
    const ua      = req.headers['user-agent'];
    const ct      = req.contentType;     // shorthand for content-type header

    // Cookies: {name: "value", …}
    const session = req.cookies['session_id'];

    // nginx variables — readable and writable via req.variables
    const xff     = req.variables['http_x_forwarded_for'];
    req.variables['my_custom_var'] = 'set-from-js';

    // Request body (requires await — nginx reads it asynchronously)
    const body    = await req.readBody();  // returns string

    req.json({
        method, uri, client, ua, session,
        bodyLength: body.length
    });
};
----

=== Async Fetch and Transform

[source,javascript]
----
// Non-blocking upstream call.  While this handler awaits, the nginx event
// loop freely serves other requests on this worker.

loc.handler = async (req) => {
    // req.fetch() performs an HTTP subrequest through nginx's upstream
    // machinery.  It returns a Promise that resolves with a Response object.
    const res  = await req.fetch('http://api.internal/v1/prices');
    const data = await res.json();

    // Apply transformation
    const adjusted = data.items.map(item => ({
        ...item,
        price: (item.price * 1.10).toFixed(2)   // add 10% margin
    }));

    req.json({ items: adjusted });
};
----

....
HTTP request arrives at worker
        │
        ▼
  loc.handler called synchronously
        │
        └─ await req.fetch(...)
               │
               │  [event loop resumes; other requests served here]
               │
               ▼  upstream response received (epoll fires)
         Promise resolves
               │
               ▼
         res.json() parsed
               │
               ▼
         req.json(result) → HTTP response sent
....

=== Live Upstream Rebalancing

[source,javascript]
----
// An admin endpoint that atomically updates upstream peer weights across
// all workers — no nginx restart, no dropped connections.

const adminLoc = nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/upstream/rebalance');

adminLoc.handler = async (req) => {
    const body    = await req.readBody();
    const weights = JSON.parse(body);   // { "192.0.2.10:8080": 5, "192.0.2.11:8080": 10 }

    // Step 1: pause all workers so the change is seen atomically.
    await nginx.suspendAllWorkers();

    // Step 2: apply weights.
    const peers = nginx.http.upstreams
        .find(u => u.name === 'backend').peers;

    for (const peer of peers) {
        if (weights[peer.addr] !== undefined) {
            peer.weight = weights[peer.addr];
        }
    }

    // Step 3: resume — all workers pick up the new weights immediately.
    await nginx.resumeAllWorkers();

    req.json({ applied: true, peers: peers.map(p => ({addr: p.addr, weight: p.weight})) });
};
----


== Request Handlers

=== Installing a Handler

A location handler is a JavaScript function assigned to `location.handler`
during `js_source` evaluation (init_conf time):

[source,javascript]
----
nginx.http.servers[0].locations
    .find(l => l.path === '/api')
    .handler = async (req) => { ... };
----

The function receives one argument — a `NginxRequest` object — and may be
synchronous or `async`.  A location that has no JS handler falls through to
nginx's normal content processing (proxy, static files, etc.).

=== Async Handler Lifecycle

....
nginx worker event loop
│
├─ accept() → new connection
│
├─ HTTP request parsed
│
├─ location matched → location.handler(req) called
│       │
│       ├─ [sync path] req.json(data)
│       │       └─► response buffered → written to socket → done
│       │
│       └─ [async path] await something
│               │
│               │  Handler suspended.  Worker event loop continues:
│               │    • accepts new connections
│               │    • runs other handlers
│               │    • processes timers and upstream responses
│               │
│               ▼  event fires (timer / upstream / Worker message)
│          Promise resolves; handler resumes from the await point
│               │
│               └─► req.json(data) → done
│
└─ (next event)
....

NOTE: Multiple async handlers can be suspended concurrently on the same worker.
Each nginx worker runs a single-threaded event loop; async handlers cooperate
by yielding at every `await` point, allowing other requests to be accepted and
served in between.  Use Workers or SharedWorkers when you need true CPU
parallelism or need to share mutable state across workers.

=== Streaming Responses

[source,javascript]
----
loc.handler = async (req) => {
    // Send status + headers, then stream the body in chunks.
    req.writeHead(200, {'Content-Type': 'text/event-stream',
                        'Cache-Control': 'no-cache'});

    for (let i = 0; i < 5; i++) {
        req.write(`data: event ${i}\n\n`);
        await req.sleep(200);      // 200 ms between events, non-blocking
    }

    req.finish();
};
----

[source,javascript]

// Fire three upstreams in parallel and merge results.
loc.handler = async (req) => {
    const [a, b, c] = await Promise.all([
        req.subrequest('/internal/prices'),
        req.subrequest('/internal/stock'),
        req.subrequest('/internal/ratings'),

        prices:  await a.json(),

=== Header and Body Filters

Filters are JavaScript functions that run in the nginx filter chain.  They
are installed on a location object:

[source,javascript]
----
// Header filter — modify response headers before they leave nginx
loc.headerFilter = (req, headers) => {
    headers['X-Powered-By'] = 'NGINX JS DOM';
    delete headers['Server'];
    return headers;
};

// Body filter — transform response body chunks
loc.bodyFilter = (req, chunk, isLast) => {
    // Replace "foo" with "bar" in every body chunk
    return chunk.replace(/foo/g, 'bar');
};
----

Filters run in priority order (lower number = earlier in chain, default
priority 50).


== Configuration Object Model (COM)

=== Overview

The COM is a live JavaScript object tree rooted at the global `nginx` object.
Properties read from the tree return current nginx struct values; writes (on
mutable properties) take immediate effect.

....
nginx
│
├── version            — string  "1.27.x"
├── cpuCount           — number  (number of CPU cores)
├── workerMemoryLimit  — number  (bytes; 0 = unlimited)  ← r/w
├── workerRequestTimeout — number (ms; 0 = unlimited)    ← r/w
│
├── log(level, msg)    — write to nginx error log
├── broadcast(msg)     — send msg to all workers' nginx.onbroadcast handler
│
├── suspendAcceptance()   — per-worker accept pause (sync)
├── resumeAcceptance()    — per-worker accept resume (sync)
├── suspendAllWorkers()   — cross-worker quiesce (async, returns Promise)
├── resumeAllWorkers()    — cross-worker resume (async, returns Promise)
│
├── cycle
│    ├── connections       — number (active connections)
│    ├── freeConnections   — number
│    ├── openFilesN        — number
│    └── sockets[]         — listener socket objects
│
├── events
│    ├── workerConnections — number ← r/w
│    ├── multiAccept       — boolean ← r/w
│    └── acceptMutex       — boolean ← r/w
│
├── http
│    ├── servers[]         — array of NginxServer (see below)
│    ├── upstreams[]       — array of NginxUpstream
│    ├── variables{}       — nginx HTTP variables
│    ├── serverNamesHashMaxSize    ← r/w
│    ├── serverNamesHashBucketSize ← r/w
│    ├── variablesHashMaxSize      ← r/w
│    ├── variablesHashBucketSize   ← r/w
│    ├── addServer(name)   — create a new virtual server at runtime
│    ├── removeServer(name [, {hard}]) — remove a vhost (reversible: tombstone)
│    ├── restoreServer(name) — bring a soft-removed vhost back (inverse)
│    ├── rebuildVhostDispatch() — recompile the server_name dispatch hash
│    ├── match(req, conditions) — evaluate an `if` condition against a request
│    └── sockets[]         — listening socket objects
│
└── stream
     ├── servers[]         — array of stream NginxServer

== Dynamic Reconfiguration

=== Scope 1 — This Worker Only

The simplest mutations happen directly in a handler with no coordination.
The change takes effect immediately for all subsequent requests on this worker.
Other workers retain their own CoW copy unchanged.

[source,javascript]
----
// Use-case: A/B flag toggle via admin endpoint, applied to this worker.
// Fine for experiments where eventual consistency across workers is acceptable.

nginx.http.servers[0].locations
    .find(l => l.path === '/admin/toggle-gzip')
    .handler = (req) => {
        // Toggle gzip for the /api location on THIS worker only
        const apiLoc = nginx.http.servers[0].locations
            .find(l => l.path === '/api');
        apiLoc.gzip = !apiLoc.gzip;
        req.text(`gzip is now ${apiLoc.gzip}`);
    };
----

=== Scope 2 — All Workers Atomically

For changes that must be consistent across every worker simultaneously, use
`suspendAllWorkers` / `resumeAllWorkers`.

....
Worker A (handler)
    │
    ├─ await suspendAllWorkers()
    │       │
    │       ├─► sends coordination signal to Workers B, C, …
    │       │     Each worker finishes its current request, then:
    │       │     • stops calling accept()
    │       │     • sends ACK
    │       │
    │       └─ resolves when ALL workers have ACK'd
    │
    ├─ [mutation window]
    │       • Direct COM writes apply to Worker A's copy
    │       • SharedWorker broadcast distributes the same data to B, C, …
    │         (each worker applies it from its own onmessage handler)
    │
    ├─ await resumeAllWorkers()
    │       └─► all workers call ngx_enable_accept_events() and resume
    │
    └─ respond
....

[source,javascript]
----
adminLoc.handler = async (req) => {
    const newPeers = JSON.parse(await req.readBody());

    await nginx.suspendAllWorkers();

    // Apply to this worker
    const peers = nginx.http.upstreams[0].peers;
    newPeers.forEach((p, i) => {
        if (peers[i]) peers[i].weight = p.weight;
    });

    await nginx.resumeAllWorkers();

    req.json({ ok: true });
};
----

=== Scope 3 — Add / Remove Servers and Locations

`addServer`, `removeServer`, `addLocation` enable structural mutations —
adding or removing routing entries at runtime.

[source,javascript]
----
// Tenant onboarding: create a new vhost live, no restart.

nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/tenant/create')
    .handler = async (req) => {
        const body   = JSON.parse(await req.readBody());
        const domain = body.domain;

        await nginx.suspendAllWorkers();

        // Create the new server
        const srv = nginx.http.addServer(domain);
        srv.listen.push('80');

        // Add a root location with a JS handler
        const loc = srv.addLocation('/');
        loc.handler = (r) => {
            r.text(`Welcome to ${domain}!\n`);
        };

        // Rebuild the server_name dispatch hash so the new Host: domain routes
        // correctly to our new server.
        nginx.http.rebuildVhostDispatch();

        await nginx.resumeAllWorkers();

        req.json({ created: domain });
    };
----

[source,javascript]
----
// Soft-remove a tenant server (reversible) — auto-rebuilds the dispatch hash.
nginx.http.removeServer('ex-tenant.example.com');
// ...later, bring it back exactly as it was:
nginx.http.restoreServer('ex-tenant.example.com');
----

[NOTE]
====
`removeServer(name)` is *reversible by default*: it **tombstones** the server —
its names are dropped from the virtual-server hash (requests fall through to the
default server) but the `cscf` + JS wrapper are kept, so `restoreServer(name)`
brings it back with identity preserved.  Both `removeServer` and `restoreServer`
**rebuild the dispatch hash automatically**, so the change takes effect on the
next request (no manual `rebuildVhostDispatch()` needed).

Pass `removeServer(name, {hard: true})` for the legacy irreversible splice
(the server is removed from `nginx.http.servers[]` and cannot be restored).
The underlying `cscf` is never freed in either mode (it lives in `cycle->pool`),
so the soft tombstone has the same memory profile as the hard splice — a strict
improvement.  In-flight responses emitted while a server was hidden are not
undone by restore.
====

IMPORTANT: `addServer()` still requires a manual `rebuildVhostDispatch()` to
activate routing; only `removeServer`/`restoreServer` rebuild automatically.

=== Scope 4 — Per-Request Config Snapshot

The `location.setWriteMode("local")` API creates a copy of the location's
config struct scoped to the current request.  The global struct is untouched;
other concurrent requests see the original values.

[source,javascript]
----
loc.handler = async (req) => {
    // Write only to a private snapshot for this request.
    req.location.setWriteMode('local');

    // This change is visible only inside this handler invocation.
    req.location.root = '/var/www/' + req.getVar('user_dir');
    req.location.gzip = false;

    // ... process request ...
    // When the request pool is freed, the snapshot is discarded automatically.
};
----

=== Hot SSL Certificate Swap

[source,javascript]
----
// Admin handler: reload the TLS certificate from disk, zero downtime.
// New connections after this call use the new certificate;
// in-flight TLS sessions are unaffected.

adminLoc.handler = async (req) => {
    const body = JSON.parse(await req.readBody());
    const srv  = nginx.http.servers.find(s => s.names.includes(body.domain));
    if (!srv) { req.respond(404, {}, 'unknown domain'); return; }

    await nginx.suspendAllWorkers();
    srv.ssl.cert = body.certPath;
    srv.ssl.key  = body.keyPath;
    await nginx.resumeAllWorkers();

    req.json({ reloaded: body.domain });
};
----


== Pre-Fork Initialization

=== `js_preprocess` — Config Injection During Parse

`js_preprocess` evaluates a JS script *during* `ngx_conf_parse`, at the exact
point where the directive appears in the config file.  The script receives a
global `config` object with a single method:

`config.write(text)` — feeds `text` back into the nginx config parser exactly
as if it had appeared inline at this position.

This happens *before* `init_conf`, so `nginx.http`, `nginx.stream`, and the
full COM are not available.  The `std` and `os` QuickJS modules are available
for file and OS access.

....
nginx.conf parse reaches js_preprocess /gen.js
        │
        ├─ New JS runtime created (isolated, short-lived)
        │
        ├─ gen.js evaluated
        │       • Can read files:    std.loadFile('/etc/conf.json')
        │       • Can read env:      std.getenv('APP_ENV')
        │       • Can run commands:  os.exec([...])
        │       • Can call config.write(text)
        │
        ├─ Runtime freed
        │
        └─ Injected text re-enters the parser as if it were inline
               → full http{}/server{}/location{} blocks allowed
               → directives go through normal merge/optimize_servers treatment
....

==== Example: Server Blocks from a JSON File

[source,javascript]
----
// /etc/nginx/js/gen.js
// Generates one server {} block per tenant from a JSON config file.
// Runs once at startup (and again on `nginx -s reload`).

import * as std from 'std';

// Read tenant definitions from a JSON file.
const raw     = std.loadFile('/etc/nginx/tenants.json');
const tenants = JSON.parse(raw);

let out = '';
for (const t of tenants) {
    out += `
server {
    listen 80;
    server_name ${t.domain};
    root /var/www/${t.id};
    location / { }
}
`;
}

config.write(out);
----

[source,nginx]
----
# nginx.conf
js_preprocess /etc/nginx/js/gen.js;   # ← generates server{} blocks

events { }
http {
    # servers from gen.js appear here as if written manually
}
----

==== Example: Conditional SSL Config

[source,javascript]
----
// Enable SSL only if the certificate file actually exists.
import * as os from 'os';

const certPath = '/etc/ssl/certs/site.pem';
const keyPath  = '/etc/ssl/private/site.key';

// os.stat() returns an object on success, error code on failure.
const [stat, err] = os.stat(certPath);
if (!err) {
    config.write(`
ssl_certificate     ${certPath};
ssl_certificate_key ${keyPath};
listen 443 ssl;
`);
}
----

==== Example: Fetching Config from a Network Service

`js_preprocess` runs synchronously inside the C parse loop.  There is no
event loop at this stage, so the standard `req.fetch()` API is unavailable.
The `std.urlGet()` function (link:{quickjs-libc}[QuickJS std library])
works around this by spawning `curl` as a child process and blocking until
the response arrives.

`curl` must be installed on the system.

[source,javascript]
----
// /etc/nginx/js/fetch-config.js
// Download upstream configuration from a config service at startup.
// Uses std.urlGet() which shells out to curl — blocking and synchronous.

import * as std from 'std';

const res = std.urlGet('http://config-service.internal/v1/nginx-upstreams',
                       { full: true });  // { status, headers, body }

if (res.status !== 200) {
    // Fail loudly — a bad config is worse than a failed start.
    throw new Error(`Config service returned ${res.status}`);
}

const cfg = JSON.parse(res.body);

// Generate upstream{} blocks
let out = '';
for (const up of cfg.upstreams) {
    out += `upstream ${up.name} {\n`;
    for (const peer of up.peers) {
        out += `    server ${peer.addr} weight=${peer.weight};\n`;
    }
    out += `}\n`;
}
config.write(out);
----

NOTE: `std.urlGet` always spawns a `curl` subprocess.  For reliability in
production, prefer writing config data to a file during a pre-start hook
and reading it with `std.loadFile()`, keeping `js_preprocess` independent of
network availability at start time.  The network fetch pattern is useful for
short-lived tooling or environments where the config service is guaranteed
to be reachable.

==== Multiple `js_preprocess` Directives

Multiple `js_preprocess` directives are allowed; each runs in its own
isolated runtime in declaration order:

[source,nginx]
----
js_preprocess /etc/nginx/js/gen-servers.js;    # generates server{} blocks
js_preprocess /etc/nginx/js/gen-upstreams.js;  # generates upstream{} blocks
js_preprocess /etc/nginx/js/gen-maps.js;       # generates map{} blocks

events { }
http { ... }
----

=== `js_init_http` — Post-Parse Server Injection

`js_init_http` fires after the entire `http {}` block has been parsed but
before directive merging takes place.  It provides both `config.write()` and
a read-only view of `nginx.http.servers[]` — the servers parsed before the
`js_init_http` directive.

....
nginx.conf
│
└── http {
    │
    ├── server { server_name primary.example.com; ... }
    │
    ├── server { server_name secondary.example.com; ... }
    │
    └── js_init_http /etc/nginx/js/post-parse.js;
           │
           ├─ nginx.http.servers[0] and [1] are readable
           ├─ config.write(text) injects new servers after these two
           └─ injected servers go through normal merge/init_locations treatment
....

[source,javascript]
----
// /etc/nginx/js/post-parse.js
// Add a management server on port 8099 only if no server is already
// listening on that port.

import * as std from 'std';

// Check whether any existing server listens on 8099
const already = nginx.http.servers.some(s =>
    s.listen.some(addr => addr.includes(':8099') || addr === '8099')
);

if (!already) {
    config.write(`
server {
    listen 8099;
    server_name management.internal;

    location /health { }
    location /metrics { }
}
`);
}
----

TIP: Place `js_init_http` *after* the `server {}` blocks it needs to read.
Servers parsed after the directive are not visible to the script.


== Workers (JS Web Workers)

JS Workers are background pthreads spawned inside an nginx worker process.
They implement the standard link:{mdn-worker}[Web Worker API] and are the
correct tool when a request needs to perform CPU-intensive computation without
blocking the event loop.

Each nginx worker process has its own set of Workers; they are not shared
between nginx workers.

=== Basic Worker Pattern

[source,javascript]
----
// init.js (js_source)

// Spawn a Worker thread for CPU-intensive prime computation.
// Workers are created once in js_source and reused across all requests.
const computeWorker = new Worker('/etc/nginx/js/prime_worker.js');

nginx.http.servers[0].locations
    .find(l => l.path === '/primes')
    .handler = async (req) => {
        const n = parseInt(req.queryParams.n) || 100;

        // Send work to the Worker thread and await the result.
        // While awaiting, the event loop is free to serve other requests.
        const result = await new Promise(resolve => {
            computeWorker.onmessage = e => resolve(e.data);
            computeWorker.postMessage({ n });
        });

        req.json(result);
    };
----

[source,javascript]
----
// /etc/nginx/js/prime_worker.js — runs in a separate pthread

function sieve(n) {
    const composite = new Uint8Array(n + 1);
    for (let i = 2; i * i <= n; i++) {
        if (!composite[i]) {
            for (let j = i * i; j <= n; j += i) composite[j] = 1;
        }
    }
    return Array.from({length: n - 1}, (_, i) => i + 2).filter(i => !composite[i]);
}

// Worker message loop
onmessage = (e) => {
    const primes = sieve(e.data.n);
    postMessage({ count: primes.length, largest: primes[primes.length - 1] });
};
----

....
HTTP request → nginx worker event loop
        │
        ├─ handler called; sends postMessage to Worker thread
        │       │
        │       ▼
        │   Worker pthread
        │   (independent JS runtime)
        │   sieve(n)  ← CPU-bound, runs without blocking event loop
        │       │
        │       ▼
        │   postMessage(result)
        │       │
        │       ▼  onmessage event delivered to event loop
        │
        └─ Promise resolves; req.json(result) → response sent
....

=== Transferring ArrayBuffers (Zero Copy)

Passing an `ArrayBuffer` by transfer moves ownership; the sender can no
longer access it.  Use this for large binary payloads:

[source,javascript]
----
// Compress a large buffer in a Worker thread, transfer result back.
const compressionWorker = new Worker('/etc/nginx/js/compress_worker.js');

loc.handler = async (req) => {
    const body   = await req.readBody();
    const input  = new TextEncoder().encode(body).buffer;  // ArrayBuffer

    const compressed = await new Promise(resolve => {
        compressionWorker.onmessage = e => resolve(e.data.buf);
        // Transfer 'input' — zero copy, Worker takes ownership
        compressionWorker.postMessage({ buf: input }, [input]);
    });

    req.setHeader('Content-Encoding', 'deflate');
    req.respond(200, {}, compressed);
};
----

=== Worker `std` and `os` Modules

Workers have access to the QuickJS standard library:

[source,javascript]
----
// worker.js
import * as std from 'std';
import * as os  from 'os';

onmessage = (e) => {
    // Blocking file read — safe in a Worker (doesn't block the event loop)
    const data = std.loadFile(e.data.path);
    postMessage({ content: data, length: data?.length ?? 0 });
};
----

See link:{quickjs-libc}[QuickJS Standard Library] for the full `std`/`os` API
reference.


== SharedWorkers

=== Concept and Use Cases

A link:{mdn-sw}[SharedWorker] is a single long-lived pthread running in the
nginx *master* process, connected to every nginx worker via dedicated UNIX
socket channels.  Unlike JS Workers (one per nginx worker), there is exactly
one SharedWorker instance regardless of the `worker_processes` count.

This makes SharedWorkers the canonical location for:

* **Session stores** — a token → user mapping visible to every worker.
* **Distributed rate limiters** — accurate global request-per-second counting.
* **Feature flags** — a single flag store; updates propagate to all workers on
  the next message.
* **Distributed locks** — a central lock arbiter that any worker can acquire.
* **Config broadcast** — push a config change to all workers simultaneously
  (see <<scope-2-all-workers-atomically>>).

=== Port-Based Pattern (Explicit `onconnect`)

Use this pattern when a worker needs a dedicated two-way channel with the
SharedWorker (i.e. replies must go back to the same worker that sent the
request):

[source,javascript]
----
// /etc/nginx/js/session_sw.js — SharedWorker script

const store = new Map();   // token → {userId, expires}

// onconnect fires once per nginx worker when the channel is first used.
onconnect = (e) => {
    const port = e.ports[0];

    port.onmessage = (msg) => {
        const { cmd, token, data } = msg.data;

        if (cmd === 'get') {
            const entry = store.get(token) ?? null;
            // Reply only to the worker that asked
            port.postMessage({ token, entry });

        } else if (cmd === 'set') {
            store.set(token, { userId: data.userId,
                               expires: Date.now() + data.ttl });
            port.postMessage({ ok: true });

        } else if (cmd === 'del') {
            store.delete(token);
            port.postMessage({ ok: true });
        }
    };
};
----

[source,javascript]
----
// init.js (js_source)

const sessionSW = new SharedWorker('/etc/nginx/js/session_sw.js');

// Helper: promise-based call into the SharedWorker.
function swCall(cmd, token, data) {
    return new Promise(resolve => {
        sessionSW.port.onmessage = e => resolve(e.data);
        sessionSW.port.postMessage({ cmd, token, data });
    });
}

nginx.http.servers[0].locations
    .find(l => l.path === '/auth')
    .handler = async (req) => {
        const token = req.cookies['session'];
        if (!token) { req.respond(401, {}, 'no session'); return; }

        const { entry } = await swCall('get', token, null);
        if (!entry || entry.expires < Date.now()) {
            req.respond(401, {}, 'invalid or expired session');
            return;
        }

        req.setVar('authenticated_user', entry.userId);
        req.respond(200, {}, `Hello ${entry.userId}`);
    };
----

=== Broadcast Pattern (Global `onmessage` + `clients`)

Use this pattern when the SharedWorker needs to push the same message to
*all* connected workers simultaneously:

[source,javascript]
----
// /etc/nginx/js/broadcast_sw.js

// No onconnect — global onmessage handles all workers via the `clients` array.
// `clients` is an array of all currently connected port objects.

onmessage = (msg) => {
    if (msg.data.cmd === 'broadcast') {
        // Forward the message to every connected worker
        clients.forEach(c => c.postMessage(msg.data.payload));
    }
};
----

[source,javascript]
----
// init.js: trigger a broadcast from any worker's request handler.
const broadcastSW = new SharedWorker('/etc/nginx/js/broadcast_sw.js');

// Each worker registers a listener on the SW port at init time.
broadcastSW.port.onmessage = (e) => {
    // This fires on every worker when a broadcast arrives.
    const { key, value } = e.data;
    // Apply the change to this worker's local copy of the config.
    applyFeatureFlag(key, value);
};

// Admin handler: update a feature flag on all workers at once.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/feature-flag')
    .handler = async (req) => {
        const { key, value } = JSON.parse(await req.readBody());

        // Tell the SharedWorker to broadcast to all workers.
        broadcastSW.port.postMessage({
            cmd: 'broadcast',
            payload: { key, value }
        });

        req.json({ ok: true });
    };
----

=== Dynamic SharedWorker Creation

SharedWorkers created in `js_source` are spawned before `fork()` and are

loc.handler = async (req) => {

== SharedArrayBuffers and Atomics

=== What They Are

A link:{mdn-sab}[`SharedArrayBuffer`] is a region of memory accessible —
with zero copying — from any thread: nginx workers, JS Workers, and the
SharedWorker thread.

Typed array views (`Int32Array`, `Float64Array`, `BigInt64Array`, etc.) over a
SAB provide direct read/write access.  link:{mdn-atomics}[`Atomics`] operations
(`add`, `compareExchange`, `wait`, `notify`) provide the synchronisation
primitives needed for safe concurrent access.

=== Pre-Fork SABs (Visible to All Workers)

A SAB created in `js_source` is backed by the CoW page mapping inherited by
every worker after `fork()`.  All workers share the same physical pages.

[source,javascript]
----
// init.js (js_source)
// A global hit counter visible to all workers with zero copy.

const counterBuf = new SharedArrayBuffer(8);
const hits       = new BigInt64Array(counterBuf);
// hits[0] is shared by every worker process.

nginx.http.servers[0].locations
    .find(l => l.path === '/count')
    .handler = (req) => {
        // Atomic increment — safe across all nginx workers simultaneously.
        const n = Atomics.add(hits, 0, 1n);
        req.text(`Request #${n + 1n}\n`);
    };

nginx.http.servers[0].locations
    .find(l => l.path === '/stats')
    .handler = (req) => {
        req.json({ total_hits: Number(Atomics.load(hits, 0)) });
    };
----

=== Post-Fork SABs (Worker-Local, Passed via Channels)

A SAB created inside a request handler (post-fork) is backed by a Linux
`memfd` and can be transferred to a JS Worker or SharedWorker via
`postMessage`.  The receiving thread `mmap`s the same file descriptor,
establishing a shared mapping without copying data.

[source,javascript]
----
// Worker thread computes a result into a SAB; main thread reads it.

const processorWorker = new Worker('/etc/nginx/js/processor.js');

loc.handler = async (req) => {
    // Allocate shared memory for the result
    const resultBuf = new SharedArrayBuffer(1024);
    const result    = new Uint8Array(resultBuf);
    const ready     = new SharedArrayBuffer(4);
    const flag      = new Int32Array(ready);

    // Pass both SABs to the Worker; it writes the result and sets flag.
    processorWorker.postMessage({
        input:     JSON.parse(await req.readBody()),
        resultBuf, // shared — Worker writes here
        ready      // shared — Worker sets flag[0]=1 when done
    });

    // Non-blocking poll using Atomics.wait in the Worker thread
    // Meanwhile the event loop remains free.
    await new Promise(resolve => {
        processorWorker.onmessage = () => resolve();
    });

    req.respond(200, {}, new TextDecoder().decode(result));
};
----

=== Atomics.wait / Atomics.notify

`Atomics.wait` is a *blocking* call — it must only be used in Worker or
SharedWorker threads, never in the main nginx event loop.

[source,javascript]
----
// Mutex implementation using SAB + Atomics.
// Safe to use in Worker and SharedWorker threads.

const mutexBuf = new SharedArrayBuffer(4);   // one Int32 = one mutex
const mutex    = new Int32Array(mutexBuf);

function lock() {
    // Spin until we CAS 0 → 1 (acquire)
    while (Atomics.compareExchange(mutex, 0, 0, 1) !== 0) {
        // Block this thread until mutex[0] changes — woken by unlock()
        Atomics.wait(mutex, 0, 1);
    }
}

function unlock() {
    Atomics.store(mutex, 0, 0);
    // Wake one waiting thread
    Atomics.notify(mutex, 0, 1);
}
----

[source,javascript]
----
// In the SharedWorker thread — use Atomics.wait/notify to signal workers.
// SharedWorker receives work, signals the waiting nginx worker via SAB.

onconnect = (e) => {
    const port = e.ports[0];

    port.onmessage = (msg) => {
        const { sab, workItem } = msg.data;
        const signal = new Int32Array(sab);

        // Do the work ...
        const result = processWork(workItem);

        // Write result into a different part of the SAB, then notify.
        // The nginx worker is blocked in Atomics.waitAsync on this index.
        Atomics.store(signal, 0, 1);       // mark done
        Atomics.notify(signal, 0);         // wake the nginx worker's Worker thread
    };
};
----

NOTE: `Atomics.waitAsync` (non-blocking, returns a Promise) is available in
the nginx event loop context and is the correct way to wait for a SAB value
to change from the main thread.


== Accept Control and Cross-Worker Coordination

=== The Problem

COM mutations applied directly from a handler affect only the worker that
executed the handler.  Other workers have independent CoW copies and will not
see the change.  Furthermore, if a mutation is applied while another request
on the same worker is halfway through using the old value, the result can be
inconsistent.

Accept control solves both problems by temporarily pausing connection
acceptance, creating a window during which no new requests can start and the
worker is in a known-clean state.

=== Per-Worker: `suspendAcceptance` / `resumeAcceptance`

These are synchronous, instant, and affect only the calling worker.

[source,javascript]
----
loc.handler = (req) => {
    // Stop accepting new connections on THIS worker.
    // OS backlog holds new connections; other workers keep accepting normally.
    nginx.suspendAcceptance();

    // Apply a batch of mutations atomically from this worker's perspective.
    const upstream = nginx.http.upstreams[0];
    upstream.peers[0].weight = 10;
    upstream.peers[1].weight = 5;
    upstream.peers[2].down   = true;

    // Resume accepting.
    nginx.resumeAcceptance();

    req.text('upstream updated\n');
};
----

What happens while suspended:

....
OS kernel
  │
  └── TCP SYN backlog accumulates (up to net.core.somaxconn connections)
          │
          └── When resumeAcceptance() is called, epoll fires again and
              the worker drains the backlog in FIFO order.
....

Other workers are unaffected and continue accepting normally.

=== Cross-Worker: `suspendAllWorkers` / `resumeAllWorkers`

For changes that must be atomic across all workers simultaneously:

....
Worker A (handler)
  │
  ├─ await nginx.suspendAllWorkers()
  │       │
  │       ├─ Workers B, C, … receive coordination signal
  │       │     Each finishes current request → stops accepting → ACKs
  │       └─ resolves when all have ACK'd
  │
  ├─ mutation window (all workers quiesced)
  │
  ├─ await nginx.resumeAllWorkers()
  │       └─ all workers re-add listening sockets to epoll
  │
  └─ req.respond(...)
....

=== SharedWorker Broadcast + Accept Control Pattern

The most flexible pattern for cross-worker config updates:

[source,javascript]
----
// coord_sw.js — SharedWorker for cross-worker coordination

const ports = [];   // one port per connected worker

onconnect = (e) => {
    const port = e.ports[0];
    ports.push(port);

    port.onmessage = (msg) => {
        if (msg.data.cmd === 'broadcast_apply') {
            // Push the same config update to every worker
            ports.forEach(p => p.postMessage({
                cmd:    'apply',
                config: msg.data.config
            }));
        }
    };
};
----

[source,javascript]
----
// init.js
const coordSW = new SharedWorker('/etc/nginx/js/coord_sw.js');

// Each worker registers a listener to apply inbound config changes.
coordSW.port.onmessage = (e) => {
    if (e.data.cmd === 'apply') {
        applyConfig(e.data.config);
        nginx.resumeAcceptance();
    }
};

function applyConfig(cfg) {
    // Apply upstream changes to this worker's local copy.
    const peers = nginx.http.upstreams[0].peers;
    cfg.peers.forEach((p, i) => {
        if (peers[i]) {
            peers[i].weight = p.weight;
            peers[i].down   = p.down;
        }
    });
}

// Admin endpoint: one worker drives the update, broadcasts to all others.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/config-push')
    .handler = async (req) => {
        const cfg = JSON.parse(await req.readBody());

        // Quiesce all workers, apply locally, then broadcast.
        await nginx.suspendAllWorkers();

        applyConfig(cfg);  // this worker applies locally

        // Tell SharedWorker to push to all workers; they will call
        // resumeAcceptance() from their onmessage handler.
        coordSW.port.postMessage({ cmd: 'broadcast_apply', config: cfg });

        // This worker also resumes acceptance.
        nginx.resumeAcceptance();

        req.json({ pushed: true });
    };
----

=== Backlog Behaviour

While any or all workers have acceptance suspended, incoming TCP connections
queue in the OS SYN/accept backlog:

* Backlog size is controlled by `net.core.somaxconn` (typically 128–4096) and
  the `listen` directive's `backlog=N` parameter.
* If the backlog fills before `resumeAcceptance()` is called, the kernel drops
  new SYN packets.  From the client's perspective this looks like the server
  is temporarily unavailable.
* For short mutation windows (sub-millisecond), the probability of backlog
  overflow is negligible even under high load.

CAUTION: Do not hold all workers suspended for long operations (database
queries, external HTTP calls).  Complete all blocking work before calling
`suspendAllWorkers()`, then apply changes synchronously in the mutation
window.


== Snapshots

Snapshots capture a point-in-time copy of a COM sub-tree.  They are useful
for rollback, for auditing config state, and for read-heavy operations that
must be isolated from concurrent writes.

=== Basic Snapshot and Rollback

[source,javascript]
----
loc.handler = async (req) => {
    // Capture the current state of a location before mutating it.
    const snap = req.location.snapshot();

    try {
        // Attempt to apply new configuration.
        const cfg = JSON.parse(await req.readBody());
        req.location.gzip        = cfg.gzip;
        req.location.root        = cfg.root;
        req.location.proxy.pass  = cfg.proxyPass;

        req.json({ applied: true });
    } catch (e) {
        // Something went wrong — restore the original state.
        snap.restore();
        req.respond(500, {}, `Config apply failed: ${e.message}`);
    }
};
----

=== Sub-Object Snapshots

You can snapshot a specific COM sub-tree rather than the entire config:

[source,javascript]
----
// Snapshot just the upstream peer list.
const snap = nginx.http.upstreams[0].snapshot();

// Apply potentially risky changes.
nginx.http.upstreams[0].peers.forEach(p => p.weight = 1);

// If health-check fails, restore peer weights.
const healthy = await runHealthCheck();
if (!healthy) {
    snap.restore();
}
----

=== Read / Write Mode Interaction with Snapshots

When `setWriteMode("local")` is active, COM writes go to a per-request
snapshot automatically, leaving the global config untouched:

[source,javascript]
----
loc.handler = async (req) => {
    // Isolate all writes to this request.
    req.location.setWriteMode('local');
    req.location.setReadMode('local');

    // Mutate the per-request copy freely.
    req.location.root = '/var/www/' + req.getVar('tenant');

    // Other concurrent requests still see the original global root.
    req.sendfile('/index.html');
};
----

== Bootstrap Functions (`nginx.createHttp` / `nginx.createStream`)

These two functions let you instantiate the nginx HTTP or stream module
entirely from JavaScript, without an `http {}` or `stream {}` block in
`nginx.conf`.  They are called inside a `js_source` script at init time and
may be combined with `nginx.http.addServer()`, `nginx.createSocket()`, and
`nginx.http.attach()` to build a completely JS-defined server topology.

=== `nginx.createHttp([directives])`

Creates the HTTP module as if an empty `http {}` block were present in
`nginx.conf`.

[cols="1,3", options="header"]
|===
| Parameter | Description

| `directives` (optional)
| A string containing http-context directives that would normally appear
  inside `http { … }`, e.g. `'access_log /var/log/nginx/access.log;'`.
  Multiple directives may be separated by whitespace.
|===

After `nginx.createHttp()` returns, `nginx.http` is available and fully
functional.  You can immediately call `nginx.http.addServer()`,
`nginx.http.upstreams`, etc.

Full working example (from `t/hello_world.t`):

[source,javascript]
----
(function () {

    // 1. Bootstrap the HTTP module.
    nginx.createHttp('access_log /var/log/nginx/access.log;');

    // 2. Create a virtual server (nginx builds a default template when
    //    servers[] is empty).
    var srv = nginx.http.addServer('hello-world.local');

    // 3. Add a location and its JS content handler.
    srv.addLocation('/hello').handler = function (req) {
        req.respond(200, { 'content-type': 'text/plain' },
                    'JS COM: Hello World!\n');
    };

    // 4. Bind a TCP socket, attach it to the HTTP listener,
    //    and register the server.
    var sock = nginx.createSocket('0.0.0.0:8080');
    nginx.http.attach(sock).addServer(srv);

})();
----

==== Pausing a listener — `removeListener` / `restoreListener`

A live listener can be quiesced and resumed at runtime:

[source,javascript]
----
nginx.http.removeListener('0.0.0.0:8080');   // stop accepting (this worker)
// ...drain / maintenance...
nginx.http.restoreListener('0.0.0.0:8080');  // resume accepting
----

[NOTE]
====
`removeListener(addr)` *soft-pauses* the listener: it removes this worker's
accept event from the event loop (`ngx_del_event`), so the worker stops
accepting on that socket.  The fd stays bound, so in-flight requests finish and
new connections complete the TCP handshake and **queue in the kernel backlog**
(they are not refused) until `restoreListener(addr)` re-arms accept
(`ngx_add_event`).  Fully reversible — ideal for *drain-during-deploy*.

Like the other structural ops it is **per-worker**; fan it out (e.g. via the
admin console's SharedWorker, as a `{op:"removeListener", addr}` snapshot op) to
pause every worker.  `removeListener(addr, {hard:true})` — close the socket so
connections are *refused* — is **reserved**: a worker cannot truly close the
listener because the master keeps the bound fd, so it needs master-side
coordination (a planned follow-up) and currently throws.
====

=== `nginx.createStream([directives])`

Creates the stream module as if an empty `stream {}` block were present in
`nginx.conf`.

[cols="1,3", options="header"]
|===
| Parameter | Description

| `directives` (optional)
| A string containing stream-context directives, e.g.
  `'proxy_timeout 30s;'`.
|===

After `nginx.createStream()` returns, `nginx.stream` is available.

Full working example (from `t/hello_stream.t`):

[source,javascript]
----
(function () {

    // 1. Bootstrap the stream module.
    nginx.createStream();

    // 2. Create a stream server and attach a handler.
    var srv = nginx.stream.addServer();
    srv.handler = function (session) {
        session.finalize(200);   // accept and close cleanly
    };

    // 3. Bind a TCP socket, attach it to the stream module,
    //    and register the server.
    var sock = nginx.createSocket('0.0.0.0:9000');
    nginx.stream.attach(sock).addServer(srv);

})();
----

=== When to Use Bootstrap Functions

[cols="1,2", options="header"]
|===
| Situation | Recommendation

| Full server topology defined in JS (dynamic, data-driven)
| Use `nginx.createHttp()` / `nginx.createStream()`.  No static
  `http {}` / `stream {}` needed.

| `http {}` block already in `nginx.conf`, only handlers vary
| Skip `createHttp()`; use `nginx.http.addServer()` and `addLocation()`
  to augment the existing topology.

| Mix of static and dynamic servers
| Include a minimal `http {}` block in `nginx.conf` for any static servers;
  call `nginx.http.addServer()` for additional dynamic ones.
|===


== Master/Worker Scripting

In addition to running handlers in worker event loops, `js_source` scripts
run in the *master process* and can hook into the master's supervisory loop:
reacting to worker lifecycle events, sending data to workers, and receiving
data back.

=== Master Lifecycle Events (`nginx.on`)

Register callbacks with `nginx.on(event, fn)` in any `js_source` script.
The callbacks run in the master process.

[cols="1,2,3", options="header"]
|===
| Event | Callback signature | When it fires

| `'workerSpawned'`  | `fn(pid, slot)`          | A new worker process has started
| `'workerExited'`   | `fn(pid, slot, status)`  | A worker process has exited
| `'reload'`         | `fn()`                   | SIGHUP received, old config still active
| `'reloaded'`       | `fn()`                   | SIGHUP complete, new workers are running
| `'reopen'`         | `fn()`                   | SIGUSR1 received (rotate logs)
| `'quit'`           | `fn()`                   | SIGQUIT received (graceful shutdown)
| `'message'`        | `fn(data)`               | Worker sent data to master via `sendToMaster()`
                                                  _(alias: `'workerMessage'` with `fn(slot, data)`)_
|===

NOTE: `'message'` and `'workerMessage'` are two spellings of the same hook.
Use `'workerMessage'` when you need the sender's `slot` index; use `'message'`
when you don't.

Example — log every worker lifecycle event to a file:

[source,javascript]
----
import * as std from 'std';

var evlog = '/var/log/nginx/worker-events.log';

function append(msg) {
    var f = std.open(evlog, 'a');
    if (f) { f.puts(msg + '\n'); f.close(); }
}

nginx.on('workerSpawned', function(pid, slot) {
    append('workerSpawned pid=' + pid + ' slot=' + slot);
});

nginx.on('workerExited', function(pid, slot, status) {
    append('workerExited pid=' + pid + ' slot=' + slot + ' status=' + status);
});

nginx.on('quit',     function() { append('quit');     });
nginx.on('reload',   function() { append('reload');   });
nginx.on('reloaded', function() { append('reloaded'); });
nginx.on('reopen',   function() { append('reopen');   });
----

=== Master → Worker Messages

The master can push arbitrary JSON-serializable data to one or all workers.

[cols="2,3", options="header"]
|===
| Method | Description

| `nginx.sendToWorker(slot, data)`
| Send `data` to the worker at index `slot`.  The worker receives it
  via `nginx.on('message', fn)`.

| `nginx.broadcastToWorkers(data)`
| Send `data` to every running worker.  Each worker receives its own
  copy via `nginx.on('message', fn)`.
|===

`data` must be JSON-serializable.  It is transferred through the existing
nginx channel socketpairs (the same fds used by `ngx_channel_t`), so no
extra file descriptors are required.

Example — greet each worker as it spawns:

[source,javascript]
----
nginx.on('workerSpawned', function(pid, slot) {
    nginx.sendToWorker(slot, { event: 'hello', slot: slot, pid: pid });
});

// In the same js_source script, workers receive:
nginx.on('message', function(data) {
    nginx.log(nginx.INFO,
        'worker ' + nginx.workerIdx + ' received: ' + JSON.stringify(data));
});
----

=== Worker → Master Messages

Workers can send data back to the master at any time — typically from inside
a request handler.

[cols="2,3", options="header"]
|===
| Method | Description

| `nginx.sendToMaster(data)`
| Send `data` from the current worker to the master.  `data` is
  JSON-serializable.

| `nginx.on('workerMessage', fn(slot, data))`
| Register a master-side handler.  `slot` is the sender's worker index;
  `data` is the received object.
|===

The master's event loop is woken via SIGIO (already set up by nginx for
other channel operations), so no polling is needed.

Example — worker sends a health ping; master writes it to a log file:

[source,javascript]
----
import * as std from 'std';

// Master side: receive and log
nginx.on('workerMessage', function(slot, data) {
    var f = std.open('/var/log/nginx/worker-msgs.log', 'a');
    if (f) {
        f.puts('slot:' + slot + ' msg:' + data.msg + '\n');
        f.close();
    }
});

// Worker side: send on HTTP request
nginx.http.servers[0].locations
    .find(function(l) { return l.path === '/ping'; })
    .handler = function(req) {
        nginx.sendToMaster({ slot: nginx.workerIdx, msg: 'ping' });
        req.respond(200, {'content-type': 'text/plain'}, 'sent\n');
    };
----

=== `nginx.workerIdx`

Inside a worker process, `nginx.workerIdx` returns the zero-based slot index
of the current worker (matches the `slot` parameter in lifecycle callbacks).
In the master process it returns `undefined`.


== nginx.repl — Interactive JavaScript REPL

`nginx.repl` provides an in-process JavaScript REPL that evaluates expressions
inside a running nginx worker over a plain HTTP upgrade connection.  It is
useful for live introspection, ad-hoc mutations, and debugging without a
restart.

=== How It Works

A request handler calls `req.hijack()` to take ownership of the raw TCP
connection, then calls `nginx.repl.attach()` to redirect `console.log` /
`nginx.log` output to that connection, and `nginx.repl.listen()` to install
a line-by-line read loop.  Each line received is evaluated by
`nginx.repl.eval()` and the result is written back.

=== REPL API

[cols="2,3", options="header"]
|===
| Method | Description

| `nginx.repl.eval(line)`
| Evaluate one line of JavaScript in the current worker's context.
  Returns `{ status, value, message, stack }`.  `status` is `"ok"`,
  `"err"`, `"incomplete"`, or `"stack"`.  `value` is the JSON-serialised
  result on success.

| `nginx.repl.attach(fd, loglevel, nginxlevel)`
| Start streaming `console.log` / `console.warn` / `console.error` and
  `nginx.log` output to `fd`.  `loglevel` filters JS console methods
  (0 = log+warn+err, 1 = warn+err, 2 = err only); `nginxlevel` is the
  nginx log severity threshold.

| `nginx.repl.detach()`
| Stop streaming; restore normal log routing.

| `nginx.repl.listen(fd, fn)`
| Install a line-by-line read handler on `fd`.  Each complete line
  (delimited by `\n`) is passed to `fn(line)`.

| `nginx.repl._writeFd(fd, str)`
| Write a UTF-8 string to a file descriptor.  Used internally to send
  prompt and result lines.

| `nginx.repl.listenRaw(fd, onData)`
| Install a raw-data read handler on `fd`.  For each TCP segment received,
  `onData(chunk)` is called with a `Uint8Array` of the received bytes.
  Unlike `listen()`, data is _not_ split on newlines — suitable for binary
  protocols (e.g. WebSocket) where frame boundaries are in the header.

| `nginx.repl._writeFdRaw(fd, data)`
| Write the raw bytes of `data` (`Uint8Array` or `ArrayBuffer`) to `fd`
  without UTF-8 encoding.  Required for writing binary frame headers that
  contain bytes in the range 0x80–0xFF.

| `req.hijack()`
| Detach the HTTP connection from nginx's connection pool and return
  the raw file descriptor.  The caller is now responsible for I/O and
  closing.
|===

=== Wire Protocol

The client connects with an HTTP GET and the `Upgrade: nginx-repl` header.
After the 101 upgrade response, the connection becomes a line-oriented
plain-text stream:

[source,text]
----
# Client → server
<token> EVAL <javascript-expression>\n

# Server → client
<token> OK [<json-value>]\n      # success
<token> ERR <message>\n          # runtime error
<token> INCOMPLETE\n             # expression needs more input
<token> STACK <frame>\n          # stack trace line (one per frame)
----

Multiline input is handled by re-sending with accumulated lines until the
server replies with something other than `INCOMPLETE`.

=== Embedding the REPL

[source,javascript]
----
// Install a REPL endpoint on /repl
nginx.http.servers[0].locations
    .find(function(l) { return l.path === '/repl'; })
    .handler = function(req) {
        if ((req.headers['upgrade'] || '').toLowerCase() !== 'nginx-repl') {
            return req.respond(400, {}, 'Expected Upgrade: nginx-repl\n');
        }

        var params = req.queryParams;
        var loglevel   = parseInt(params.loglevel   || '0');
        var nginxlevel = parseInt(params.nginxlevel || '6');

        req.respond(101, {
            'upgrade':    'nginx-repl',
            'connection': 'upgrade'
        }, '');

        var fd = req.hijack();
        nginx.repl.attach(fd, loglevel, nginxlevel);
        nginx.repl.listen(fd, function(line) {
            var r = nginx.repl.eval(line);
            if (r.status === 'ok') {
                nginx.repl._writeFd(fd,
                    '- OK' + (r.value !== undefined ? ' ' + r.value : '') + '\n');
            } else if (r.status === 'incomplete') {
                nginx.repl._writeFd(fd, '- INCOMPLETE\n');
            } else {
                nginx.repl._writeFd(fd, '- ERR ' + (r.message || '') + '\n');
            }
        });
    };
----

==== Per-worker `?w=N` targeting and cross-worker relay

[source]
----
ws://host/admin/ws?w=2   ←  browser connects to any worker, but targets worker 2

Worker 0 (accepted the upgrade)
    │  relay.postMessage({type:'eval', targetWorker:2, ...})
    ▼
repl-relay SharedWorker (master-process pthread)
    │  port[2].postMessage({type:'eval', ...})
    ▼
Worker 2  →  nginx.repl.eval(code) + captureConsole()
    │  relay.postMessage({type:'result', replyWorker:0, ...})
    ▼
repl-relay SharedWorker
    │  port[0].postMessage({type:'result', ...})
    ▼
Worker 0  →  nginx.repl._writeFdRaw(fd, wsFrame)
    ▼
Browser  ←  JSON-RPC response
----

The SharedWorker pthread is started *after* daemonisation (via the
`ngx_js_sw_threads_start` function pointer called from
`ngx_master_process_cycle`) to avoid being lost across the daemon double-fork.

=== admin_snapshot_rollback

`js_com_apps/admin_snapshot_rollback/` is a self-contained reference
application.  The packaged version used in demos is
`js_com_demos/A2_Cross_Worker_Coordination/A2.7_Admin_plugin_snapshot_rollback/`.

==== Concept

Operators mutate the live nginx config through the JS COM API (upstream peer
weights, location handlers, added/removed servers, COM scalar properties).
After a successful change, the current state is captured as a *snapshot* — a
JSON ops-list.  Snapshots can be applied, rolled back, squashed, and compacted.

==== Snapshot op families

Three op shapes are supported.  All three can appear in the same snapshot.

[cols="1,3", options="header"]
|===
| Shape | Semantics

| `{"shared": "key", "value": "v"}`
| Write to `nginx.shared`.  Lock-free shared memory; visible to all workers
  instantly without any IPC.

| `{"prop": descriptor, "value": v}`
| COM scalar mutation via a *stable named descriptor* — identifies the target
  COM object by upstream name, peer address, server name, or location path
  (not by array index, which breaks when peers are reordered or locations are
  added/removed).  See _Named descriptor shapes_ below.

| `{"op": "addLocation"\|"removeLocation", "serverName": "…", "pattern": "…", "handler"?: "name"}`
| Structural routing-tree mutation.  Per-worker state — requires the
  SharedWorker fan-out to reach all workers.  `handler` is a name registered
  via `nginx.admin.registerHandler`.
|===

==== Named descriptor shapes for `{prop}`

[cols="2,3", options="header"]
|===
| Shape | Resolves to

| `{"upstream": "u", "property": "p"}`
| upstream-level property (e.g. `zone`)

| `{"upstream": "u", "peer": "host:port", "property": "p"}`
| individual peer property (`weight`, `down`, `maxFails`, …)

| `{"server": "name", "property": "p"}`
| server-level scalar

| `{"server": "name", "location": "/path/", "property": "p"}`
| location scalar (`sendfile`, `root`, `keepaliveTime`, …)

| `{"server": "name", "location": "/path/", "subobject": "proxy", "property": "p"}`
| sub-object property (`proxy.connectTimeout`, `gzip.level`, …)

| `"http.upstreams[0].peers[0].weight"` (string)
| Raw `nginx.set()` path — backward compat; fragile if topology changes.
|===

An optional `"default"` field in a descriptor sets the value used when rolling
back past the first snapshot (resets to the configured baseline).

Props support both scalar and array-valued properties.  The `{prop}` descriptor
can navigate to a sub-object via the `subobject` field before reading or writing
the final property:

[source,javascript]
----
// Array-valued prop: loc.headers.addHeaders
{ server: 'api.local', location: '/api/', subobject: 'headers',
  property: 'addHeaders', default: [] }
----

Identity removal in `compactSnapshot` / `squash` uses `_valEqual` (===  for
scalars, JSON.stringify comparison for objects and arrays) so that two distinct
empty-array values are correctly treated as equal when eliding no-op ops.

==== Plugin configuration (`nginx.use`)

[source,javascript]
----
nginx.use('./admin-plugin', {
    // nginx.shared keys — seeded at startup, captured by createSnapshot()
    keys: { 'feature:beta': '0', 'canary.weight': '0' },

    // COM scalar and array-valued properties — captured and restored
    // by snapshot/rollback.  Use subobject: to navigate one level deeper.
    props: [
        { upstream: 'backend', peer: '10.0.0.1:8080',
          property: 'weight', default: 5 },
        { server: 'api.example.com', location: '/api/', subobject: 'proxy',
          property: 'connectTimeout', default: 5000 },
        // Array-valued prop — requires _valEqual for identity removal
        { server: 'api.example.com', location: '/api/', subobject: 'headers',
          property: 'addHeaders', default: [] }
    ]
});
----

==== `squash` and `compactSnapshot`

`squash` is the standard way to reduce snapshot history after accumulating
many incremental changes:

[source,shell]
----
# Merge a week of daily snapshots into one
curl -X POST http://127.0.0.1:8116/admin/squash \
     -H 'Content-Type: application/json' \
     -d '{"ids":["0001-mon","0002-tue","0003-wed"],"name":"week-01"}'
# → {"id":"0004-week-01"}
----

`compactSnapshot` prunes a single snapshot (useful before exporting or archiving):

[source,shell]
----
curl -X POST http://127.0.0.1:8116/admin/compact/0004-week-01
# → {"id":"0004-week-01","removed":3}
----

==== `location.clearHandler()`

`location.clearHandler()` removes a JS handler and restores the original nginx
C handler.  Used internally by rollback for structural ops.

[source,javascript]
----
loc.handler = function(req) { req.respond(200, {}, 'hello'); };
// ...
loc.clearHandler();   // location.hasHandler → false
----

== External Config Sources and Full Reload

=== Pattern A — File at Startup (`js_preprocess`)

Config data is written to a file by an external process (deploy script,
Kubernetes operator, config management tool) and read synchronously during
nginx startup:

[source,javascript]
----
// /etc/nginx/js/from-file.js
import * as std from 'std';

const cfg = JSON.parse(std.loadFile('/etc/nginx/dynamic-config.json') || '{}');

for (const vhost of (cfg.vhosts || [])) {
    config.write(`
server {
    listen 80;
    server_name ${vhost.domain};
    root /var/www/${vhost.docroot};
    location / { }
}
`);
}
----

This runs on every `nginx -s reload`, so the file is the single source of
truth.

=== Pattern B — Network at Startup (`js_preprocess` + `std.urlGet`)

See the example in <<example-fetching-config-from-a-network-service>>.
Use this pattern for tooling environments where network availability is
guaranteed.  In production, pre-download to a file during a health-check
or init-container step to avoid coupling nginx startup to network
availability.

=== Pattern C — Live Reload via Handler (Zero Downtime)

For changes that do not require a full restart — upstream weights, SSL
certificates, location handlers — apply mutations via the COM from a request
handler:

[source,javascript]
----
// init.js

function applyConfig(cfg) {
    // Update upstream peer weights
    if (cfg.upstreams) {
        for (const [name, peerCfg] of Object.entries(cfg.upstreams)) {
            const up = nginx.http.upstreams.find(u => u.name === name);
            if (!up) continue;
            for (const [addr, w] of Object.entries(peerCfg)) {
                const peer = up.peers.find(p => p.addr === addr);
                if (peer) peer.weight = w;
            }
        }
    }

    // Hot-swap SSL certificates
    if (cfg.ssl) {
        for (const [domain, paths] of Object.entries(cfg.ssl)) {
            const srv = nginx.http.servers.find(s => s.names.includes(domain));
            if (!srv) continue;
            srv.ssl.cert = paths.cert;
            srv.ssl.key  = paths.key;
        }
    }
}

// Admin endpoint: POST the new config JSON.
nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/config/apply')
    .handler = async (req) => {
        const cfg = JSON.parse(await req.readBody());

        await nginx.suspendAllWorkers();
        applyConfig(cfg);
        await nginx.resumeAllWorkers();

        req.json({ applied: true, ts: Date.now() });
    };

// Pull-based reload: a background Worker polls the config service
// periodically and applies changes.
const pollerWorker = new Worker('/etc/nginx/js/config_poller.js');
pollerWorker.onmessage = async (e) => {
    if (e.data.type === 'config-update') {
        await nginx.suspendAllWorkers();
        applyConfig(e.data.config);
        await nginx.resumeAllWorkers();
    }
};
----

[source,javascript]
----
// /etc/nginx/js/config_poller.js — JS Worker thread
import * as std from 'std';

let lastETag = '';

while (true) {
    // Poll every 30 seconds
    os.sleep(30000);

    const res = std.urlGet('http://config-service.internal/v1/nginx-config',
                           { full: true });
    const etag = (res.headers || {})['etag'] || '';

    if (res.status === 200 && etag !== lastETag) {
        lastETag = etag;
        postMessage({ type: 'config-update', config: JSON.parse(res.body) });
    }
}
----

== Third-Party Module Integration

=== Overview

Any nginx module can expose its configuration to the COM by implementing a
small bridge file that reads the module's C config structs and projects them
as JS properties.

This section walks through adding COM support to a hypothetical `ngx_http_mymod`
module with a main-level config struct.

=== Step 1 — Identify the Config Structs

[source,c]
----
/* ngx_http_mymod.h */

typedef struct {
    ngx_flag_t   enable;
    ngx_uint_t   max_entries;
    ngx_str_t    backend_url;
} ngx_http_mymod_main_conf_t;

typedef struct {
    ngx_msec_t   timeout_ms;
    ngx_flag_t   cache;
} ngx_http_mymod_loc_conf_t;

extern ngx_module_t  ngx_http_mymod_module;
----

=== Step 2 — Write the COM Bridge File

Create `ngx_js_com_mymod.c` next to your module sources:

[source,c]
----
/* ngx_js_com_mymod.c */
#include <ngx_config.h>
#include <ngx_core.h>
#include <ngx_http.h>
#include "quickjs.h"
#include "ngx_js.h"
#include "ngx_http_mymod.h"

/*
 * Getter / setter for main-conf properties.
 * 'magic' selects which property (same pattern as NginxRequest).
 */
static JSValue
ngx_js_mymod_main_get(JSContext *ctx, JSValueConst this_val, int magic)
{
    ngx_http_mymod_main_conf_t  *mcf;

    /* Retrieve the main config from the cycle. */
    mcf = ngx_http_cycle_get_module_main_conf(ngx_cycle,
                                              ngx_http_mymod_module);
    if (mcf == NULL) {
        return JS_UNDEFINED;
    }

    switch (magic) {
    case 0: return JS_NewBool(ctx, mcf->enable);
    case 1: return JS_NewUint32(ctx, mcf->max_entries);
    case 2: return JS_NewStringLen(ctx, (char *) mcf->backend_url.data,
                                   mcf->backend_url.len);
    }
    return JS_UNDEFINED;
}

static JSValue
ngx_js_mymod_main_set(JSContext *ctx, JSValueConst this_val,
    JSValueConst val, int magic)
{
    ngx_http_mymod_main_conf_t  *mcf;

    mcf = ngx_http_cycle_get_module_main_conf(ngx_cycle,
                                              ngx_http_mymod_module);
    if (mcf == NULL) {
        return JS_EXCEPTION;
    }

    switch (magic) {
    case 0:
        mcf->enable = JS_ToBool(ctx, val);
        break;
    case 1:
        JS_ToUint32(ctx, &mcf->max_entries, val);
        break;
    /* backend_url is an ngx_str_t backed by pool memory — omit setter
       or implement with careful pool allocation */
    }
    return JS_UNDEFINED;
}

/*
 * Install nginx.http.mymod into ctx.
 * Called from ngx_js_install_nginx_com() during init_conf.
 */
ngx_int_t
ngx_js_com_mymod_install(JSContext *ctx, JSValueConst nginx_obj)
{
    JSValue  http_obj, mymod_obj;

    /* Retrieve the existing nginx.http object. */
    http_obj = JS_GetPropertyStr(ctx, nginx_obj, "http");
    if (JS_IsUndefined(http_obj)) {
        return NGX_ERROR;
    }

    mymod_obj = JS_NewObject(ctx);
    if (JS_IsException(mymod_obj)) {
        JS_FreeValue(ctx, http_obj);
        return NGX_ERROR;
    }

    /* Expose enable / maxEntries / backendUrl as JS properties. */
    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "enable"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_enable", 0,
                             JS_CFUNC_generic_magic, 0),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_set, "set_enable", 1,
                             JS_CFUNC_generic_magic, 0),
        JS_PROP_CONFIGURABLE);

    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "maxEntries"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_maxEntries", 0,
                             JS_CFUNC_generic_magic, 1),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_set, "set_maxEntries", 1,
                             JS_CFUNC_generic_magic, 1),
        JS_PROP_CONFIGURABLE);

    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "backendUrl"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_backendUrl", 0,
                             JS_CFUNC_generic_magic, 2),
        JS_UNDEFINED,   /* no setter — read-only */
        JS_PROP_CONFIGURABLE);

    JS_SetPropertyStr(ctx, http_obj, "mymod", mymod_obj);
    JS_FreeValue(ctx, http_obj);

    return NGX_OK;
}
----

== Resource Protection

=== Worker Memory Limit

`nginx.workerMemoryLimit` caps the QuickJS heap for all JS allocations in a
worker process.  The limit applies on top of nginx's own memory — it measures
only memory allocated through the QuickJS allocator.

[source,javascript]
----
// Set from js_source — applies to every worker after fork().
nginx.workerMemoryLimit = 128 * 1024 * 1024;  // 128 MB per worker

// Read back the configured limit (0 = unlimited).
nginx.log(nginx.INFO, `Memory limit: ${nginx.workerMemoryLimit}`);
----

When a JS allocation exceeds the limit, QuickJS throws `RangeError: out of
memory`.  The worker process remains healthy; the individual request receives
a 500 error.

[source,javascript]
----
loc.handler = (req) => {
    try {
        const huge = new ArrayBuffer(512 * 1024 * 1024);  // exceeds limit
        req.text('allocated\n');
    } catch (e) {
        // e is RangeError: out of memory
        req.respond(503, {}, 'memory limit exceeded, try again\n');
    }
};
----

=== Worker Request Timeout

`nginx.workerRequestTimeout` sets the maximum wall-clock time (in milliseconds)
a single JS handler invocation may consume.  If the handler runs longer than
this (including time spent in a tight synchronous loop), QuickJS fires an
interrupt that aborts the handler.  The worker survives and the request
receives HTTP 500.

[source,javascript]
----
// Allow each handler at most 5 seconds of wall time.
nginx.workerRequestTimeout = 5000;

// Re-configure at runtime from a handler.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/timeout')
    .handler = (req) => {
        const ms = parseInt(req.queryParams.ms);
        if (ms >= 0) nginx.workerRequestTimeout = ms;
        req.text(`timeout is now ${nginx.workerRequestTimeout} ms\n`);
    };
----

=== Error Isolation

JavaScript exceptions in a handler are caught by the module framework and
converted to HTTP 500 responses.  The worker process never crashes due to an
unhandled JS exception.

[source,javascript]
----
loc.handler = (req) => {
    // This exception is caught by the framework — worker stays up.
    throw new Error('deliberate error');
    // Client receives: HTTP/1.1 500 Internal Server Error
};
----

=== What JS Cannot Do

The JS runtime runs inside an nginx worker process (or master, for SharedWorkers)
with the same OS privileges.  The following restrictions apply:

* No access to nginx's internal C memory outside the COM API.  There is no
  `ctypes`, `ffi`, or equivalent.
* No subprocess spawning from handlers or SharedWorkers.  The `os.exec()`
  function from QuickJS `os` is available only in Workers and `js_preprocess`
  scripts, not in nginx event-loop handlers.
* Blocking the event loop with a synchronous tight loop is interrupted by the
  request timeout if `nginx.workerRequestTimeout` is set.
* `Atomics.wait` (blocking) must not be called from the event loop; use
  `Atomics.waitAsync` (non-blocking, returns a Promise) instead.

[NOTE]
====
`removeLocation(path)` is *reversible by default*: it **tombstones** the
location — excluded from the live routing tree but kept (clcf preserved), so
`restoreLocation(path)` brings it back with its original handler and config
intact (identity preserved).  Requests to a tombstoned location fall through as
if it were absent; in-flight 404s emitted while it was hidden are not undone.

Pass `removeLocation(path, {hard: true})` for the legacy irreversible splice
(reclaims a dynamic location's memory when the server is freed; cannot be
restored).  Both forms accept the same pattern grammar as `addLocation`
(`"@name"`, `"= /exact"`, `"^~ /pfx"`, `"~ /re"`, `"~* /re"`, bare prefix).
`removeLocation`/`restoreLocation` also exist on `NginxLocation` (same `srv_op`
constraints as `addLocation`).
