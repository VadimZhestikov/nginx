1. Overview

This guide is a comprehensive reference for the top-level nginx global object that is available in every JavaScript context created by the JS module. It covers all properties and methods directly on nginx.* — from read-only version information to cross-process coordination primitives — plus the two sub-namespaces nginx.cycle and nginx.events that expose core and event-loop configuration.

Related guides for the deeper sub-namespaces:

  • Guide 6 (HTTP) — nginx.http.*

  • Guide 5 (Servers) — HTTP server API

  • Guide 4 (Locations) — HTTP location API

  • Guide 2 (All Workers) — cross-worker coordination

  • Guide 3 (Checkpoint/Restore) — snapshot API

1.1. The nginx global object at a glance

// Read-only metadata
nginx.version                  // "1.27.x" — nginx version string
nginx.cpu_count                // number of logical CPUs

// Logging
nginx.log(level, message)      // write to error log

// Sub-namespaces
nginx.cycle                    // NginxCycle — master-process config
nginx.events                   // NginxEvents — events{} block
nginx.http                     // NginxHttp   — HTTP subsystem
nginx.stream                   // plain object — stream{} subsystem

// Socket provisioning
nginx.createSocket('host:port') // → NginxSocket (Phase A pre-fork / Phase F post-fork)

// Worker bootstrap
nginx.broadcast(fn)            // register per-worker startup callback

// Async timer
nginx.setTimeout(ms)           // → Promise<undefined>

// Acceptance control — single worker (Phase 1)
nginx.suspendAcceptance()      // disable accept events in this worker
nginx.resumeAcceptance()       // re-enable accept events in this worker

// Acceptance control — all workers (Phase 2)
nginx.suspendAllWorkers()      // → Promise<undefined>
nginx.resumeAllWorkers()       // → Promise<undefined>
nginx.withSuspendedAcceptance(fn) // convenience wrapper — suspend → fn() → resume

// Per-worker resource limits (written in config phase)
nginx.workerMemoryLimit        // r/w number — JS heap cap per worker (bytes, 0 = none)
nginx.workerRequestTimeout     // r/w number — per-request JS timeout (ms, 0 = none)

2. nginx.version and nginx.cpu_count

nginx.version:   string  (read-only)
nginx.cpu_count: number  (read-only)

nginx.version — the nginx version string as compiled in, e.g. "1.27.3".

nginx.cpu_count — the number of logical CPUs detected by nginx at startup (the value of ngx_ncpu). Useful for setting nginx.cycle.workers to an appropriate value.

nginx.log(4, `nginx ${nginx.version} on ${nginx.cpu_count} CPUs`);

// Ensure workers = CPU count at startup
nginx.cycle.workers = nginx.cpu_count;

4.3. Setting workers count

nginx.cycle.workers is the only writable cycle property. Write it during config phase (in a js_source script) to adjust the worker count before nginx forks. This is equivalent to the worker_processes directive.

// Auto-size to CPU count (mirrors worker_processes auto;)
nginx.cycle.workers = nginx.cpu_count;
nginx.log(7, `workers set to ${nginx.cycle.workers}`);
Writing workers after the fork has no effect on the running process count. Use it only in config-phase scripts.

4.4. nginx.cycle.sockets[]

A read-only snapshot array listing every listening socket currently active on this cycle. It combines HTTP and stream sockets. Each entry has:

number

Bind port.

ssl

boolean

Whether TLS is active.

boolean

for (const s of nginx.cycle.sockets) {
    nginx.log(8, `${s.address}:${s.port}  ssl=${s.ssl}`);

5. nginx.events (NginxEvents)

The nginx.events object exposes the events {} block configuration.

5.1. Properties

Property Type R/W Description

connections

number

R

worker_connections — maximum simultaneous connections per worker. Read-only because the connection pool is allocated at startup.

use

string

R

Event method name, e.g. "epoll", "kqueue", "select".

multiAccept

boolean

R/W

multi_accept on/off — whether a worker accepts as many connections as possible at once. Default: off.

acceptMutex

boolean

R/W

accept_mutex on/off — whether workers take turns accepting new connections (reduces thundering-herd on old kernels).

acceptMutexDelay

number (ms)

R/W

accept_mutex_delay — delay before trying to acquire the accept mutex.

 
const ev = nginx.events;
nginx.log(8, `events: use=${ev.use}  connections=${ev.connections}`);
nginx.log(8, `  multiAccept=${ev.multiAccept}  acceptMutex=${ev.acceptMutex}`);
nginx.log(8, `  acceptMutexDelay=${ev.acceptMutexDelay} ms`);

5.2. Tuning accept behaviour at startup

// Enable multi_accept for high-connection-rate workloads
nginx.events.multiAccept = true;

// Reduce accept-mutex delay for faster hand-off
nginx.events.acceptMutexDelay = 50;    // ms (default 500)
multiAccept and acceptMutex are read by the event loop at worker start. Changing them post-fork has no effect on accepted connections but will be visible to future reads of the property.

7. nginx.broadcast(fn)

Registers a function to be called in every nginx worker process.

7.1. Signature

nginx.broadcast(fn: function): undefined

7.2. Behaviour

The behaviour differs depending on where broadcast is called:

Context Behaviour

Config phase (js_source top-level code, master process)

fn is appended to the internal nginx.__broadcast_queue. After the master forks, each worker calls every queued function during init_process, with the worker context already set. This lets you register per-worker startup logic that requires worker-only APIs (e.g. nginx.setTimeout, request-level COM objects).

Worker request handler (post-fork)

fn is called immediately in the current worker only. No IPC to other workers is performed.

 
  Config phase (master)                  Workers (after fork)
  ─────────────────────                  ────────────────────
  nginx.broadcast(fn)                    init_process:
        │                                  calls fn() in Worker 0
        │  appended to                     calls fn() in Worker 1
        ▼  __broadcast_queue              calls fn() in Worker 2 …
  [ fn, fn2, … ]

7.3. Use cases

Registering per-worker state — set up a cache, open a file descriptor, or start a background loop that needs to run in every worker:

// Config phase — register once, runs in every worker at startup

nginx.broadcast(function workerInit() {
    // This runs in every worker after fork
    nginx.log(8, 'worker started, setting up local state');

    // Example: start a periodic health-check timer
    async function healthLoop() {
        while (true) {
            await nginx.setTimeout(5000);
            nginx.log(8, 'worker health tick');
        }
    }
    healthLoop();
});

Installing a handler that requires worker context:

// Some handlers need the worker context (e.g. nginx.setTimeout)
// nginx.broadcast defers registration until worker init

nginx.broadcast(function() {
    const loc = nginx.http.servers[0].locations.find(l => l.path === '/slow');
    if (loc) {
        loc.handler = async function(req) {
            await nginx.setTimeout(200);
            req.respond(200, {}, 'done\n');
        };
    }
});
Functions queued via broadcast() in config phase share the same JS runtime and context as the main js_source code. They can close over module-level variables defined in the same script.

8. nginx.setTimeout(ms)

Suspends the current async request handler for ms milliseconds using nginx’s event-loop timer infrastructure.

8.1. Signature

nginx.setTimeout(ms: number): Promise<undefined>

8.2. Behaviour

  • Creates a native ngx_event_t timer in the worker’s event loop.

  • Returns a Promise that resolves when the timer fires.

  • While suspended, the worker’s event loop continues processing other connections and timers normally.

  • After the promise resolves, microtasks are drained and any suspended nginx requests (awaiting the same timer) are finalized.

  request handler
       │
       ├─ await nginx.setTimeout(200)
       │          │
       │          │  worker event loop runs (other requests served)
       │          │
       │     timer fires (200ms later)
       │          │  resolve Promise
       │          │  drain microtasks
       │          │  ngx_js_async_check → finalize request
       │
       └─ execution resumes here

8.3. Worker-only restriction

setTimeout requires a worker context opaque (set after fork). Calling it from config-phase top-level code throws an error. Use nginx.broadcast to defer setTimeout calls to worker startup:

// WRONG — throws at config phase:
// await nginx.setTimeout(100);

// CORRECT — deferred to worker:
nginx.broadcast(async function() {
    await nginx.setTimeout(100);
    nginx.log(8, 'post-startup delay done');
});

8.4. Example: polling loop with back-off

nginx.broadcast(async function() {
    let delay = 1000;
    const MAX_DELAY = 30000;

    while (true) {
        await nginx.setTimeout(delay);
        try {
            checkUpstreamHealth();
            delay = 1000;           // reset on success
        } catch (e) {
            nginx.log(5, `health check failed: ${e.message}`);
            delay = Math.min(delay * 2, MAX_DELAY);
        }
    }
});

9. nginx.suspendAcceptance() and nginx.resumeAcceptance()

Per-worker acceptance control (Phase 1). These are synchronous, instant, and affect only the calling worker.

9.1. Signatures

nginx.suspendAcceptance(): undefined
nginx.resumeAcceptance(): undefined

9.2. Behaviour

suspendAcceptance() — removes all listening socket read events from this worker’s event loop. Incoming TCP connections continue to queue in the OS SYN backlog (up to net.core.somaxconn) and will be accepted once resumeAcceptance() is called. Other workers continue accepting normally.

resumeAcceptance() — re-adds the listening socket read events. No-op if acceptance was not suspended.

Both functions are only callable from a worker process. Calling from config phase throws a TypeError.

9.3. Use case: atomic multi-field mutation

Wrap a batch of COM mutations that must appear atomic from new connections' perspective. Without suspension, a new connection could arrive between two mutations and observe a partially-updated configuration:

function atomicUpdate(req) {
    nginx.suspendAcceptance();
    try {
        // Both mutations applied before any new connection is accepted
        nginx.http.upstreams[0].peers[0].weight = 200;
        nginx.http.servers[0].locations
              .find(l => l.path === '/api').root = '/var/www/api-v2';
    } finally {
        nginx.resumeAcceptance();
    }
    req.respond(200, {}, 'updated\n');
}
  Worker N
  ├─ nginx.suspendAcceptance()   ← remove listen read events
  │        (new conns queue in OS backlog)
  │
  ├─ mutation 1 (upstream weight)
  ├─ mutation 2 (location root)
  │
  └─ nginx.resumeAcceptance()    ← restore listen read events
           (queued conns now accepted with updated config)
Because this is per-worker, parallel workers may accept connections with the old config while this worker is suspended. For cluster-wide atomicity use suspendAllWorkers() instead.

10. nginx.suspendAllWorkers() and nginx.resumeAllWorkers()

Cross-worker acceptance control (Phase 2). Asynchronous; coordinates through the manager process.

10.1. Signatures

nginx.suspendAllWorkers(): Promise<undefined>
nginx.resumeAllWorkers():  Promise<undefined>

10.2. Behaviour

Both functions return a Promise that resolves after every worker in the nginx pool has acknowledged the suspend/resume command.

Protocol:

  Worker 0 (request handler)
       │
       ├─ await nginx.suspendAllWorkers()
       │          │
       │          ├─ sends NGX_JS_MGR_CMD_SUSPEND_ACCEPT to manager
       │          │
       │   Manager process
       │   ├─ broadcasts suspend command to Worker 0, 1, 2 …
       │   ├─ waits for acks (500 ms timeout)
       │   └─ writes 1-byte reply on reply_fd
       │          │
       │          └─ reply_fd read event fires → resolve Promise
       │
       ├─ all workers now suspended
       ├─ perform cluster-wide COM mutations
       │
       └─ await nginx.resumeAllWorkers()   (same protocol)

10.3. Timeout

If not all workers ack within 500 ms the manager resolves anyway so the calling worker is not stuck. Slow workers will resume acceptance on their own when the next resumeAllWorkers broadcast arrives.

10.4. nginx.withSuspendedAcceptance(fn)

A convenience wrapper defined in pure JavaScript during ngx_js_com_init:

nginx.withSuspendedAcceptance = async function(fn) {
    await nginx.suspendAllWorkers();
    try {
        await fn();
    } finally {
        await nginx.resumeAllWorkers();
    }
};

Use this instead of the raw pair to guarantee resumeAllWorkers is called even if fn throws.

10.5. Example: cluster-wide atomic server reconfiguration

async function hotReloadServers(req) {
    await nginx.withSuspendedAcceptance(async () => {
        // All workers suspended; no new connections accepted anywhere

        // Remove old API server
        nginx.http.removeServer('api-v1.example.com');

        // Add new API server
        const srv = nginx.http.addServer('api-v2.example.com');
        srv.addLocation('/').handler = apiV2Handler;

        // Rebuild routing hash
        nginx.http.rebuildVhostDispatch();
    });
    // All workers resumed with new config

    req.respond(200, {}, 'hot reload complete\n');
}
  Worker 0 (request handler)
       │
       ├─ await nginx.withSuspendedAcceptance(async () => {
       │          │
       │          │  suspendAllWorkers()
       │          │    → manager broadcasts suspend → all workers ack
       │          │
       │          ├─ removeServer('api-v1.example.com')
       │          ├─ addServer('api-v2.example.com') + addLocation
       │          ├─ rebuildVhostDispatch()
       │          │
       │          │  resumeAllWorkers()
       │          │    → manager broadcasts resume → all workers ack
       │          │
       │          └─ Promise resolves
       │
       └─ req.respond(200, {}, 'done\n')
Worker 0 is also suspended during this window (it cannot accept new connections). In-flight requests on Worker 0 continue executing.

11. nginx.createSocket(address)

Creates a TCP listening socket. See Guide 6 for the full NginxSocket API and the Phase A-D provisioning pipeline.

11.1. Signature

nginx.createSocket(address: string): NginxSocket

11.2. Phase A vs Phase F

Phase Context Behaviour

A (pre-fork)

Config phase (js_source top-level code)

Calls socket() + bind() + listen() directly in the master. All workers inherit the fd on fork.

F (post-fork)

Worker request handler

Sends the bind address to the manager thread via AF_UNIX + SCM_RIGHTS. The manager creates the socket and returns the fd to the requesting worker. Use sock.broadcast() to share it with sibling workers.

 
// Config phase (Phase A)
const httpSock   = nginx.createSocket('0.0.0.0:8080');
const httpListen = nginx.http.attach(httpSock);

const streamSock   = nginx.createSocket('0.0.0.0:5000');
const streamListen = nginx.stream.attach(streamSock);

12. nginx.workerMemoryLimit and nginx.workerRequestTimeout

Two writable properties that configure per-worker resource limits. They are read by init_process (after fork) and cannot be changed at runtime.

12.1. workerMemoryLimit

nginx.workerMemoryLimit: number  (bytes, 0 = no limit)

Caps the QuickJS heap size for each worker’s JS runtime. After fork, init_process calls JS_SetMemoryLimit(rt, workerMemoryLimit) if the value is non-zero.

// Limit each worker to 128 MB of JS heap
nginx.workerMemoryLimit = 128 * 1024 * 1024;

12.2. workerRequestTimeout

nginx.workerRequestTimeout: number  (ms, 0 = no timeout)

Caps the wall-clock time a single JS request handler invocation may run. After fork, init_process installs a QuickJS interrupt handler that checks a monotonic-clock deadline set around each JS_Call in the content handler. If the deadline passes, the interrupt handler throws a SyntaxError to terminate the runaway script.

// Kill any request handler that runs for more than 5 seconds
nginx.workerRequestTimeout = 5000;
The timeout applies to synchronous execution time within a single JS_Call invocation. Async handlers that await nginx.setTimeout() are not penalised for the wall-clock time spent waiting; the deadline is reset at each resume.

13.4. Example 4: Graceful config reload with cluster-wide suspension

A handler that reloads routing config from an external source and applies it atomically across all workers:

async function reloadConfig(req) {
    let newRoutes;
    try {
        // Fetch new routing table (async, workers still accepting)
        newRoutes = await fetchRoutingTable();
    } catch (e) {
        req.respond(500, {}, `fetch failed: ${e.message}\n`);
        return;
    }

    await nginx.withSuspendedAcceptance(async () => {
        // Validate before applying
        for (const { host, path, upstream } of newRoutes) {
            if (!nginx.http.servers.find(s => s.names.includes(host))) {
                nginx.http.addServer(host);
            }
            const srv = nginx.http.servers.find(s => s.names.includes(host));
            const loc = srv.addLocation(path);
            loc.proxyPass = upstream;
        }
        nginx.http.rebuildVhostDispatch();
    });

    req.respond(200, {}, `reload complete (${newRoutes.length} routes)\n`);
}

15. Design notes

15.1. Why nginx.cycle.workers is writable

workers is the only writable NginxCycle property because it modifies the worker_processes field in ngx_core_conf_t — a plain integer read at fork time. All other cycle fields are either structural (memory pool layouts, allocated arrays) or already computed at config parse time in ways that cannot be safely changed after-the-fact.

15.2. broadcast() and the init_process hook

JavaScript code evaluated at config phase (inside js_source) runs in the master process before any workers fork. Functions in __broadcast_queue are stored as JS values in the shared context. Because workers inherit the JS runtime via copy-on-write after fork, the queue is accessible in all workers. init_process iterates the queue and calls each function with the worker context opaque already installed, so nginx.setTimeout and request-level COM objects work correctly inside broadcast callbacks.

15.3. withSuspendedAcceptance is pure JS

withSuspendedAcceptance is not a C function — it is a short async function defined in a script string evaluated during ngx_js_com_init. This makes it easy to inspect or override: nginx.withSuspendedAcceptance can be reassigned from JS code for testing purposes.

15.4. workerRequestTimeout and QuickJS interrupts

The timeout is implemented with JS_SetInterruptHandler. Before each JS_Call into a request handler, the C layer records clock_gettime(CLOCK_MONOTONIC) + workerRequestTimeout as a deadline. The interrupt handler fires periodically (QuickJS checks at branch-back points) and compares the current time to the deadline. If exceeded it returns 1, which causes QuickJS to throw a SyntaxError("Script interrupted"). Async suspend points (await) do not advance the deadline; the deadline is re-stamped each time the event loop resumes the handler from a timer or I/O event.
