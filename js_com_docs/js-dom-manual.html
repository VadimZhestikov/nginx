1. Introduction

1.1. What NGINX JS DOM Is

NGINX is deliberately static: its configuration is read once at startup (or reload) and compiled into kernel-level data structures. This rigidity is a feature — it makes nginx predictable, fast, and easy to reason about — but it creates friction whenever runtime adaptability is required: upstream weights that need to track backend health scores, virtual hosts generated from a tenant database, SSL certificates that rotate on a schedule, or request routing rules that depend on live feature-flag state.

NGINX JS DOM embeds QuickJS (a lightweight ES2020+ JavaScript engine) directly into nginx and exposes the entire nginx configuration as a structured JavaScript object tree called the Configuration Object Model (COM). Through the COM, JavaScript can:

  • Read the full live configuration of every module in every server and location.

  • Write configuration properties — upstream peer weights, SSL certificates, location directives, gzip settings, and much more — with immediate effect, either for the current worker or atomically for all workers at once.

  • Generate server and location blocks at parse time, before nginx has even finished reading its configuration file, and at run-time, when traffic events are processed by nginx workers in their nginx event loops.

  • Handle requests in JavaScript, using the same event-driven async model as nginx itself.

  • Offload CPU-intensive work to background threads (Workers) without blocking the nginx event loop.

  • Maintain shared mutable state across all nginx worker processes using SharedWorkers and SharedArrayBuffers.

The result is an nginx that can be programmed rather than merely configured — without restarting, without patching C code, and without sacrificing the performance or stability of the core server.

1.2. Intended Audience

This manual assumes:

  • Familiarity with nginx configuration syntax and core concepts (workers, upstreams, locations, modules). See the NGINX Beginner’s Guide and the full module reference if you need a refresher.

  • Working knowledge of modern JavaScript (ES2020): async/await, Promises, import/export, SharedArrayBuffer, Atomics. See the ECMAScript 2020 specification or any ES2020 reference.

You do not need to know C or QuickJS internals to use the JS DOM API.

1.3. A Map of the Moving Parts

The sections that follow cover these components:

Component What it gives you

js_preprocess

Runs JavaScript during config parsing; the script writes config text back into the parser. Use it to generate server/location blocks from files, environment variables, or external sources.

js_init_http

Runs JavaScript after the http {} block is parsed but before directives are merged. Can read already-parsed servers and inject new ones.

js_source

Evaluates JavaScript in the master process after all config has been parsed. This is where you install request handlers, set up Workers and SharedWorkers, and perform any pre-fork initialisation.

Request handlers

JavaScript async functions assigned to location.handler. Each request runs through the nginx event loop; await suspends the handler without blocking any other request.

COM

The nginx global object tree. Read live config values; write mutations that take effect immediately.

Workers

Standard Web Worker API. A per-nginx-worker background thread for CPU-bound work. Does not block the event loop.

SharedWorkers

A single long-lived thread in the master process, connected to every nginx worker via UNIX sockets. The canonical place for mutable state that must be consistent across all workers.

SharedArrayBuffers + Atomics

Binary shared-memory regions (MDN reference) accessible from any thread with zero copy. Combined with Atomics, they enable lock-free counters, mutexes, and condition variables.

Bootstrap functions

nginx.createHttp() / nginx.createStream() — instantiate the HTTP or stream module entirely from JavaScript, without an http {} or stream {} block in nginx.conf. Combine with nginx.http.addServer() and nginx.createSocket() for a fully JS-defined server topology.

Master/worker scripting

nginx.on(event, fn) hooks into master lifecycle events (worker spawn, reload, SIGUSR1, …). nginx.sendToWorker() / nginx.broadcastToWorkers() push messages from master to workers; nginx.sendToMaster() sends from a worker back to the master.

nginx.repl

An interactive JavaScript REPL that evaluates expressions inside a running nginx worker over a plain HTTP upgrade connection. Useful for live introspection, ad-hoc mutations, and debugging.

location.clearHandler()

Removes a previously installed JS content handler and restores the original nginx C handler for that location. Used by snapshot/rollback to undo handler changes atomically.

Accept control

nginx.suspendAcceptance() / nginx.suspendAllWorkers() — pause connection acceptance during a mutation window, then resume.

Resource limits

nginx.workerMemoryLimit and nginx.workerRequestTimeout cap heap usage and CPU time per request; JS exceptions are caught; the worker survives.

2.1. Lifecycle Overview

├─ Config file parsing begins (ngx_conf_parse)
│   │
│   ├── js_preprocess /gen.js ◄── STAGE 1: runs immediately, mid-parse
│   │      • Ephemeral JS runtime (freed after script returns)
│   │      • config.write(text) injects text back into the parser
│   │      • nginx.http, nginx.stream, etc. do NOT exist yet
│   │
│   ├── ... rest of nginx.conf parsed (servers, locations, upstreams) ...
│   │
│   └── js_init_http /init.js ◄── STAGE 2: runs after http{} block parses
│          • Ephemeral runtime, scoped to this directive
│          • config.write(text) still works; new servers get full merge treatment
│          • nginx.http.servers[] is readable (servers parsed before this line)
│
├─ init_conf (master process)  ◄── STAGE 3: js_source scripts evaluated here
│   │
│   ├── JS runtime + context created (persists, will be inherited by workers)
│   ├── All js_source files evaluated in order
│   │      • Install location.handler = fn assignments
│   │      • Create SharedWorkers (they start running immediately)
│   │      • Set nginx.workerMemoryLimit / nginx.workerRequestTimeout
│   │      • Any other pre-fork setup
│   └── SharedWorker threads spawned; channels to each future worker prepared
│
├─ fork() × worker_processes  ◄── STAGE 4: worker processes created
│   │
│   └── init_process (per worker)
│          • JS runtime inherited via copy-on-write
│          • No re-evaluation of scripts; all handlers already installed
│          • Worker attaches its UNIX socket channels to each SharedWorker
│
└─ Event loop (per worker)     ◄── STAGE 5: runtime
        │
        └── HTTP/stream request arrives
               • location.handler(req) called
               • await suspends handler; event loop serves other requests
               • COM reads/writes apply to THIS worker's copy (or all, with
                 suspendAllWorkers)
               • req.json() / req.respond() sends the response

2.2. Process and Thread Topology

  ┌─────────────────────────────────────────────────────────────────┐
  │  Master process                                                 │
  │                                                                 │
  │  ┌──────────────────────┐  ┌──────────────────────┐             │
  │  │  SharedWorker A      │  │  SharedWorker B      │             │
  │  │  (pthread)           │  │  (pthread)           │             │
  │  │  long-lived JS state │  │  e.g. rate-limiter   │             │
  │  └──────────────────────┘  └──────────────────────┘             │
  └────────────────────────┬────────────────────────────────────────┘
                           │  AF_UNIX SEQPACKET
                           │  each worker gets one channel per SharedWorker
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │  Worker 0    │  │  Worker 1    │  │  Worker N    │
  │  JS Runtime  │  │  JS Runtime  │  │  JS Runtime  │
  │  (CoW copy)  │  │  (CoW copy)  │  │  (CoW copy)  │
  │  Event loop  │  │  Event loop  │  │  Event loop  │
  │  JS Workers  │  │  JS Workers  │  │  JS Workers  │
  └──────────────┘  └──────────────┘  └──────────────┘

Key properties of this topology:

  • Each nginx worker process has its own independent JS runtime. QuickJS is not thread-safe; no runtime is ever shared between processes.

  • Workers inherit the master’s runtime via copy-on-write after fork(). Scripts do not need to be re-evaluated; all handler functions, SharedWorker references, and global variables are ready immediately.

  • SharedWorkers run in the master process as pthreads, outside any worker. Each worker communicates with a SharedWorker over a dedicated UNIX socket channel. This is the only channel through which workers can share mutable JS state.

  • JS Workers (lowercase) are pthreads spawned inside a worker process. They exist to offload work from the event loop and are private to their nginx worker.

3. Quick Start

This section goes from "hello world" to "live upstream rebalancing" in four steps, each building on the previous one.

3.1. Hello World — Minimal (No http{} block)

The most compact nginx JS DOM server needs only a js_source directive and an events {} block. Everything else — the HTTP module, socket, virtual server, and location handler — is created from JavaScript at init time:

# nginx.conf
js_source /etc/nginx/js/hello_world.js;

events { }
// hello_world.js — evaluated once in the master process after config parsing.
// Creates the entire server topology from JS; no http{}/server{}/location{}
// blocks are needed in nginx.conf.

(function () {

    // 1. Bootstrap the HTTP module (equivalent to an empty http{} block).
    //    Pass any http-level directives as a string argument.
    nginx.createHttp('access_log /var/log/nginx/access.log;');

    // 2. Create a new virtual server.
    var srv = nginx.http.addServer('hello-world.local');

    // 3. Add a location and install the JS content handler inline.
    srv.addLocation('/hello').handler = function (req) {
        req.respond(200, { 'content-type': 'text/plain' },
                    'JS COM: Hello World!\n');
    };

    // 4. Bind a TCP socket, attach it to the HTTP module,
    //    and register the server on that listener.
    var sock = nginx.createSocket('0.0.0.0:8080');
    nginx.http.attach(sock).addServer(srv);

})();

3.2. Hello World — Classic (with http{} block)

When http {} is already present in nginx.conf, just find the location placeholder and assign a handler function:

# nginx.conf
js_source /etc/nginx/js/init.js;

events { }

http {
    server {
        listen 80;
        location /hello { }   # placeholder — handler installed from JS
    }
}
// /etc/nginx/js/init.js
// This file is evaluated once in the master process after config parsing.
// All location.handler assignments made here are inherited by every worker.

const loc = nginx.http.servers[0].locations.find(l => l.path === '/hello');

loc.handler = (req) => {
    // req is a NginxRequest object.  text() is a convenience shorthand
    // for respond(200, {'Content-Type': 'text/plain'}, body).
    req.text('Hello from JS DOM!\n');
};

3.3. Reading Request Data

// Read everything you might want from an incoming request.

loc.handler = async (req) => {
    // Basic identity
    const method  = req.method;          // "GET", "POST", …
    const uri     = req.uri;             // "/hello"
    const args    = req.args;            // raw query string: "a=1&b=2"
    const params  = req.queryParams;     // {a: "1", b: "2"}
    const scheme  = req.scheme;          // "http" or "https"
    const host    = req.host;            // "example.com"

    // Network info
    const client  = req.remoteAddr;      // "203.0.113.42"
    const port    = req.remotePort;      // 54321
    const server  = req.serverAddr;      // "192.0.2.1"

    // Headers (read-only object; keys are lowercased)
    const ua      = req.headers['user-agent'];
    const ct      = req.contentType;     // shorthand for content-type header

    // Cookies: {name: "value", …}
    const session = req.cookies['session_id'];

    // nginx variables — readable and writable via req.variables
    const xff     = req.variables['http_x_forwarded_for'];
    req.variables['my_custom_var'] = 'set-from-js';

    // Request body (requires await — nginx reads it asynchronously)
    const body    = await req.readBody();  // returns string

    req.json({
        method, uri, client, ua, session,
        bodyLength: body.length
    });
};

3.4. Async Fetch and Transform

// Non-blocking upstream call.  While this handler awaits, the nginx event
// loop freely serves other requests on this worker.

loc.handler = async (req) => {
    // req.fetch() performs an HTTP subrequest through nginx's upstream
    // machinery.  It returns a Promise that resolves with a Response object.
    const res  = await req.fetch('http://api.internal/v1/prices');
    const data = await res.json();

    // Apply transformation
    const adjusted = data.items.map(item => ({
        ...item,
        price: (item.price * 1.10).toFixed(2)   // add 10% margin
    }));

    req.json({ items: adjusted });
};

3.5. Live Upstream Rebalancing

// An admin endpoint that atomically updates upstream peer weights across
// all workers — no nginx restart, no dropped connections.

const adminLoc = nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/upstream/rebalance');

adminLoc.handler = async (req) => {
    const body    = await req.readBody();
    const weights = JSON.parse(body);   // { "192.0.2.10:8080": 5, "192.0.2.11:8080": 10 }

    // Step 1: pause all workers so the change is seen atomically.
    await nginx.suspendAllWorkers();

    // Step 2: apply weights.
    const peers = nginx.http.upstreams
        .find(u => u.name === 'backend').peers;

    for (const peer of peers) {
        if (weights[peer.addr] !== undefined) {
            peer.weight = weights[peer.addr];
        }
    }

    // Step 3: resume — all workers pick up the new weights immediately.
    await nginx.resumeAllWorkers();

    req.json({ applied: true, peers: peers.map(p => ({addr: p.addr, weight: p.weight})) });
};

4. Request Handlers

4.1. Installing a Handler

A location handler is a JavaScript function assigned to location.handler during js_source evaluation (init_conf time):

nginx.http.servers[0].locations
    .find(l => l.path === '/api')
    .handler = async (req) => { ... };

The function receives one argument — a NginxRequest object — and may be synchronous or async. A location that has no JS handler falls through to nginx’s normal content processing (proxy, static files, etc.).

4.3. Async Handler Lifecycle

nginx worker event loop
│
├─ accept() → new connection
│
├─ HTTP request parsed
│
├─ location matched → location.handler(req) called
│       │
│       ├─ [sync path] req.json(data)
│       │       └─► response buffered → written to socket → done
│       │
│       └─ [async path] await something
│               │
│               │  Handler suspended.  Worker event loop continues:
│               │    • accepts new connections
│               │    • runs other handlers
│               │    • processes timers and upstream responses
│               │
│               ▼  event fires (timer / upstream / Worker message)
│          Promise resolves; handler resumes from the await point
│               │
│               └─► req.json(data) → done
│
└─ (next event)
Multiple async handlers can be suspended concurrently on the same worker. Each nginx worker runs a single-threaded event loop; async handlers cooperate by yielding at every await point, allowing other requests to be accepted and served in between. Use Workers or SharedWorkers when you need true CPU parallelism or need to share mutable state across workers.

4.4. Streaming Responses

loc.handler = async (req) => {
    // Send status + headers, then stream the body in chunks.
    req.writeHead(200, {'Content-Type': 'text/event-stream',
                        'Cache-Control': 'no-cache'});

    for (let i = 0; i < 5; i++) {
        req.write(`data: event ${i}\n\n`);
        await req.sleep(200);      // 200 ms between events, non-blocking
    }

    req.finish();
};

4.5. Subrequest Fan-Out

// Fire three upstreams in parallel and merge results.
loc.handler = async (req) => {
    const [a, b, c] = await Promise.all([
        req.subrequest('/internal/prices'),
        req.subrequest('/internal/stock'),
        req.subrequest('/internal/ratings'),
    ]);

    req.json({
        prices:  await a.json(),
        stock:   await b.json(),
        ratings: await c.json(),
    });
};

4.6. Header and Body Filters

Filters are JavaScript functions that run in the nginx filter chain. They are installed on a location object:

// Header filter — modify response headers before they leave nginx
loc.headerFilter = (req, headers) => {
    headers['X-Powered-By'] = 'NGINX JS DOM';
    delete headers['Server'];
    return headers;
};

// Body filter — transform response body chunks
loc.bodyFilter = (req, chunk, isLast) => {
    // Replace "foo" with "bar" in every body chunk
    return chunk.replace(/foo/g, 'bar');
};

Filters run in priority order (lower number = earlier in chain, default priority 50).

6. Dynamic Reconfiguration

6.1. Scope 1 — This Worker Only

The simplest mutations happen directly in a handler with no coordination. The change takes effect immediately for all subsequent requests on this worker. Other workers retain their own CoW copy unchanged.

// Use-case: A/B flag toggle via admin endpoint, applied to this worker.
// Fine for experiments where eventual consistency across workers is acceptable.

nginx.http.servers[0].locations
    .find(l => l.path === '/admin/toggle-gzip')
    .handler = (req) => {
        // Toggle gzip for the /api location on THIS worker only
        const apiLoc = nginx.http.servers[0].locations
            .find(l => l.path === '/api');
        apiLoc.gzip = !apiLoc.gzip;
        req.text(`gzip is now ${apiLoc.gzip}`);
    };

6.2. Scope 2 — All Workers Atomically

For changes that must be consistent across every worker simultaneously, use suspendAllWorkers / resumeAllWorkers.

Worker A (handler)
    │
    ├─ await suspendAllWorkers()
    │       │
    │       ├─► sends coordination signal to Workers B, C, …
    │       │     Each worker finishes its current request, then:
    │       │     • stops calling accept()
    │       │     • sends ACK
    │       │
    │       └─ resolves when ALL workers have ACK'd
    │
    ├─ [mutation window]
    │       • Direct COM writes apply to Worker A's copy
    │       • SharedWorker broadcast distributes the same data to B, C, …
    │         (each worker applies it from its own onmessage handler)
    │
    ├─ await resumeAllWorkers()
    │       └─► all workers call ngx_enable_accept_events() and resume
    │
    └─ respond
adminLoc.handler = async (req) => {
    const newPeers = JSON.parse(await req.readBody());

    await nginx.suspendAllWorkers();

    // Apply to this worker
    const peers = nginx.http.upstreams[0].peers;
    newPeers.forEach((p, i) => {
        if (peers[i]) peers[i].weight = p.weight;
    });

    await nginx.resumeAllWorkers();

    req.json({ ok: true });
};

6.3. Scope 3 — Add / Remove Servers and Locations

addServer, removeServer, addLocation enable structural mutations — adding or removing routing entries at runtime.

// Tenant onboarding: create a new vhost live, no restart.

nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/tenant/create')
    .handler = async (req) => {
        const body   = JSON.parse(await req.readBody());
        const domain = body.domain;

        await nginx.suspendAllWorkers();

        // Create the new server
        const srv = nginx.http.addServer(domain);
        srv.listen.push('80');

        // Add a root location with a JS handler
        const loc = srv.addLocation('/');
        loc.handler = (r) => {
            r.text(`Welcome to ${domain}!\n`);
        };

        // Rebuild the server_name dispatch hash so the new Host: domain routes
        // correctly to our new server.
        nginx.http.rebuildVhostDispatch();

        await nginx.resumeAllWorkers();

        req.json({ created: domain });
    };
// Remove a tenant server (e.g. account deleted).
nginx.http.removeServer('ex-tenant.example.com');
nginx.http.rebuildVhostDispatch();
rebuildVhostDispatch() must be called after any change to server names. Without it the Host-based routing hash is stale and requests will be routed to the wrong server.

6.4. Scope 4 — Per-Request Config Snapshot

The location.setWriteMode("local") API creates a copy of the location’s config struct scoped to the current request. The global struct is untouched; other concurrent requests see the original values.

loc.handler = async (req) => {
    // Write only to a private snapshot for this request.
    req.location.setWriteMode('local');

    // This change is visible only inside this handler invocation.
    req.location.root = '/var/www/' + req.getVar('user_dir');
    req.location.gzip = false;

    // ... process request ...
    // When the request pool is freed, the snapshot is discarded automatically.
};

6.5. Hot SSL Certificate Swap

// Admin handler: reload the TLS certificate from disk, zero downtime.
// New connections after this call use the new certificate;
// in-flight TLS sessions are unaffected.

adminLoc.handler = async (req) => {
    const body = JSON.parse(await req.readBody());
    const srv  = nginx.http.servers.find(s => s.names.includes(body.domain));
    if (!srv) { req.respond(404, {}, 'unknown domain'); return; }

    await nginx.suspendAllWorkers();
    srv.ssl.cert = body.certPath;
    srv.ssl.key  = body.keyPath;
    await nginx.resumeAllWorkers();

    req.json({ reloaded: body.domain });
};

7. Pre-Fork Initialization

7.1. js_preprocess — Config Injection During Parse

js_preprocess evaluates a JS script during ngx_conf_parse, at the exact point where the directive appears in the config file. The script receives a global config object with a single method:

config.write(text) — feeds text back into the nginx config parser exactly as if it had appeared inline at this position.

This happens before init_conf, so nginx.http, nginx.stream, and the full COM are not available. The std and os QuickJS modules are available for file and OS access.

nginx.conf parse reaches js_preprocess /gen.js
        │
        ├─ New JS runtime created (isolated, short-lived)
        │
        ├─ gen.js evaluated
        │       • Can read files:    std.loadFile('/etc/conf.json')
        │       • Can read env:      std.getenv('APP_ENV')
        │       • Can run commands:  os.exec([...])
        │       • Can call config.write(text)
        │
        ├─ Runtime freed
        │
        └─ Injected text re-enters the parser as if it were inline
               → full http{}/server{}/location{} blocks allowed
               → directives go through normal merge/optimize_servers treatment

7.1.1. Example: Server Blocks from a JSON File

// /etc/nginx/js/gen.js
// Generates one server {} block per tenant from a JSON config file.
// Runs once at startup (and again on `nginx -s reload`).

import * as std from 'std';

// Read tenant definitions from a JSON file.
const raw     = std.loadFile('/etc/nginx/tenants.json');
const tenants = JSON.parse(raw);

let out = '';
for (const t of tenants) {
    out += `
server {
    listen 80;
    server_name ${t.domain};
    root /var/www/${t.id};
    location / { }
}
`;
}

config.write(out);
# nginx.conf

events { }
http {
    # servers from gen.js appear here as if written manually
}

7.1.2. Example: Conditional SSL Config

// Enable SSL only if the certificate file actually exists.
import * as os from 'os';

const certPath = '/etc/ssl/certs/site.pem';
const keyPath  = '/etc/ssl/private/site.key';

7.1.3. Example: Fetching Config from a Network Service

js_preprocess runs synchronously inside the C parse loop. There is no event loop at this stage, so the standard req.fetch() API is unavailable. The std.urlGet() function (QuickJS std library) works around this by spawning curl as a child process and blocking until the response arrives.

curl must be installed on the system.

// /etc/nginx/js/fetch-config.js
// Download upstream configuration from a config service at startup.
// Uses std.urlGet() which shells out to curl — blocking and synchronous.

import * as std from 'std';

const res = std.urlGet('http://config-service.internal/v1/nginx-upstreams',
                       { full: true });  // { status, headers, body }

if (res.status !== 200) {
    // Fail loudly — a bad config is worse than a failed start.
    throw new Error(`Config service returned ${res.status}`);
}

const cfg = JSON.parse(res.body);

// Generate upstream{} blocks
let out = '';
for (const up of cfg.upstreams) {
    out += `upstream ${up.name} {\n`;
    for (const peer of up.peers) {
        out += `    server ${peer.addr} weight=${peer.weight};\n`;
    }
    out += `}\n`;
}
config.write(out);
std.urlGet always spawns a curl subprocess. For reliability in production, prefer writing config data to a file during a pre-start hook and reading it with std.loadFile(), keeping js_preprocess independent of network availability at start time. The network fetch pattern is useful for short-lived tooling or environments where the config service is guaranteed to be reachable.

7.1.4. Multiple js_preprocess Directives

Multiple js_preprocess directives are allowed; each runs in its own isolated runtime in declaration order:

7.2. js_init_http — Post-Parse Server Injection

js_init_http fires after the entire http {} block has been parsed but before directive merging takes place. It provides both config.write() and a read-only view of nginx.http.servers[] — the servers parsed before the js_init_http directive.

│
└── http {
    │
    ├── server { server_name primary.example.com; ... }

8. Workers (JS Web Workers)

JS Workers are background pthreads spawned inside an nginx worker process. They implement the standard Web Worker API and are the correct tool when a request needs to perform CPU-intensive computation without blocking the event loop.

Each nginx worker process has its own set of Workers; they are not shared between nginx workers.

8.1. Basic Worker Pattern

// init.js (js_source)

// Spawn a Worker thread for CPU-intensive prime computation.
// Workers are created once in js_source and reused across all requests.
const computeWorker = new Worker('/etc/nginx/js/prime_worker.js');

nginx.http.servers[0].locations
    .find(l => l.path === '/primes')
    .handler = async (req) => {
        const n = parseInt(req.queryParams.n) || 100;

        // Send work to the Worker thread and await the result.
        // While awaiting, the event loop is free to serve other requests.
        const result = await new Promise(resolve => {
            computeWorker.onmessage = e => resolve(e.data);
            computeWorker.postMessage({ n });
        });

        req.json(result);
    };
// /etc/nginx/js/prime_worker.js — runs in a separate pthread

function sieve(n) {
    const composite = new Uint8Array(n + 1);
    for (let i = 2; i * i <= n; i++) {
        if (!composite[i]) {
            for (let j = i * i; j <= n; j += i) composite[j] = 1;
        }
    }
    return Array.from({length: n - 1}, (_, i) => i + 2).filter(i => !composite[i]);
}

// Worker message loop
onmessage = (e) => {
    const primes = sieve(e.data.n);
    postMessage({ count: primes.length, largest: primes[primes.length - 1] });
};
HTTP request → nginx worker event loop
        │
        ├─ handler called; sends postMessage to Worker thread
        │       │
        │       ▼
        │   Worker pthread
        │   (independent JS runtime)
        │   sieve(n)  ← CPU-bound, runs without blocking event loop
        │       │
        │       ▼
        │   postMessage(result)
        │       │
        │       ▼  onmessage event delivered to event loop
        │
        └─ Promise resolves; req.json(result) → response sent

8.2. Transferring ArrayBuffers (Zero Copy)

Passing an ArrayBuffer by transfer moves ownership; the sender can no longer access it. Use this for large binary payloads:

// Compress a large buffer in a Worker thread, transfer result back.
const compressionWorker = new Worker('/etc/nginx/js/compress_worker.js');

loc.handler = async (req) => {
    const body   = await req.readBody();
    const input  = new TextEncoder().encode(body).buffer;  // ArrayBuffer

    const compressed = await new Promise(resolve => {
        compressionWorker.onmessage = e => resolve(e.data.buf);
        // Transfer 'input' — zero copy, Worker takes ownership
        compressionWorker.postMessage({ buf: input }, [input]);
    });

    req.setHeader('Content-Encoding', 'deflate');
    req.respond(200, {}, compressed);
};

8.3. Worker std and os Modules

Workers have access to the QuickJS standard library:

import * as std from 'std';
import * as os  from 'os';

onmessage = (e) => {
    // Blocking file read — safe in a Worker (doesn't block the event loop)
    const data = std.loadFile(e.data.path);

};

9. SharedWorkers

9.1. Concept and Use Cases

A SharedWorker is a single long-lived pthread running in the nginx master process, connected to every nginx worker via dedicated UNIX socket channels. Unlike JS Workers (one per nginx worker), there is exactly one SharedWorker instance regardless of the worker_processes count.

This makes SharedWorkers the canonical location for:

  • Session stores — a token → user mapping visible to every worker.

  • Distributed rate limiters — accurate global request-per-second counting.

  • Feature flags — a single flag store; updates propagate to all workers on the next message.

  • Distributed locks — a central lock arbiter that any worker can acquire.

  • Config broadcast — push a config change to all workers simultaneously (see [scope-2-all-workers-atomically]).

9.2. Port-Based Pattern (Explicit onconnect)

Use this pattern when a worker needs a dedicated two-way channel with the SharedWorker (i.e. replies must go back to the same worker that sent the request):

// /etc/nginx/js/session_sw.js — SharedWorker script

const store = new Map();   // token → {userId, expires}

// onconnect fires once per nginx worker when the channel is first used.
onconnect = (e) => {
    const port = e.ports[0];

    port.onmessage = (msg) => {
        const { cmd, token, data } = msg.data;

        if (cmd === 'get') {
            const entry = store.get(token) ?? null;
            // Reply only to the worker that asked
            port.postMessage({ token, entry });

        } else if (cmd === 'set') {
            store.set(token, { userId: data.userId,
                               expires: Date.now() + data.ttl });
            port.postMessage({ ok: true });

        } else if (cmd === 'del') {
            store.delete(token);
            port.postMessage({ ok: true });
        }
    };
};
// init.js (js_source)

const sessionSW = new SharedWorker('/etc/nginx/js/session_sw.js');

// Helper: promise-based call into the SharedWorker.
function swCall(cmd, token, data) {
    return new Promise(resolve => {
        sessionSW.port.onmessage = e => resolve(e.data);
        sessionSW.port.postMessage({ cmd, token, data });
    });
}

nginx.http.servers[0].locations
    .find(l => l.path === '/auth')
    .handler = async (req) => {
        const token = req.cookies['session'];
        if (!token) { req.respond(401, {}, 'no session'); return; }

        const { entry } = await swCall('get', token, null);
        if (!entry || entry.expires < Date.now()) {
            req.respond(401, {}, 'invalid or expired session');
            return;
        }

        req.setVar('authenticated_user', entry.userId);
        req.respond(200, {}, `Hello ${entry.userId}`);
    };

9.3. Broadcast Pattern (Global onmessage + clients)

Use this pattern when the SharedWorker needs to push the same message to all connected workers simultaneously:

// /etc/nginx/js/broadcast_sw.js

// No onconnect — global onmessage handles all workers via the `clients` array.
// `clients` is an array of all currently connected port objects.

onmessage = (msg) => {
    if (msg.data.cmd === 'broadcast') {
        // Forward the message to every connected worker
        clients.forEach(c => c.postMessage(msg.data.payload));
    }
};
// init.js: trigger a broadcast from any worker's request handler.
const broadcastSW = new SharedWorker('/etc/nginx/js/broadcast_sw.js');

// Each worker registers a listener on the SW port at init time.
broadcastSW.port.onmessage = (e) => {
    // This fires on every worker when a broadcast arrives.
    const { key, value } = e.data;
    // Apply the change to this worker's local copy of the config.
    applyFeatureFlag(key, value);
};

// Admin handler: update a feature flag on all workers at once.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/feature-flag')
    .handler = async (req) => {
        const { key, value } = JSON.parse(await req.readBody());

        // Tell the SharedWorker to broadcast to all workers.
        broadcastSW.port.postMessage({
            cmd: 'broadcast',
            payload: { key, value }
        });

        req.json({ ok: true });
    };

9.4. Dynamic SharedWorker Creation

SharedWorkers created in js_source are spawned before fork() and are available to all workers from the start. They can also be created dynamically from a request handler after fork():

// Create a SharedWorker on demand from a handler.
// The SharedWorker is registered globally and subsequent handlers
// calling new SharedWorker('/js/dynamic.js') reuse the same thread.

loc.handler = async (req) => {
    const sw = new SharedWorker('/etc/nginx/js/on_demand_sw.js');

    const result = await new Promise(resolve => {
        sw.port.onmessage = e => resolve(e.data);
        sw.port.postMessage({ req: req.uri });
    });

    req.json(result);
};

10. SharedArrayBuffers and Atomics

10.1. What They Are

A SharedArrayBuffer is a region of memory accessible — with zero copying — from any thread: nginx workers, JS Workers, and the SharedWorker thread.

Typed array views (Int32Array, Float64Array, BigInt64Array, etc.) over a SAB provide direct read/write access. Atomics operations (add, compareExchange, wait, notify) provide the synchronisation primitives needed for safe concurrent access.

10.2. Pre-Fork SABs (Visible to All Workers)

A SAB created in js_source is backed by the CoW page mapping inherited by every worker after fork(). All workers share the same physical pages.

// init.js (js_source)
// A global hit counter visible to all workers with zero copy.

const counterBuf = new SharedArrayBuffer(8);
const hits       = new BigInt64Array(counterBuf);
// hits[0] is shared by every worker process.

nginx.http.servers[0].locations
    .find(l => l.path === '/count')
    .handler = (req) => {
        // Atomic increment — safe across all nginx workers simultaneously.
        const n = Atomics.add(hits, 0, 1n);
        req.text(`Request #${n + 1n}\n`);
    };

nginx.http.servers[0].locations
    .find(l => l.path === '/stats')
    .handler = (req) => {
        req.json({ total_hits: Number(Atomics.load(hits, 0)) });
    };

10.3. Post-Fork SABs (Worker-Local, Passed via Channels)

A SAB created inside a request handler (post-fork) is backed by a Linux memfd and can be transferred to a JS Worker or SharedWorker via postMessage. The receiving thread `mmap`s the same file descriptor, establishing a shared mapping without copying data.

// Worker thread computes a result into a SAB; main thread reads it.

const processorWorker = new Worker('/etc/nginx/js/processor.js');

loc.handler = async (req) => {
    // Allocate shared memory for the result
    const resultBuf = new SharedArrayBuffer(1024);
    const result    = new Uint8Array(resultBuf);
    const ready     = new SharedArrayBuffer(4);
    const flag      = new Int32Array(ready);

    // Pass both SABs to the Worker; it writes the result and sets flag.
    processorWorker.postMessage({
        input:     JSON.parse(await req.readBody()),
        resultBuf, // shared — Worker writes here
        ready      // shared — Worker sets flag[0]=1 when done
    });

    // Non-blocking poll using Atomics.wait in the Worker thread
    // Meanwhile the event loop remains free.
    await new Promise(resolve => {
        processorWorker.onmessage = () => resolve();
    });

    req.respond(200, {}, new TextDecoder().decode(result));
};

10.4. Atomics.wait / Atomics.notify

Atomics.wait is a blocking call — it must only be used in Worker or SharedWorker threads, never in the main nginx event loop.

// Mutex implementation using SAB + Atomics.
// Safe to use in Worker and SharedWorker threads.

const mutexBuf = new SharedArrayBuffer(4);   // one Int32 = one mutex
const mutex    = new Int32Array(mutexBuf);

function lock() {
    // Spin until we CAS 0 → 1 (acquire)
    while (Atomics.compareExchange(mutex, 0, 0, 1) !== 0) {
        // Block this thread until mutex[0] changes — woken by unlock()
        Atomics.wait(mutex, 0, 1);
    }
}

function unlock() {
    Atomics.store(mutex, 0, 0);
    // Wake one waiting thread
    Atomics.notify(mutex, 0, 1);
}
// In the SharedWorker thread — use Atomics.wait/notify to signal workers.
// SharedWorker receives work, signals the waiting nginx worker via SAB.

onconnect = (e) => {
    const port = e.ports[0];

    port.onmessage = (msg) => {
        const { sab, workItem } = msg.data;
        const signal = new Int32Array(sab);

        // Do the work ...
        const result = processWork(workItem);

        // Write result into a different part of the SAB, then notify.
        // The nginx worker is blocked in Atomics.waitAsync on this index.
        Atomics.store(signal, 0, 1);       // mark done
        Atomics.notify(signal, 0);         // wake the nginx worker's Worker thread
    };
};
Atomics.waitAsync (non-blocking, returns a Promise) is available in the nginx event loop context and is the correct way to wait for a SAB value to change from the main thread.

11. Accept Control and Cross-Worker Coordination

11.1. The Problem

COM mutations applied directly from a handler affect only the worker that executed the handler. Other workers have independent CoW copies and will not see the change. Furthermore, if a mutation is applied while another request on the same worker is halfway through using the old value, the result can be inconsistent.

Accept control solves both problems by temporarily pausing connection acceptance, creating a window during which no new requests can start and the worker is in a known-clean state.

11.2. Per-Worker: suspendAcceptance / resumeAcceptance

These are synchronous, instant, and affect only the calling worker.

loc.handler = (req) => {
    // Stop accepting new connections on THIS worker.
    // OS backlog holds new connections; other workers keep accepting normally.
    nginx.suspendAcceptance();

    // Apply a batch of mutations atomically from this worker's perspective.
    const upstream = nginx.http.upstreams[0];
    upstream.peers[0].weight = 10;
    upstream.peers[1].weight = 5;
    upstream.peers[2].down   = true;

    // Resume accepting.
    nginx.resumeAcceptance();

    req.text('upstream updated\n');
};

What happens while suspended:

OS kernel
  │
  └── TCP SYN backlog accumulates (up to net.core.somaxconn connections)
          │
          └── When resumeAcceptance() is called, epoll fires again and
              the worker drains the backlog in FIFO order.

Other workers are unaffected and continue accepting normally.

11.3. Cross-Worker: suspendAllWorkers / resumeAllWorkers

For changes that must be atomic across all workers simultaneously:

Worker A (handler)
  │
  ├─ await nginx.suspendAllWorkers()
  │       │
  │       ├─ Workers B, C, … receive coordination signal
  │       │     Each finishes current request → stops accepting → ACKs
  │       └─ resolves when all have ACK'd
  │
  ├─ mutation window (all workers quiesced)
  │
  ├─ await nginx.resumeAllWorkers()
  │       └─ all workers re-add listening sockets to epoll
  │
  └─ req.respond(...)

11.4. SharedWorker Broadcast + Accept Control Pattern

The most flexible pattern for cross-worker config updates:

// coord_sw.js — SharedWorker for cross-worker coordination

const ports = [];   // one port per connected worker

onconnect = (e) => {
    const port = e.ports[0];
    ports.push(port);

    port.onmessage = (msg) => {
        if (msg.data.cmd === 'broadcast_apply') {
            // Push the same config update to every worker
            ports.forEach(p => p.postMessage({
                cmd:    'apply',
                config: msg.data.config
            }));
        }
    };
};
// init.js
const coordSW = new SharedWorker('/etc/nginx/js/coord_sw.js');

// Each worker registers a listener to apply inbound config changes.
coordSW.port.onmessage = (e) => {
    if (e.data.cmd === 'apply') {
        applyConfig(e.data.config);
        nginx.resumeAcceptance();
    }
};

function applyConfig(cfg) {
    // Apply upstream changes to this worker's local copy.
    const peers = nginx.http.upstreams[0].peers;
    cfg.peers.forEach((p, i) => {
        if (peers[i]) {
            peers[i].weight = p.weight;
            peers[i].down   = p.down;
        }
    });
}

// Admin endpoint: one worker drives the update, broadcasts to all others.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/config-push')
    .handler = async (req) => {
        const cfg = JSON.parse(await req.readBody());

        // Quiesce all workers, apply locally, then broadcast.
        await nginx.suspendAllWorkers();

        applyConfig(cfg);  // this worker applies locally

        // Tell SharedWorker to push to all workers; they will call
        // resumeAcceptance() from their onmessage handler.
        coordSW.port.postMessage({ cmd: 'broadcast_apply', config: cfg });

        // This worker also resumes acceptance.
        nginx.resumeAcceptance();

        req.json({ pushed: true });
    };

11.5. Backlog Behaviour

While any or all workers have acceptance suspended, incoming TCP connections queue in the OS SYN/accept backlog:

  • Backlog size is controlled by net.core.somaxconn (typically 128–4096) and the listen directive’s backlog=N parameter.

  • If the backlog fills before resumeAcceptance() is called, the kernel drops new SYN packets. From the client’s perspective this looks like the server is temporarily unavailable.

  • For short mutation windows (sub-millisecond), the probability of backlog overflow is negligible even under high load.

Do not hold all workers suspended for long operations (database queries, external HTTP calls). Complete all blocking work before calling suspendAllWorkers(), then apply changes synchronously in the mutation window.

12. Snapshots

Snapshots capture a point-in-time copy of a COM sub-tree. They are useful for rollback, for auditing config state, and for read-heavy operations that must be isolated from concurrent writes.

12.1. Basic Snapshot and Rollback

loc.handler = async (req) => {
    // Capture the current state of a location before mutating it.
    const snap = req.location.snapshot();

    try {
        // Attempt to apply new configuration.
        const cfg = JSON.parse(await req.readBody());
        req.location.gzip        = cfg.gzip;
        req.location.root        = cfg.root;
        req.location.proxy.pass  = cfg.proxyPass;

        req.json({ applied: true });
    } catch (e) {
        // Something went wrong — restore the original state.
        snap.restore();
        req.respond(500, {}, `Config apply failed: ${e.message}`);
    }
};

12.2. Sub-Object Snapshots

You can snapshot a specific COM sub-tree rather than the entire config:

// Snapshot just the upstream peer list.
const snap = nginx.http.upstreams[0].snapshot();

// Apply potentially risky changes.
nginx.http.upstreams[0].peers.forEach(p => p.weight = 1);

// If health-check fails, restore peer weights.
const healthy = await runHealthCheck();
if (!healthy) {
    snap.restore();
}

12.3. Read / Write Mode Interaction with Snapshots

When setWriteMode("local") is active, COM writes go to a per-request snapshot automatically, leaving the global config untouched:

loc.handler = async (req) => {
    // Isolate all writes to this request.
    req.location.setWriteMode('local');
    req.location.setReadMode('local');

    // Mutate the per-request copy freely.
    req.location.root = '/var/www/' + req.getVar('tenant');

    // Other concurrent requests still see the original global root.
    req.sendfile('/index.html');
};

14. Bootstrap Functions (nginx.createHttp / nginx.createStream)

These two functions let you instantiate the nginx HTTP or stream module entirely from JavaScript, without an http {} or stream {} block in nginx.conf. They are called inside a js_source script at init time and may be combined with nginx.http.addServer(), nginx.createSocket(), and nginx.http.attach() to build a completely JS-defined server topology.

14.1. nginx.createHttp([directives])

Creates the HTTP module as if an empty http {} block were present in nginx.conf.

Parameter Description

directives (optional)

A string containing http-context directives that would normally appear inside http { … }, e.g. 'access_log /var/log/nginx/access.log;'. Multiple directives may be separated by whitespace.

After nginx.createHttp() returns, nginx.http is available and fully functional. You can immediately call nginx.http.addServer(), nginx.http.upstreams, etc.

Full working example (from t/hello_world.t):

(function () {

    // 1. Bootstrap the HTTP module.
    nginx.createHttp('access_log /var/log/nginx/access.log;');

    // 2. Create a virtual server (nginx builds a default template when
    //    servers[] is empty).
    var srv = nginx.http.addServer('hello-world.local');

    // 3. Add a location and its JS content handler.
    srv.addLocation('/hello').handler = function (req) {
        req.respond(200, { 'content-type': 'text/plain' },
                    'JS COM: Hello World!\n');
    };

    // 4. Bind a TCP socket, attach it to the HTTP listener,
    //    and register the server.
    var sock = nginx.createSocket('0.0.0.0:8080');
    nginx.http.attach(sock).addServer(srv);

})();

14.2. nginx.createStream([directives])

Creates the stream module as if an empty stream {} block were present in nginx.conf.

Parameter Description

directives (optional)

A string containing stream-context directives, e.g. 'proxy_timeout 30s;'.

After nginx.createStream() returns, nginx.stream is available.

Full working example (from t/hello_stream.t):

(function () {

    // 1. Bootstrap the stream module.
    nginx.createStream();

    // 2. Create a stream server and attach a handler.
    var srv = nginx.stream.addServer();
    srv.handler = function (session) {
        session.finalize(200);   // accept and close cleanly
    };

    // 3. Bind a TCP socket, attach it to the stream module,
    //    and register the server.
    var sock = nginx.createSocket('0.0.0.0:9000');
    nginx.stream.attach(sock).addServer(srv);

})();

14.3. When to Use Bootstrap Functions

Situation Recommendation

Full server topology defined in JS (dynamic, data-driven)

Use nginx.createHttp() / nginx.createStream(). No static http {} / stream {} needed.

http {} block already in nginx.conf, only handlers vary

Skip createHttp(); use nginx.http.addServer() and addLocation() to augment the existing topology.

Mix of static and dynamic servers

Include a minimal http {} block in nginx.conf for any static servers; call nginx.http.addServer() for additional dynamic ones.

15. Master/Worker Scripting

In addition to running handlers in worker event loops, js_source scripts run in the master process and can hook into the master’s supervisory loop: reacting to worker lifecycle events, sending data to workers, and receiving data back.

15.1. Master Lifecycle Events (nginx.on)

Register callbacks with nginx.on(event, fn) in any js_source script. The callbacks run in the master process.

Event Callback signature When it fires

'workerSpawned'

fn(pid, slot)

A new worker process has started

'workerExited'

fn(pid, slot, status)

A worker process has exited

'reload'

fn()

SIGHUP received, old config still active

'reloaded'

fn()

SIGHUP complete, new workers are running

'reopen'

fn()

Example — log every worker lifecycle event to a file:

import * as std from 'std';

var evlog = '/var/log/nginx/worker-events.log';

function append(msg) {
    var f = std.open(evlog, 'a');
    if (f) { f.puts(msg + '\n'); f.close(); }
}

nginx.on('workerSpawned', function(pid, slot) {
    append('workerSpawned pid=' + pid + ' slot=' + slot);
});

nginx.on('workerExited', function(pid, slot, status) {
    append('workerExited pid=' + pid + ' slot=' + slot + ' status=' + status);
});

nginx.on('quit',     function() { append('quit');     });
nginx.on('reload',   function() { append('reload');   });
nginx.on('reloaded', function() { append('reloaded'); });
nginx.on('reopen',   function() { append('reopen');   });

15.2. Master → Worker Messages

The master can push arbitrary JSON-serializable data to one or all workers.

Method Description

nginx.sendToWorker(slot, data)

Send data to the worker at index slot. The worker receives it via nginx.on('message', fn).

nginx.broadcastToWorkers(data)

Send data to every running worker. Each worker receives its own copy via nginx.on('message', fn).

data must be JSON-serializable. It is transferred through the existing nginx channel socketpairs (the same fds used by ngx_channel_t), so no extra file descriptors are required.

Example — greet each worker as it spawns:

nginx.on('workerSpawned', function(pid, slot) {
    nginx.sendToWorker(slot, { event: 'hello', slot: slot, pid: pid });
});

// In the same js_source script, workers receive:
nginx.on('message', function(data) {
    nginx.log(nginx.INFO,
        'worker ' + nginx.workerIdx + ' received: ' + JSON.stringify(data));
});

15.3. Worker → Master Messages

Workers can send data back to the master at any time — typically from inside a request handler.

Method Description

nginx.sendToMaster(data)

Send data from the current worker to the master. data is JSON-serializable.

nginx.on('workerMessage', fn(slot, data))

Register a master-side handler. slot is the sender’s worker index; data is the received object.

The master’s event loop is woken via SIGIO (already set up by nginx for other channel operations), so no polling is needed.

Example — worker sends a health ping; master writes it to a log file:

import * as std from 'std';

// Master side: receive and log
nginx.on('workerMessage', function(slot, data) {
    var f = std.open('/var/log/nginx/worker-msgs.log', 'a');
    if (f) {
        f.puts('slot:' + slot + ' msg:' + data.msg + '\n');
        f.close();
    }
});

// Worker side: send on HTTP request
nginx.http.servers[0].locations
    .find(function(l) { return l.path === '/ping'; })
    .handler = function(req) {
        nginx.sendToMaster({ slot: nginx.workerIdx, msg: 'ping' });
        req.respond(200, {'content-type': 'text/plain'}, 'sent\n');
    };

15.4. nginx.workerIdx

Inside a worker process, nginx.workerIdx returns the zero-based slot index of the current worker (matches the slot parameter in lifecycle callbacks). In the master process it returns undefined.

16. nginx.repl — Interactive JavaScript REPL

nginx.repl provides an in-process JavaScript REPL that evaluates expressions inside a running nginx worker over a plain HTTP upgrade connection. It is useful for live introspection, ad-hoc mutations, and debugging without a restart.

16.1. How It Works

A request handler calls req.hijack() to take ownership of the raw TCP connection, then calls nginx.repl.attach() to redirect console.log / nginx.log output to that connection, and nginx.repl.listen() to install a line-by-line read loop. Each line received is evaluated by nginx.repl.eval() and the result is written back.

16.2. REPL API

Method Description

nginx.repl.eval(line)

Evaluate one line of JavaScript in the current worker’s context. Returns { status, value, message, stack }. status is "ok", "err", "incomplete", or "stack". value is the JSON-serialised result on success.

nginx.repl.attach(fd, loglevel, nginxlevel)

Start streaming console.log / console.warn / console.error and nginx.log output to fd. loglevel filters JS console methods (0 = log+warn+err, 1 = warn+err, 2 = err only); nginxlevel is the nginx log severity threshold.

nginx.repl.detach()

Stop streaming; restore normal log routing.

nginx.repl.listen(fd, fn)

Install a line-by-line read handler on fd. Each complete line (delimited by \n) is passed to fn(line).

nginx.repl._writeFd(fd, str)

Write raw bytes to a file descriptor. Used internally to send prompt and result lines.

req.hijack()

Detach the HTTP connection from nginx’s connection pool and return the raw file descriptor. The caller is now responsible for I/O and closing.

16.3. Wire Protocol

The client connects with an HTTP GET and the Upgrade: nginx-repl header. After the 101 upgrade response, the connection becomes a line-oriented plain-text stream:

# Client → server
<token> EVAL <javascript-expression>\n

# Server → client
<token> OK [<json-value>]\n      # success
<token> ERR <message>\n          # runtime error
<token> INCOMPLETE\n             # expression needs more input
<token> STACK <frame>\n          # stack trace line (one per frame)

Multiline input is handled by re-sending with accumulated lines until the server replies with something other than INCOMPLETE.

16.4. Embedding the REPL

// Install a REPL endpoint on /repl
nginx.http.servers[0].locations
    .find(function(l) { return l.path === '/repl'; })
    .handler = function(req) {
        if ((req.headers['upgrade'] || '').toLowerCase() !== 'nginx-repl') {
            return req.respond(400, {}, 'Expected Upgrade: nginx-repl\n');
        }

        var params = req.queryParams;
        var loglevel   = parseInt(params.loglevel   || '0');
        var nginxlevel = parseInt(params.nginxlevel || '6');

        req.respond(101, {
            'upgrade':    'nginx-repl',
            'connection': 'upgrade'
        }, '');

        var fd = req.hijack();
        nginx.repl.attach(fd, loglevel, nginxlevel);
        nginx.repl.listen(fd, function(line) {
            var r = nginx.repl.eval(line);
            if (r.status === 'ok') {
                nginx.repl._writeFd(fd,
                    '- OK' + (r.value !== undefined ? ' ' + r.value : '') + '\n');
            } else if (r.status === 'incomplete') {
                nginx.repl._writeFd(fd, '- INCOMPLETE\n');
            } else {
                nginx.repl._writeFd(fd, '- ERR ' + (r.message || '') + '\n');
            }
        });
    };

18.2. Pattern B — Network at Startup (js_preprocess + std.urlGet)

18.3. Pattern C — Live Reload via Handler (Zero Downtime)

For changes that do not require a full restart — upstream weights, SSL certificates, location handlers — apply mutations via the COM from a request handler:

// init.js

function applyConfig(cfg) {
    // Update upstream peer weights
    if (cfg.upstreams) {
        for (const [name, peerCfg] of Object.entries(cfg.upstreams)) {
            const up = nginx.http.upstreams.find(u => u.name === name);
            if (!up) continue;
            for (const [addr, w] of Object.entries(peerCfg)) {
                const peer = up.peers.find(p => p.addr === addr);
                if (peer) peer.weight = w;
            }
        }
    }

    // Hot-swap SSL certificates
    if (cfg.ssl) {
        for (const [domain, paths] of Object.entries(cfg.ssl)) {
            const srv = nginx.http.servers.find(s => s.names.includes(domain));
            if (!srv) continue;
            srv.ssl.cert = paths.cert;
            srv.ssl.key  = paths.key;
        }
    }
}

// Admin endpoint: POST the new config JSON.
nginx.http.servers
    .find(s => s.names.includes('admin.internal'))
    .locations.find(l => l.path === '/config/apply')
    .handler = async (req) => {
        const cfg = JSON.parse(await req.readBody());

        await nginx.suspendAllWorkers();
        applyConfig(cfg);
        await nginx.resumeAllWorkers();

        req.json({ applied: true, ts: Date.now() });
    };

// Pull-based reload: a background Worker polls the config service
// periodically and applies changes.
const pollerWorker = new Worker('/etc/nginx/js/config_poller.js');
pollerWorker.onmessage = async (e) => {
    if (e.data.type === 'config-update') {
        await nginx.suspendAllWorkers();
        applyConfig(e.data.config);
        await nginx.resumeAllWorkers();
    }
};
// /etc/nginx/js/config_poller.js — JS Worker thread
import * as std from 'std';

let lastETag = '';

while (true) {
    // Poll every 30 seconds
    os.sleep(30000);

    const res = std.urlGet('http://config-service.internal/v1/nginx-config',
                           { full: true });
    const etag = (res.headers || {})['etag'] || '';

    if (res.status === 200 && etag !== lastETag) {
        lastETag = etag;
        postMessage({ type: 'config-update', config: JSON.parse(res.body) });
    }
}

19. Third-Party Module Integration

19.1. Overview

Any nginx module can expose its configuration to the COM by implementing a small bridge file that reads the module’s C config structs and projects them as JS properties.

This section walks through adding COM support to a hypothetical ngx_http_mymod module with a main-level config struct.

19.2. Step 1 — Identify the Config Structs

/* ngx_http_mymod.h */

typedef struct {
    ngx_flag_t   enable;
    ngx_uint_t   max_entries;
    ngx_str_t    backend_url;
} ngx_http_mymod_main_conf_t;

typedef struct {
    ngx_msec_t   timeout_ms;
    ngx_flag_t   cache;
} ngx_http_mymod_loc_conf_t;

extern ngx_module_t  ngx_http_mymod_module;

19.3. Step 2 — Write the COM Bridge File

Create ngx_js_com_mymod.c next to your module sources:

/* ngx_js_com_mymod.c */
#include <ngx_config.h>
#include <ngx_core.h>
#include <ngx_http.h>
#include "quickjs.h"
#include "ngx_js.h"
#include "ngx_http_mymod.h"

/*
 * Getter / setter for main-conf properties.
 * 'magic' selects which property (same pattern as NginxRequest).
 */
static JSValue
ngx_js_mymod_main_get(JSContext *ctx, JSValueConst this_val, int magic)
{
    ngx_http_mymod_main_conf_t  *mcf;

    /* Retrieve the main config from the cycle. */
    mcf = ngx_http_cycle_get_module_main_conf(ngx_cycle,
                                              ngx_http_mymod_module);
    if (mcf == NULL) {
        return JS_UNDEFINED;
    }

    switch (magic) {
    case 0: return JS_NewBool(ctx, mcf->enable);
    case 1: return JS_NewUint32(ctx, mcf->max_entries);
    case 2: return JS_NewStringLen(ctx, (char *) mcf->backend_url.data,
                                   mcf->backend_url.len);
    }
    return JS_UNDEFINED;
}

static JSValue
ngx_js_mymod_main_set(JSContext *ctx, JSValueConst this_val,
    JSValueConst val, int magic)
{
    ngx_http_mymod_main_conf_t  *mcf;

    mcf = ngx_http_cycle_get_module_main_conf(ngx_cycle,
                                              ngx_http_mymod_module);
    if (mcf == NULL) {
        return JS_EXCEPTION;
    }

    switch (magic) {
    case 0:
        mcf->enable = JS_ToBool(ctx, val);
        break;
    case 1:
        JS_ToUint32(ctx, &mcf->max_entries, val);
        break;
    /* backend_url is an ngx_str_t backed by pool memory — omit setter
       or implement with careful pool allocation */
    }
    return JS_UNDEFINED;
}

/*
 * Install nginx.http.mymod into ctx.
 * Called from ngx_js_install_nginx_com() during init_conf.
 */
ngx_int_t
ngx_js_com_mymod_install(JSContext *ctx, JSValueConst nginx_obj)
{
    JSValue  http_obj, mymod_obj;

    /* Retrieve the existing nginx.http object. */
    http_obj = JS_GetPropertyStr(ctx, nginx_obj, "http");
    if (JS_IsUndefined(http_obj)) {
        return NGX_ERROR;
    }

    mymod_obj = JS_NewObject(ctx);
    if (JS_IsException(mymod_obj)) {
        JS_FreeValue(ctx, http_obj);
        return NGX_ERROR;
    }

    /* Expose enable / maxEntries / backendUrl as JS properties. */
    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "enable"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_enable", 0,
                             JS_CFUNC_generic_magic, 0),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_set, "set_enable", 1,
                             JS_CFUNC_generic_magic, 0),
        JS_PROP_CONFIGURABLE);

    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "maxEntries"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_maxEntries", 0,
                             JS_CFUNC_generic_magic, 1),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_set, "set_maxEntries", 1,
                             JS_CFUNC_generic_magic, 1),
        JS_PROP_CONFIGURABLE);

    JS_DefinePropertyGetSet(ctx, mymod_obj,
        JS_NewAtom(ctx, "backendUrl"),
        JS_NewCFunctionMagic(ctx, ngx_js_mymod_main_get, "get_backendUrl", 0,
                             JS_CFUNC_generic_magic, 2),
        JS_UNDEFINED,   /* no setter — read-only */
        JS_PROP_CONFIGURABLE);

    JS_SetPropertyStr(ctx, http_obj, "mymod", mymod_obj);
    JS_FreeValue(ctx, http_obj);

    return NGX_OK;
}

19.6. Location-Level Config

For per-location config, retrieve the conf pointer from the request’s loc_conf array rather than the cycle:

/* In a JS getter called from a request handler context */
static JSValue
ngx_js_mymod_loc_get_timeout(JSContext *ctx, JSValueConst this_val, int magic)
{
    ngx_http_request_t          *r;
    ngx_js_worker_t             *w;
    ngx_http_mymod_loc_conf_t   *lcf;

    w = JS_GetContextOpaque(ctx);
    r = w->current_request;
    if (r == NULL) {
        return JS_UNDEFINED;
    }

    lcf = ngx_http_get_module_loc_conf(r, ngx_http_mymod_module);
    return JS_NewUint32(ctx, lcf->timeout_ms);
}

20. Resource Protection

20.1. Worker Memory Limit

nginx.workerMemoryLimit caps the QuickJS heap for all JS allocations in a worker process. The limit applies on top of nginx’s own memory — it measures only memory allocated through the QuickJS allocator.

// Set from js_source — applies to every worker after fork().
nginx.workerMemoryLimit = 128 * 1024 * 1024;  // 128 MB per worker

// Read back the configured limit (0 = unlimited).
nginx.log(nginx.INFO, `Memory limit: ${nginx.workerMemoryLimit}`);

When a JS allocation exceeds the limit, QuickJS throws RangeError: out of memory. The worker process remains healthy; the individual request receives a 500 error.

loc.handler = (req) => {
    try {
        const huge = new ArrayBuffer(512 * 1024 * 1024);  // exceeds limit
        req.text('allocated\n');
    } catch (e) {
        // e is RangeError: out of memory
        req.respond(503, {}, 'memory limit exceeded, try again\n');
    }
};

20.2. Worker Request Timeout

nginx.workerRequestTimeout sets the maximum wall-clock time (in milliseconds) a single JS handler invocation may consume. If the handler runs longer than this (including time spent in a tight synchronous loop), QuickJS fires an interrupt that aborts the handler. The worker survives and the request receives HTTP 500.

// Allow each handler at most 5 seconds of wall time.
nginx.workerRequestTimeout = 5000;

// Re-configure at runtime from a handler.
nginx.http.servers[0].locations
    .find(l => l.path === '/admin/timeout')
    .handler = (req) => {
        const ms = parseInt(req.queryParams.ms);
        if (ms >= 0) nginx.workerRequestTimeout = ms;
        req.text(`timeout is now ${nginx.workerRequestTimeout} ms\n`);
    };

20.3. Error Isolation

JavaScript exceptions in a handler are caught by the module framework and converted to HTTP 500 responses. The worker process never crashes due to an unhandled JS exception.

loc.handler = (req) => {
    // This exception is caught by the framework — worker stays up.
    throw new Error('deliberate error');
    // Client receives: HTTP/1.1 500 Internal Server Error
};

20.4. What JS Cannot Do

The JS runtime runs inside an nginx worker process (or master, for SharedWorkers) with the same OS privileges. The following restrictions apply:

  • No access to nginx’s internal C memory outside the COM API. There is no ctypes, ffi, or equivalent.

  • No subprocess spawning from handlers or SharedWorkers. The os.exec() function from QuickJS os is available only in Workers and js_preprocess scripts, not in nginx event-loop handlers.

  • Blocking the event loop with a synchronous tight loop is interrupted by the request timeout if nginx.workerRequestTimeout is set.

  • Atomics.wait (blocking) must not be called from the event loop; use Atomics.waitAsync (non-blocking, returns a Promise) instead.
