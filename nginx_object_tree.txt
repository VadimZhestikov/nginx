❯ what nginx modules can be reconfigured without usual nginx config reload?     

● There are two distinct categories depending on when the change happens and how
   far it propagates:

  ---
  1. Cross-worker live reconfiguration (shared memory — no reload, instant, all 
  workers)

  Only upstream load-balancing works here, because nginx stores the active peer
  state in a shared memory zone (zone directive):

  NginxRRPeer — readable and writable from request handlers, changes visible
  immediately to all workers:
  upstream[].peers[].weight        — shift traffic weight
  upstream[].peers[].down          — take a backend out of rotation
  upstream[].peers[].maxFails      — adjust failure threshold
  upstream[].peers[].failTimeout   — adjust penalty period
  upstream[].peers[].maxConns      — cap per-backend concurrency
  upstream[].addPeer(addr, opts)   — add a backend server on the fly
  upstream[].removePeer(addr)      — remove a backend server on the fly

  This is the only mechanism that is truly cross-worker (changes written through
   one worker are immediately seen by all others), because the data lives in a
  named shared memory zone, not in COW-forked process memory.

  Requirement: the upstream block must have a zone directive. Without it there 
  is no shared memory and peer state is per-worker.

  ---
  2. Per-worker runtime reconfiguration (COW memory — change affects only that 
  worker)

  Writable properties that live in the worker's own copy-on-write address space.
   A change made in one worker's request handler is not visible to other
  workers:

  nginx.workerMemoryLimit          — JS heap cap for this worker (bytes,
  0=unlimited)
  nginx.workerRequestTimeout       — per-request JS deadline for this worker
  (ms, 0=none)
  location.handler                 — swap out the JS content handler function
  location.root / server.root      — change document root path

  These are useful for per-worker self-tuning (e.g., a handler that detects high
   load and tightens its own timeout), but not for coordinated config changes
  across the whole nginx instance.

  ---
  3. Pre-fork reconfiguration (js_source / js_init_http — before workers fork, 
  all workers inherit)

  Everything writable in the COM, plus config generation, runs during init_conf.
   Since workers inherit via fork, all of them see the result:

  - All location.* / server.* r/w fields
  - nginx.cycle.workers
  - upstream[] peer fields (NginxPeer, config-phase)
  - Config injection via config.write() (js_preprocess) or js_init_http

  But this still requires an nginx reload to trigger — it's just that the reload
   does not need to touch nginx.conf on disk because the JS script generates the
   config dynamically.

  ---
  Summary

  ┌──────────────┬─────────────────────────────────────────┬───────────────┐
  │    Scope     │            Module / Property            │   Mechanism   │
  ├──────────────┼─────────────────────────────────────────┼───────────────┤
  │ All workers, │ Upstream peer weight/down/add/remove    │ Shared memory │
  │  instant     │                                         │  zone         │
  ├──────────────┼─────────────────────────────────────────┼───────────────┤
  │ This worker  │ workerMemoryLimit,                      │ COW process   │
  │ only         │ workerRequestTimeout, location.handler, │ memory        │
  │              │  location.root                          │               │
  ├──────────────┼─────────────────────────────────────────┼───────────────┤
  │ All workers, │ Everything else writable                │ Fork          │
  │  on reload   │                                         │ inheritance   │
  └──────────────┴─────────────────────────────────────────┴───────────────┘

  The practical answer for "without config reload": upstream peers are the only
  thing that propagates to all workers instantly. Everything else either
  requires a reload or only affects the worker that made the change.

❯ What modules have internal state which affect request/response processing     
between phase handlers?                                                         

● This is a deep architectural question. The answer spans three different kinds
  of "internal state":

  ---
  1. Cross-phase request state (set in one phase, read in another)

  These modules write into r->* fields or per-request contexts that later phases
   depend on:

  ngx_http_rewrite_module
  - Sets r->uri_changed, r->internal, r->rewritten — these control whether nginx
   loops back through server/location resolution after a rewrite
  - Tracks redirect count in r->main->count to detect infinite rewrite loops
  - The script engine's variable assignments live in r->variables[] and are
  visible to all subsequent phases

  ngx_http_realip_module (POST_READ)
  - Rewrites r->connection->addr_text, r->connection->sockaddr in-place
  - Access module, geo module, and log module in later phases see the replaced
  client address, not the original TCP source

  ngx_http_auth_request_module (ACCESS)
  - Issues a subrequest; stores result in its per-request context
  - Gates POST_ACCESS phase: if the subrequest returned non-2xx, the main
  request is rejected before CONTENT phase runs

  ngx_http_limit_req_module (PREACCESS → LOG)
  - On PREACCESS: acquires a slot in a shared memory rbtree; may delay the
  request
  - On request cleanup (LOG-equivalent): releases the slot
  - The "was this request delayed" flag lives in per-request context and affects
   whether the delay is charged

  ngx_http_limit_conn_module (PREACCESS → LOG)
  - Increments a shared memory counter on PREACCESS
  - Registers a cleanup handler that decrements it at LOG phase — the decrement
  is state that depends on the request having been accepted earlier

  ngx_http_userid_module (CONTENT → LOG)
  - Parses incoming cookie in content phase
  - May set/update $uid_got/$uid_set variables
  - Cookie is sent in response headers, but the variable values cross into the
  log phase for logging

  ---
  2. Modules with significant intra-request streaming state (filter chain)

  These run in the body filter chain; their state accumulates across multiple 
  ngx_http_output_filter() calls for a single request — i.e., between successive
   invocations of the same phase handler for chunked data:

  ngx_http_sub_filter_module
  - Maintains a KMP automaton state machine across buffer boundaries
  - Partial-match buffer: a string that started matching the search pattern at
  the end of one buffer may complete in the next
  - ctx->tried flag prevents re-application after sub_filter_once on

  ngx_http_charset_filter_module
  - Holds an iconv_t conversion descriptor open across buffer calls
  - Multi-byte character boundary state: a character may be split across two
  output buffers

  ngx_http_gzip_filter_module
  - Holds a live z_stream (zlib deflate context) across the entire response
  - Output is not flushed on every call; zlib internal buffering state persists

  ngx_http_gunzip_filter_module
  - Same pattern with z_stream inflate context

  ngx_http_ssi_filter_module
  - Full SSI parser state machine across chunks: tag scanning position, <!--#
  partial-match state
  - Manages a stack of active SSI blocks (if/else nesting)
  - Issues subrequests mid-stream and buffers output while waiting for them

  ngx_http_slice_filter_module
  - Tracks the current byte offset into the sliced range
  - Each slice is a separate internal subrequest; the filter orchestrates them
  sequentially, replacing the main request's range header between subrequests

  ---
  3. Modules that buffer the entire response body before processing

  These effectively "hold" the response across all body filter calls until the
  upstream sends the final buffer:

  ngx_http_image_filter_module
  - Accumulates all body buffers into one contiguous block
  - Only processes and re-emits the image (resize/crop/rotate) on last buffer
  received

  ngx_http_xslt_filter_module
  - Same pattern: accumulates entire body, builds an xmlDoc, applies XSLT, emits
   transformed output
  - libxslt state lives in per-request context from first to last buffer

  ngx_http_addition_filter_module
  - Issues subrequests for add_before_body and add_after_body
  - Buffers the main response body while waiting for the "before" subrequest to
  finish

  ---
  4. Upstream connection state (CONTENT phase spanning multiple event loop 
  iterations)

  ngx_http_upstream_module (base for proxy, fastcgi, scgi, uwsgi, memcached,
  grpc)
  - Maintains the entire upstream state machine in r->upstream
  (ngx_http_upstream_t):
    - Peer connection, SSL handshake state
    - Send buffer (request to backend) / receive buffer (response from backend)
    - Retry count and which peer was tried last
    - Header parse state (partial headers across TCP segments)
    - Buffered-proxy disk write state
  - This is all "between invocations of the same content handler" triggered by
  I/O events, not a different phase, but it is long-lived state that outlasts
  any single event loop iteration

  ngx_http_fastcgi_module adds:
  - FastCGI framing parser state: record type, payload length, remaining bytes
  for the current record

  ---
  What this means for the JS COM

  Currently the COM exposes only static configuration (the merged *_loc_conf_t,
  *_srv_conf_t structs). None of the per-request dynamic state described above
  is visible or writable from JavaScript — no r->upstream, no zlib stream, no
  sub filter automaton state.

  The most actionable consequence: when you write a JS content handler
  (location.handler), you are replacing nginx's content phase entirely for that
  location. The filter chain modules (gzip, sub_filter, SSI, etc.) still run on
  your response — their state machines activate on whatever buffers your handler
   produces via r.respond() or r.write().

❯ question: having last answer in the mind, which of all core modules can be    
reconfigured safely on the fly (from JS called by nginx event loop (as example, 
 by nginx.setTimeout() in nginx workers) ?                                      

● This is a subtle but important question. The key architectural distinction is:

  Does the module read its config struct field on every request invocation, or 
  does it pre-build derivative data structures at init time that the field 
  merely parameterises?

  If a module re-reads clcf->field on every request, changing the field is safe.
   If it built a compiled structure (KMP table, regex bytecode, hash table,
  OpenSSL context) from the field once, changing the field has no effect and
  could leave the derivative structure inconsistent.

  The JS event loop gives you single-threaded exclusivity within the worker — no
   nginx module code runs concurrently while your JS callback runs. But other
  workers are separate processes running concurrently in shared memory.

  ---
  Fully safe — designed for runtime changes

  These are either pure JS properties or use nginx's shared memory rwlock
  protocol:

  nginx.workerMemoryLimit           — applied before every JS_Call, no nginx
  internals
  nginx.workerRequestTimeout        — applied before every JS_Call, no nginx
  internals
  location.handler                  — JS function swap, purely within QuickJS
  heap

  upstream[].peers[].weight         — shm rwlock; upstream reads under lock
  upstream[].peers[].down           — shm rwlock
  upstream[].peers[].maxFails       — shm rwlock
  upstream[].peers[].failTimeout    — shm rwlock
  upstream[].peers[].maxConns       — shm rwlock
  upstream[].addPeer()              — shm rwlock
  upstream[].removePeer()           — shm rwlock

  ---
  Safe in practice — module re-reads the field on every request

  No derivative structures; the module does a straight clcf->field read at
  request time. Changing the field between requests takes effect immediately
  with no risk:

  Static/core request handling
  location.root / server.root           — read at start of each static
  file/proxy resolve
  location.defaultType                  — read when setting Content-Type
  location.sendfile / tcpNopush / tcpNodelay / etag
  location.keepaliveTimeout / keepaliveRequests / keepaliveTime
  location.clientMaxBodySize            — checked when body arrives
  location.clientBodyTimeout
  location.sendTimeout
  location.alias
  location.satisfy                      — read at access phase
  location.limitExcept                  — read at access phase
  location.errorPage[]                  — read when generating error response

  Upstream/proxy timeouts — copied into r->upstream at connection start; safe to
   change between requests:
  proxy.connectTimeout / sendTimeout / readTimeout
  proxy.nextUpstreamTries / nextUpstreamTimeout
  proxy.interceptErrors / buffering / requestBuffering
  fastcgi.connectTimeout / sendTimeout / readTimeout
  scgi/uwsgi/memcached — same timeout fields

  Filter module flags — read at the start of each response's filter chain:
  gzip.enable / level / minLength / vary   — checked per response
  gunzip.enable
  autoindex.enable / format / localtime / exactSize
  subFilter.once / lastModified            — flags only; safe between responses
  addition.addBeforeBody / addAfterBody    — URI read at precontent phase
  mirror.uris[] / requestBody             — read at precontent phase
  slice.size                               — read at start of slicing (between
  subrequests)

  Access/auth — re-evaluated per request:
  access.rules[]                           — iterated on each access check
  auth.userFile                            — file path re-read on each auth
  check
  auth.realm                               — sent in WWW-Authenticate header
  each time
  limitReq.logLevel / statusCode / dryRun
  limitConn.logLevel / statusCode / dryRun
  authRequest.uri                          — subrequest URI read at access phase

  ---
  Unsafe — pre-built derivative structures, changing the field has no effect

  These modules build a compiled artifact from config at init/first-use time.
  The field you can write is stale metadata; the real logic runs from the
  artifact:

  rewrite rules (.hasRules, .stackSize)
    → scripts compiled to QuickJS-like bytecode at parse time; not re-compiled

  subFilter.pairs[]
    → KMP failure function table built at first response; changing pairs[]
      would desync from the already-running automaton state for live responses

  charset.charset / sourceCharset
    → iconv_t descriptor opened once; not re-opened on field change

  SSL (certificate, certificateKey, ciphers, protocols, …)
    → OpenSSL SSL_CTX built once at init; these fields are metadata after that

  server names / serverNamesHashMaxSize / serverNamesHashBucketSize
    → hash table built once during post-configuration; field change doesn't
  rebuild it

  variables hash / variablesHashMaxSize / variablesHashBucketSize
    → same: hash built once, indexes already distributed to all modules

  cycle.workers
    → field write doesn't signal master process; master controls worker
  lifecycle
      independently of this field value

  imageFilter.action / width / height / angle
    → GD/libpng processing parameters read once per response (actually safe
      between responses, but the image is processed as a whole — no mid-stream
      state machine to corrupt)

  xslt parameters
    → libxslt stylesheet compiled once; runtime XSLT param values safe between
      responses but the stylesheet itself is not reloadable

  secureLink.secret
    → HMAC computed fresh each request — actually safe to change between
  requests
      (the new secret takes effect on the next check)

  ---
  The precise safety boundary

             ┌─ reads field on every request/response? ──────► SAFE to change
             │
  config ────┤
  field      │
             └─ was used to build a table/context/bytecode? ─► UNSAFE to change
                                                                 (the field is
  now
                                                                  dead metadata)

  The modules that are safe to tune from a setTimeout callback or request
  handler are primarily: upstream load-balancing, timeouts, document root,
  content handler, and simple on/off flags in filter modules. Anything that
  involved compilation, hashing, or cryptographic context construction at init
  time cannot be meaningfully reconfigured this way.

  Here's how each unsafe case would need to be handled:

  ---
  Sub filter — KMP tables

  What to rebuild: the KMP failure function table for each pattern in pairs[].

  /* ngx_http_sub_filter_module.c builds tables in ngx_http_sub_init_tables()
     called lazily on first response. Expose a method: */
  location.subFilter.setPairs([{match, replacement}, ...])

  The setter would:
  1. Write new slcf->pairs array
  2. Call ngx_http_sub_init_tables(cf, slcf) to rebuild KMP tables
  3. Only safe between responses (not while a body filter is mid-stream)

  Risk: must not be called while a response using this location is being
  filtered. Since JS runs in the event loop and body filtering is synchronous
  within a single event loop tick, calling from setTimeout between requests is
  safe.

  ---
  Charset — iconv descriptor

  What to rebuild: close old iconv_t, open a new one.

  location.charset.setCharset(charset, sourceCharset)

  The setter would:
  1. Find or open a new iconv_t for the new pair
  2. Replace the stored descriptor
  3. The per-request filter context holds its own iconv_t copy — only new
  requests get the new descriptor

  ---
  SSL — OpenSSL SSL_CTX

  This is the most complex. nginx already has a solution: ngx_ssl_t holds an
  SSL_CTX*. There are two levels:

  server.ssl.setCertificate(certPath, keyPath)
  server.ssl.setCiphers(cipherString)
  server.ssl.setProtocols([...])

  Each setter would:
  1. Write the metadata field
  2. Call SSL_CTX_use_certificate_file() / SSL_CTX_use_PrivateKey_file() /
  SSL_CTX_set_cipher_list() on the existing SSL_CTX*

  This is actually what nginx already does on graceful reload — the same SSL_CTX
   can be updated in place. Existing TLS connections keep their old session; new
   handshakes use the new cert/ciphers.

  This is the most valuable one — dynamic certificate rotation without reload.

  ---
  Server name hash

  What to rebuild: call ngx_hash_init() on the names array.

  server.setNames([...])

  The setter would:
  1. Update cscf->server_names array
  2. Reallocate and rebuild the hash in cycle->pool (or a dedicated pool)
  3. Swap the pointer atomically

  Complexity: the hash is also used by ngx_http_find_virtual_server() at the
  http-block level — a single server's hash feeds into a larger virtual server
  dispatch table. Rebuilding one server's names in isolation requires
  understanding the full virtual server dispatch tree.

  ---
  Rewrite rules

  This is the hardest and probably not worth doing:

  location.rewrite.setRules(scriptText)

  Would require:
  1. Creating a temporary ngx_conf_t
  2. Running ngx_http_rewrite_module's directive handler on the script text
  3. Compiling new bytecode into a fresh array
  4. Swapping rlcf->codes

  Verdict: too invasive. Better to replace location.handler with a JS function
  that does the equivalent logic — JS is already a superset of what rewrite
  scripts can express.

  Variables hash

  already has ngx_http_variables_init_vars() for this — calling it again after

  Verdict: addVariable() already only works during js_init_http (config phase)
